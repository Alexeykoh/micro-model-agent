# Loopback-доступ веб-тулов (`security.network.allowLoopback`)

> **Дата:** 2026-11-03. Закрывает TODO §1.12 «Localhost-проверки для веб-разработки».
> **Статус:** реализовано. **Решение:** loopback-only за явным конфиг-флагом.

## Проблема

Агент, разрабатывающий веб-приложение, не может проверить результат своей же работы:
`web_fetch`, `web_browse` и браузерная политика URL блокируют `localhost`, `127.0.0.1`
и `::1` как SSRF. Дефолтный `deniedDomains` содержит эти хосты, а `isIpPrivate`
относит весь `127.0.0.0/8` к приватным. В итоге цикл «запустил dev-сервер → открыл
страницу → увидел ошибку» недоступен: модель либо сдаётся, либо просит пользователя
проверить вручную.

Открыть приватную сеть целиком (`allowPrivateOutbound`) для этого нельзя: флаг снимает
SSRF-защиту со всех приватных адресов и предназначен для callback'ов каркаса, а не для
браузера/чтения URL. Нужен отдельный узкий флаг.

## Флаг

`security.network.allowLoopback: boolean` (default `false`).

- Ключ реестра: `security.network.allowLoopback`, домен `security`, без `reconfigure`.
- i18n-подписи: `config.key.security.network.allowLoopback` и `config.desc...` в `en`/`ru`.
- `deniedDomains` по умолчанию **не меняются** (`localhost`, `127.0.0.1`, `::1` остаются).

## Точный охват

Один предикат `isLoopbackHost(host)` (`src/modules/security/ip-guard.ts`, реэкспорт из
`network-validator`):

- `localhost` (регистр и хвостовая точка FQDN нормализуются);
- IPv4 `127.0.0.0/8` — dotted-quad, сокращённые (`127.1`), целые/hex/octal формы;
- IPv6 `::1`, включая развёрнутую запись, и IPv4-mapped loopback (`::ffff:127.0.0.1`);
- скобки IPv6-литерала (`[::1]`) снимаются.

При `allowLoopback === true` loopback-хост обходит **только**:

1. private-IP блок (`isIpPrivate`) для самого loopback-адреса;
2. записи `deniedDomains`, которые сами являются loopback (`localhost`, `127.0.0.1`, `::1`).

Всё остальное действует без изменений:

- приватная LAN (`10/8`, `172.16/12`, `192.168/16`, link-local/metadata, CGNAT и т.д.)
  по-прежнему блокируется;
- прочие `deniedDomains` (внешние и пользовательские) по-прежнему блокируют;
- `allowedDomains` (непустой) применяется к loopback так же, как к любому хосту;
- не-`http(s)` схемы по-прежнему запрещены;
- DNS-гард по-прежнему блокирует публичное имя, резолвящееся в приватный адрес:
  исключение сделано для loopback-**литерала**, а не для «любого имени, ведущего на
  127.0.0.1» (это классический канал DNS-rebinding);
- `allowPrivateOutbound` сохраняет прежний смысл и не пересекается с новым флагом.

Точки применения (общий путь, отдельные правки тулов не нужны):

- `isUrlAllowed` / `isUrlAllowedAsync` → `web_fetch` (`fetchValidated` на каждом
  редиректе), `web_browse` и rest-маршруты через `checkBrowserUrl`;
- `checkOutboundUrl` → исходящие вызовы каркаса (webhook аудита, callback задачи).

`verify browser:` (`runBrowserCheck`) политику URL не вызывает — он и раньше
открывал любой `http(s)` URL напрямую; новый флаг на него не влияет.

## Системный промпт

При включённом флаге в блок `SECURITY RESTRICTIONS` добавляется строка, что loopback
URL dev-сервера разрешены. Это снимает ложный вывод модели «localhost запрещён
навсегда» и экономит итерацию на пробном блокированном вызове.

## Тесты

`tests/security/loopback-access.test.ts`:

- default off: `localhost`, `127.0.0.1`, `::1` блокируются;
- flag on: те же хосты разрешены (sync и DNS-aware путь);
- flag on: `10.0.0.1`, `192.168.1.1`, внешний deny-домен и `file:` блокируются;
- непустой `allowedDomains` продолжает ограничивать loopback;
- `checkOutboundUrl` повторяет поведение (loopback — да, LAN — нет);
- `checkBrowserUrl` (путь `web_browse`) разрешает `http://localhost:5173/` только с флагом.

`tests/config/registry.test.ts`: ключ читается как `off`, ставится в `on`, эффектов
`reconfigure` не даёт.

`tests/i18n.test.ts`: обе локали содержат `config.key/desc` для ключа (общий гвард
«каждый ключ реестра подписан»).

## Остаточные риски

1. **Loopback-сервисы без аутентификации.** С флагом модель может обратиться к любому
   локальному порту (админки, отладочные endpoint'ы, metadata-прокси на loopback).
   Это осознанная цена: флаг выключен по умолчанию и включается пользователем.
2. **DNS-rebinding через loopback-литерал исключён**, но публичное имя, резолвящееся в
   loopback, по-прежнему блокируется. Если понадобится `*.localhost`-имя — это отдельное
   расширение политики, а не побочный эффект флага.
3. **`verify browser:` не проходит политику URL** (существующее поведение, не регрессия).
   Отдельная задача — провести `runBrowserCheck` через `checkBrowserUrl`.
4. **Флаг не влияет на `allowPrivateOutbound`**; комбинация обоих флагов открывает и LAN,
   и loopback, что ожидаемо и явно.
