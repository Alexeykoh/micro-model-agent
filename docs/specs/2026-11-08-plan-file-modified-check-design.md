# Plan check `file-modified:` — проверка правки существующего файла

Дата: 2026-11-08. Сессия-мотивация: `ses_mw7z4mav` (правка UI-индикатора обновления).

## Проблема

Шаг плана «Правка `panels.ts`: убрать `.upd-dot`, встроить точку в кнопку» закрывался
проверкой `file-exists:panels.ts`. Файл существовал до правки, поэтому `done` проходил
по чтению файла без единой правки: агент 64 вызова тулов (28 чтений, 20 grep, 0 правок)
так и не дошёл до `edit_file`. `file-exists` доказывает наличие, а не правку.

## Решение

Новый тип контракта `file-modified:<path>` (единственный источник — `plan-checks.ts`):

- На `create`/`re-plan` для шагов с этим check снимается снапшот: sha256 контента
  файла (тот же резолв пути, что у `checkFileExists`: `resolveCheckPath` +
  `findExistingFile`). Снапшот хранится в `PlanStep.checkBaseline`
  (`string` — хеш, `null` — файла не было, `undefined` — легаси-план без снапшота).
- На `done` (`verifyCheckContract` в `step-guards.ts`, рядом с `file-exists:`)
  текущий хеш сравнивается со снапшотом. Не совпал → шаг не `done`, ответ —
  `plan.check_failed` с причиной `verify.file_not_modified`. Файл создан с нуля
  (`null` → хеш) считается изменённым; файл так и не создан — не изменён.
- Легаси (`checkBaseline === undefined`, план создан до фичи): `done` блокируется
  с требованием `re-plan` — доказать правку нечем, молчаливое пропускание вернуло
  бы дырку из мотивации.
- `kind` шага (`create`/`delete`) на `file-modified` не влияет: проверяется только
  факт изменения контента.

## Что НЕ делаем

- Не запрещаем `file-exists` для шагов-правок regex'ом по описанию: хрупко,
  ложные блокировки легитимных шагов. Вместо этого — новый точный инструмент;
  промпт тула `plan` описывает, когда его брать (правка существующего файла).
- Не добавляем read-only стрик-гард в петлю — это отдельная задача/ветка
  (страховка для планов без checks), не часть этого контракта.
