# Эксперты: наследование модели и выбор «провайдер → модель» в настройках

**Дата:** 2026-11-01 · **Ветка:** `feat/experts-model-select` · **Статус:** принято

## 1. Проблема

`experts[tag].model` был **обязательным** и все четыре дефолтных эксперта
(`src/config/defaults.ts`) писали в персист `DEFAULT_MODEL = "qwen/qwen3.5-9b"`.
Смена активной модели в вебе (`/api/config` → ключ `model`) меняла только
`config.model`, а пин экспертов оставался прежним. Следствия:

- `subagent { expert_tag: "code" }` исполнялся на `qwen/qwen3.5-9b`, хотя
  пользователь выбрал другую модель. `resolveExpertProvider`
  (`src/modules/execution/expert-provider.ts`) не переиспользует провайдера
  родителя, когда модель эксперта отличается от `config.model`.
- Падение/мусор на стороне бэкенда выглядели как «агент тупит», а не как
  «эксперт пинуется на модель, которой у провайдера может не быть».
- Второй источник правды: `subagent-run.ts` копировал конфиг родителя в
  `subConfig`, оставляя там **активную** модель, поэтому токен-каунтер,
  cost-tracker и `logger.logLLMRequest` маркировали вызовы не той моделью.
- В настройках экспертов колонка `model` предлагала список моделей **только
  активного** провайдера и не давала выбрать другого провайдера, а «пустая»
  модель была невалидна (`extraValidate` требовал `typeof e.model === "string"`).

## 2. Решение

**Модель эксперта — опция, а не обязанность. По умолчанию эксперт идёт на
активной модели родителя; отдельный провайдер/модель — осознанный пин.**

### 2.1 Контракт конфига (INV-E1)

```ts
interface ExpertConfig {
  model?: string;    // пусто/нет → активная модель; строка → пин модели
  provider?: string; // имя записи provider.entries[]; пусто → активный провайдер
  tool_tags: string[];
  max_attempts?: number;
  description?: string;
}
```

- `provider` без `model` — **немая настройка**: провайдер игнорируется, идём на
  активной модели, в лог пишется `warn`. Это тот же контракт, что у
  `critic.provider` без `critic.model` (`src/modules/critic/provider.ts:43-49`).
- `model` без `provider` — модель на **активном** провайдере (поведение v1).
- `provider` + `model` — выделенный управляемый провайдер на записи
  `provider.entries[]` (резолв через `resolveProviderRef`, как у критика).

### 2.2 Резолв (INV-E2)

`resolveExpertProvider(config, expertModel, expertProvider, activeProvider, …)`:

1. `model` пуст → `activeProvider` (+ warn, если задан `provider`).
2. `model` совпадает с `config.model` **и** `provider` пуст или равен имени
   активной записи → `activeProvider` (переиспользование, без лишнего билда).
3. иначе → управляемый провайдер на `resolveProviderRef(config, provider) ??
   config.provider` с `manager.setModel(model)`. Ошибка сборки → warn +
   `activeProvider` (fail-open, INV-E5).

### 2.3 Согласованность наблюдения (INV-E3)

`subagent-run.ts` строит `subConfig` с `model: expertModel ?? ctx.config.model`:
токен-каунтер, цена и запись `logLLMRequest` относятся к модели, на которой
реально исполняется дочерний агент, а не к активной модели родителя.

### 2.4 Миграция персиста (INV-E4)

Персист хранит `experts` целиком, поэтому смена дефолта сама до пользователя
не доедет. При загрузке (`loadConfig`, до слияния с `DEFAULTS`) миграция
удаляет `experts[*].model`, **если** значение равно прежнему дефолту
`qwen/qwen3.5-9b` **и** у эксперта нет `provider`. Любое другое значение —
ручная настройка пользователя, миграция её не трогает. Факт миграции пишется
в лог один раз за процесс (`config.experts_model_migrated`).

### 2.5 Настройки в вебе

**API.** `GET /api/models?provider=<name>` возвращает `{ models: string[],
loading: boolean }` для записи провайдера (аддитивно к существующему
`/api/models` без параметра = модели активного провайдера). Список живёт в
per-provider кеше `makeModelCache`; первый запрос к незакешированному
провайдеру запускает фоновый `listModels()` и отвечает `{ models: [], loading:
true }`, клиент перезапрашивает. Кеш активного провайдера обновляется на
`reconfigure` (как раньше). Fail-open: офлайн-провайдер оставляет прежний
список и не роняет хендлер.

**UI.** Таблица `experts` (Настройки → Агент → Эксперты) получает колонки:

| колонка | контрол |
|---|---|
| `name` | текст (ключ эксперта) |
| `provider` | `<select>` из `providerOptions` (`/api/providers`), пусто = активный |
| `model` | `<select>` из моделей **выбранного** провайдера, пусто = «как у агента» |
| `tool_tags` | список тегов |
| `max_attempts` | число, опционально |
| `description` | текст, опционально |

- Пустой пункт в `provider`/`model` подписан «inherit / как у агента».
- Список моделей активного провайдера догружается, если панель отрисована
  раньше ответа `/api/models` (`settings.modelsReady`); иначе селект inherit
  оставался пустым до переоткрытия настроек.
- Смена `provider` перерисовывает `model`-селект; значение, которого нет в
  новом списке, сбрасывается (пользователь видит актуальные варианты, а не
  висящий «битый» id).
- Догрузка моделей записи — не более одной автоматической попытки на провайдера
  за жизнь редактора (до ~6 с опроса `loading`). Без этого `draw()` и
  `loadModelsFor()` зацикливали перерисовку и вешали рендерер.
- Валидация на клиенте: неполная строка не постится (как сейчас);
  `provider`/`model` опциональны на сервере и на клиенте.

## 3. Не-цели

- Автоматический подбор модели «под задачу» по способностям/цене — сигнала для
  него нет; остаётся детерминированное наследование.
- `critic`/`orchestrator` в этой задаче не меняются (следующая волна, если
  понадобится: у них тот же дефект «модели только активного провайдера»).
- Рантайм-вопрос пользователю при спавне субагента — отвергнут: модель спавнит
  параллельно, у `serve`/one-shot нет пользователя, это второй путь исполнения.
