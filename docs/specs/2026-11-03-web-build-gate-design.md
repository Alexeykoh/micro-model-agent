# Post-build гейт для веб-задач (`web-build:<dir>`)

> **Дата:** 2026-11-03. Закрывает TODO §1.12 «Post-build гейт для веб-задач».
> **Долг:** F-30/F-34. **Статус:** реализовано. **Решение:** явный check-контракт,
> а не автоматический перехват любого `build`.

## Проблема

`command: npm run build` — статическое доказательство: exit code 0 означает, что
сборщик не упал, но не означает, что артефакт пригоден. В живых прогонах
([web-agent-test-report-2026-11-02](../../agents/web-agent-test-report-2026-11-02.md))
встречались оба класса:

- CSS собран, но Tailwind-утилиты не сгенерированы (неверный `content`/`@source`) —
  страница открывается без стилей;
- `index.html` есть, но пуст (сломанный entry/шаблон) — «200, но пусто».

Гейт проверяет **содержимое артефакта**, а не только факт запуска сборки.

## Контракт

Новый вид check-контракта: `web-build:<dir>`, где `<dir>` — каталог сборки
относительно `baseDir` (абсолютный путь внутри `baseDir` тоже допустим).

`checkDoneEvidence` на `done` вызывает `checkWebBuild(baseDir, dir)`
(`src/modules/execution/web-build-check.ts`) и:

- при успехе добавляет заметку `plan.web_build_ok` (`{dir}`);
- при отказе возвращает `blocked` с `plan.web_build_failed`
  (`{step}`, `{dir}`, `{reason}`).

`classifyCheck` относит `web-build:` к поведенческим: это не рантайм, но и не
«скомпилировалось» — проверяется собранный UI-артефакт. Поэтому шаг, меняющий
UI, не отсекается гейтом «нужно поведенческое доказательство».

### Что именно проверяется

1. **CSS.** Ищутся `*.css` под `<dir>` (глубина ≤ 4, `node_modules`/`.git`
   пропускаются) и в типовых подкаталогах `dist`, `build`, `out`,
   `.next/static/css` — `<dir>` может быть корнем проекта или уже каталогом
   сборки. Нет ни одного файла → `no built CSS found`.
2. **Tailwind.** Содержимое CSS (не более 2 МБ на файл) обязано содержать
   `--tw-` **или** хотя бы два из `.grid{`, `.flex{`, `.hidden{`, `.block{`
   (пробелы перед `{` допускаются). Иначе →
   `CSS has no utility classes (Tailwind not generated?)`.
3. **HTML.** Ищется `index.html` в тех же корнях (глубина ≤ 4). Нет →
   `no index.html in build output`.
4. **Непустая страница.** Из HTML вырезаются `<script>…</script>`,
   `<style>…</style>`, комментарии, теги и HTML-сущности. Если видимого текста
   меньше 20 символов **и** нет `id="root"`/`id="app"`/`id="__next"`/`<canvas>`
   → `page is empty`.

Порядок проверок фиксирован: CSS → Tailwind → HTML → пустота. Первый отказ
возвращается один — модель получает одну конкретную причину, а не список.

### Безопасность

`dir` резолвится через `resolveCheckPath` с включённым jail: выход за `baseDir`
(включая `..` и symlink-побег) блокируется до чтения файлов. Проверка всегда
жёсткая, независимо от `security.paths.enabled`: это новый код, а не легаси.

## Почему явный check, а не автоперехват `build`

- Автоперехват требовал бы эвристики «это веб-проект» и угадывания output-dir;
  ложные срабатывания на не-веб сборках дороже пропуска.
- Check объявляется моделью при создании плана и виден в промпте — она сама
  называет каталог, который собрала.
- Гейт остаётся в единственной точке исполнения контрактов
  (`checkDoneEvidence`), без второго пути проверки.

## Тесты

`tests/modules/execution/web-build-check.test.ts`:

- Tailwind CSS + `index.html` с `id="root"` → `ok`;
- текст вместо root-маркера → `ok`;
- `--tw-`, пробелы перед `{`, `dist` под корнем проекта → `ok`;
- CSS без утилит / нет CSS / нет `index.html` / пустой body без root → отказ с
  точной причиной;
- cap 2 МБ на файл;
- абсолютный и относительный (`..`) выход за `baseDir` → отказ;
- `parseCheck`/`classifyCheck` для нового вида.

`tests/execution/plan-checks-web-build.test.ts`:

- `checkDoneEvidence` проходит и блокирует с причиной;
- без `baseDir` — отказ, а не «молча ок»;
- полный путь `plan_step done` до и после появления артефакта.

## Остаточные ограничения

1. **Эвристика Tailwind.** Проект без Tailwind (чистый CSS, CSS-in-JS,
   styled-components) не пройдёт `web-build:` — контракт и не предлагается для
   таких шагов. Это осознанно: «утилиты» — признак именно Tailwind-пайплайна.
2. **Глубина 4 и типовые каталоги.** Нестандартный output-dir глубже или с
   другим именем нужно указать в самом check (`web-build:<dir>`), иначе CSS/HTML
   не найдутся.
3. **Симлинки внутри сборки.** Обход не следует по symlink-файлам/каталогам
   (используется `Dirent.isFile()/isDirectory()`); артефакты, целиком
   собранные из симлинков, могут не найтись. Выход за `baseDir` при этом
   блокируется отдельно.
4. **Чтение CSS целиком.** Cap применяется после `readFileSync` — для файлов
   больше 2 МБ память тратится на полный файл; на практике CSS-бандлы такого
   размера редки. Если понадобится, чтение будет переведено на потоковое.
5. **`<canvas>` без текста** считается непустой страницей (графика рисуется
   рантаймом); визуальная корректность остаётся за `browser:`/`manual:`.
6. **Рантайм не проверяется.** Ошибка JS после загрузки страницы этим гейтом не
   ловится — для этого по-прежнему `browser:`.
