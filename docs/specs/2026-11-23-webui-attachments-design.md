# Web UI: единая скрепка вложений и capability-gated загрузки (2026-11-23)

**Дата:** 2026-11-23 · **Статус:** target · **Ветка:** `integration/v0.26.1-live`

## Проблема

В композере `mma web` кнопка «прикрепить изображение» (`#attachBtn`) активна
всегда, хотя модель может не принимать изображения — на скриншоте активная
кнопка при `llama.cpp / inkling-2-mini-q4`. Возможности модели уже приходят в
фронтенд (`session.capabilities.vision/pdf` из `GET /api/models`, ответа на
`POST /api/config` и SSE `models`), но ни один контрол их не использует.

PDF как вложение отсутствует полностью: флаг `capabilities.pdf` детектится и
показывается в чипе, но кода, который кладёт PDF в сообщение, нет.

## Решения (утверждены пользователем)

1. Изображения при `vision === false` или `capabilities === null` — скрыть /
   disabled с причиной **и запретить на сервере**.
2. Все вложения композера — под одной иконкой-скрепкой с меню; скрепки в
   вкладке Files остаются, но получают уточнённую подсказку «вставить путь».
3. PDF → текст через существующий `pdfHandler`. Родной PDF-парт и растеризация
   сканов в этой итерации не делаются.

## Не-цели

- Не тащить `pdfjs-dist` в браузерный бандл.
- Не менять механизм picture data URL и не рефакторить лимиты изображений
  (существующий разрыв 50 МиБ на клиенте / 70 МиБ на сервере / 768 МиБ тело
  остаётся как есть; отдельная правка).
- Не добавлять конфигурационные ключи: лимиты — константы модуля вложений.

## Архитектура

```
скрепка (attachments-menu.ts)
  ├─ Изображения  → file input accept=image/* → dataURL (как сейчас)
  ├─ PDF → текст  → POST /api/attachments (binary) → { id }
  └─ Путь проекта → вставка "@" в черновик
        ↓ отправить
POST /api/message { text, images?, documents?: [{id}], sessionId, clientTz }
        ↓ capability gate (vision) → загрузка PDF → pdfHandler
        ↓ bounded-блок <untrusted-document> в ходе
        ↓ SSE models → перерисовка меню
```

### Фронтенд

- `src/modules/webui/assets/js/session/attachments-menu.ts` (новый): единая
  точка вложений. держит меню, один скрытый `<input type=file>` с динамическим
  `accept`, обработчики выбора.
- Пункт «Изображения»: `enabled` только при `session.capabilities.vision === true`.
  При `false` — подсказка «модель не принимает изображения»; при `null` —
  «определяем возможности модели…». `null` означает *неизвестно*, а не
  *не поддерживается* (см. `js/core/store/session.ts`).
- Перерисовка меню вместе с чипом возможностей (`js/settings/selectors-write.ts`)
  и по SSE `models` (`js/sse.ts`). При переключении модели capabilities
  обнуляются (`js/settings/write.ts`) — меню должно сразу уйти в «неизвестно».
- Paste (`#inp`) и drop (`.input-area`) картинок при `vision !== true` не добавляют
  превью, а показывают честную ошибку через `setAttachError()`.
- Скрепки в `js/sidebar/files/tree.ts` и `filesAttach` меняют только aria/title
  на «вставить путь» — семантика `@path` не меняется.

### Бэкенд

- `POST /api/attachments`: бинарное тело PDF, имя файла — заголовок
  `X-File-Name` (обязательный, санитизируется), сессия — `sessionId` в query.
  Сохранение в каталог сессии в поддиректорию `attachments/`, ответ
  `{ id, name, bytes }`. Идентификатор генерируется сервером, файлы живут до
  удаления сессии.
  Лимиты модуля: `MAX_PDF_BYTES = 20 MiB`, `MAX_PDFS_PER_MESSAGE = 5`.
- `parseMessageBody()` (`src/modules/webui/util.ts`) расширяется полем
  `documents?: Array<{id: string}>`; id проверяется как безопасный идентификатор
  и должен существовать в хранилище вложений этой сессии.
- `handleMessagePost` / `turns.ts`: для каждого документа вызывается
  `pdfHandler` (`src/modules/documents/handlers/pdf.ts`), результат добавляется
  в ход как текстовый блок:
  `<untrusted-document name="…" pages="…">…текст…</untrusted-document>`.
  Действуют существующие лимиты `MAX_PAGES = 200` и
  `DEFAULT_DOC_LIMITS` (400 строк / 24 000 символов). При `meta.degraded`
  (сканированный PDF / обрезанный документ) добавляется явная пометка.
- Capability gate в точке приёма сообщения: если `images.length > 0` и
  `capabilities.vision !== true` — 400 с причиной; при `capabilities === null` —
  400 «возможности модели ещё определяются». Источник — тот же снимок
  `providerReasoningSnapshot()`, что используется `/api/models`.
- PDF-текст не gate-ится по `capabilities.pdf`: извлечение работает с любой
  моделью. Флаг `pdf` остаётся только информационным.

## Контракт (публичный)

- Новый REST: `POST /api/attachments`.
- Расширение тела `POST /api/message`: поле `documents`.
- Поэтому до кода — эта спека, затем детальный план.

## Ошибки

| Случай | Поведение |
|---|---|
| `vision=false`, выбор картинки | пункт disabled + причина; обход через API → 400 |
| `capabilities=null` | «определяем возможности…»; загрузка невозможна до ответа пробы |
| битый PDF | ошибка загрузки с причиной, черновик и вложения сохраняются |
| >20 МиБ / >5 PDF / >200 страниц | отказ с конкретным лимитом |
| PDF без текстового слоя | блок с пометкой «текст не извлечён», не пустота |
| capabilities обновились по SSE | меню перерисовано без перезагрузки страницы |

## Тестирование

- Фронтенд: gating для `true/false/null`, динамический `accept`, запрет
  paste/drop, перерисовка по SSE.
- Бэкенд: 400 без vision, загрузка/парсинг PDF, лимиты, вставка
  `<untrusted-document>`, `meta.degraded`, изоляция вложений по сессии.
- i18n: новые ключи симметрично в `src/i18n/en.json` / `ru.json`.
- `bun test` и `bun run quality` зелёные; живой прогон в `mma web` с моделью без
  vision и с vision-моделью.

## Риски

- Снимок capability глобален для активной модели; если сессия привязана к другой
  модели, нужен per-session снимок — в этой итерации предполагаем одну активную
  модель на web-сессию (как сейчас в UI).
- Текст PDF считается недоверенными данными; не должен влиять на инструкции
  системы.
