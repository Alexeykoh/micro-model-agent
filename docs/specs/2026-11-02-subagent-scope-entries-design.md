# Скоуп субагента: glob-записи и честный пустой `glob` (design)

**Дата:** 2026-11-02 · **Ветка:** `fix/subagent-scope-entries` · **Статус:** принято

**Источник:** `TODO.md` §1.8, пункты **A1** и **A2**; разбор живой сессии

Два дефекта одного контракта — «что такое запись скоупа субагента»:

- **A1** — `allowed_files: ["src/**/*"]` не сопоставляется ни с одним путём, поэтому
  субагент не читает вообще ничего (в сессии 4 ребёнка прочитали 0 файлов).
- **A2** — `glob` внутри субагента при пустой выдаче отвечает «нет совпадений» и
  **скрывает**, что совпадения были отфильтрованы скоупом/политикой (14/14 вызовов
  детей — ложное «нет совпадений» при 780+ файлах у родителя).

Одна ветка, два коммита (правило 3): каждый откатывается отдельно, пересекаются они
только в тестах и i18n.

# A. Запись скоупа: путь, glob или «весь workspace»

## Проблема

`matchesScopeEntry` (`src/tools/path-utils.ts:36`) — это сравнение префиксов:
`resolve(baseDir, entry)` даёт для `src/**/*` буквальный путь
`<baseDir>/src/**/*`, которого на диске нет. Любой реальный путь оказывается «не
внутри» этой строки → отказ с причиной «Path is not within the allowed scope for this
sub-agent». Модель видит, что файлы существуют (родитель их читал), получает
необъяснимый отказ и либо повторяет вызов, либо галлюцинирует «файла нет».

Причина не в авторе — в **недоопределённом контракте**: параметр назывался
«files/directories», но модель естественно пишет glob (как в `security.paths.allowed`,
где glob поддерживается), а скоуп проверялся другим матчером с другой семантикой.

## Решение

Запись скоупа — три формы, различаемые по нормализованной строке:

| Форма                      | Пример                             | Семантика                                                                                                                                         |
| -------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Каталог/файл (без `*`/`?`) | `src`, `src/App.tsx`, `tests/`     | цель равна записи **или внутри неё** (как сейчас)                                                                                                 |
| Glob (`*`, `?`, `**`)      | `src/**/*.ts`, `**/*.md`, `*.json` | `matchesGlobPattern` (`src/modules/security/path-glob.ts`): `**` — любая глубина, `*` — в пределах сегмента, паттерн без `/` — шаблон имени файла |
| Весь workspace             | `**`                               | любая цель внутри `baseDir` (эквивалент отсутствия ограничения чтения/записи), джейл `baseDir` сохраняется                                        |

Почему переиспользуется `matchesGlobPattern`, а не пишется второй матчер: это уже
проверенная семантика `security.paths.allowed/denied` (регистр, basename-паттерны,
`**`), её понимает и модель, и конфиг. Второй матчер с другим поведением — ровно та
ошибка, которая породила A1.

### Нормализация — одна точка

`normalizeScopeEntry` (`src/modules/security/scope.ts`):

- trim, `\` → `/` (UNC-префикс `\\server\share` не схлопывается), снять
  ведущий `./`, схлопнуть `//`, снять хвостовой `/`;
- пустая строка, `.` и любой `..`-сегмент → **невалидная** запись
  (`normalizeScopeEntries` возвращает `{ entries, invalid }`);
- абсолютная запись (`/opt/data`, `C:/data`, UNC) **легальна** — это
  явное намерение (A10: при `enabled:false` скоуп может указывать вне
  `baseDir`); цель сверяется как абсолютный путь, glob — по абсолютному пути.

Невалидные записи **не отбрасываются молча**: `subagent` возвращает `success:false`
с перечислением отвергнутых записей и причиной. Тихий дроп даёт пустой скоуп и
«нет доступа ко всему» — тот же класс непонятного отказа, что и A1.

Отсечение `..` не ослабляет ничего: относительная запись с `..` неоднозначна
(«от корня или от cwd?»), а выразить доступ вне проекта всё равно можно
абсолютной записью — явно.

### Причина отказа — с составом скоупа

Все три отказа «не в скоупе» (`isPathInScope` ×2, `isPathWritable`) получают причину
вида:

```
Path is not within the allowed scope for this sub-agent (scope: src/**/*, docs)
```

(не больше 5 записей, остальное — `… +N more`). Модель, читающая tool-output, должна
иметь возможность исправить аргументы, а не угадывать.

### Где применяется

- `src/modules/security/scope.ts` — новый шов: `normalizeScopeEntry`,
  `normalizeScopeEntries`, `matchesScopeEntry`, `formatScopeEntries`,
  `isAbsoluteScopeEntry`.
- `src/modules/security/path-glob.ts` — `globToRegExp` переписан на честную
  грамматику: прежний разбор `**` как «префикс + суффикс» не понимал шаблоны
  вида `src` + `/` + `**` + `/` + `*.ts` (суффикс сравнивался буквально) —
  такие паттерны молча не совпадали **и в конфиге** `security.paths`, где
  `**/secrets/**` работал только по совпадению имени сегмента.
- `src/modules/security/path-validator.ts` — `isPathInScope`/`isPathWritable`
  используют новый матчер; причина отказа называет состав скоупа.
- `src/tools/path-utils.ts` — старый `matchesScopeEntry` удалён (единственный
  потребитель — `path-validator`; две реализации одного контракта — источник A1).
- `src/tools/subagent-run.ts` — нормализация скоупа при спавне, отказ на
  невалидных.
- `src/tools/subagent.ts` — описание `allowed_files`/`read_only_files`: формы
  записи, `**` = весь workspace. Контракт аргументов не меняется, только текст.

## Инварианты

- **INV-S1** Запись скоупа никогда не расширяет джейл `baseDir`: `enabled:false`
  снимает jail только явным конфигом, не скоупом.
- **INV-S2** Нормализация — только в `scope.ts`; `path-validator` не парсит записи.
- **INV-S3** Запись даёт право записи, только если она в `allowed_files`; glob
  `**` в `read_only_files` остаётся только чтением.
- **INV-S4** Отказ по скоупу всегда называет состав скоупа.

## Тесты

- `tests/security/scope-entries.test.ts` — нормализация (`./`, `\`, `//`,
  UNC, хвостовой `/`), невалидные (`""`, `.`, `..`) ловятся, абсолютная запись
  легальна, матчинг всех форм, кап `formatScopeEntries`, грамматика
  `globToRegExp` (`**` + суффиксный шаблон, `**/` в середине, `src/**`).
- `tests/security/scope-glob-entries.test.ts` — `src` + `/` + `**` + `/` + `*.ts`
  разрешает `.ts` внутри `src` и отказывает вне; `read_only_files` не даёт
  записи; `**` не расширяет джейл `baseDir`; glob-скоуп действует при
  `enabled:false`; причина содержит запись скоупа.
- `tests/tools/subagent-scope.test.ts` — `..` и пустая запись отвергаются с
  причиной; glob-форма проходит валидацию спавна.

# B. `glob`: «скрыто скоупом» ≠ «нет совпадений»

## Проблема

`src/tools/glob-tool.ts:60-62` при `visible.length === 0` возвращает
`file.no_matches` **до** формирования строки `file.glob_hidden` (`:67`). Счётчик
`hidden` уже есть, но в ветке пустой выдачи теряется. Итог: ребёнок с любым
(в т.ч. сломанным, A1) скоупом получает «No matches» и делает вывод «файлов нет».

## Решение

- Считать `hidden` всегда; при `visible.length === 0 && hidden > 0` ответ:
  `file.no_matches` + перевод строки + `file.glob_hidden`.
- При `visible.length === 0 && hidden === 0` — прежнее `file.no_matches`.
- Новых i18n-ключей не нужно: `file.glob_hidden` уже говорит
  «({count} paths hidden by scope/security)».

## Тесты

- `tests/tools/glob-scope.test.ts` — скоуп, не покрывающий ни одного совпадения,
  даёт в выводе и «No matches», и `glob_hidden` с числом; без скоупа — только
  «No matches».
