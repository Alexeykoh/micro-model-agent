# Отказ критика должен быть виден в ленте

_Дата: 2026-10-24. Ветка: `fix/critic-degrade-feed`. Долг: `critic-degrade-not-in-feed`._

## Что случилось (наблюдение)

Ход в `mma web` выглядит завершённым, даже когда верификация **не состоялась**:
критик не ответил (`call_timeout`), его ответ не разобрался
(`unparseable_verdict`), цикл проверок упал (`checks_loop_failed`) или провайдер
вернул ошибку (`llm_error`). Гейт fail-open пропускает ответ — это правильно —
но единственный след отказа остаётся в `session.jsonl` (`critic_verdict` с
`degraded: true` + `critic_error` с причиной) и в app-логе. В ленте
пользователь видит обычное завершение хода.

Молчаливый pass неотличим от «проверил и сказал ок». Это ровно тот дефект,
который INV-15 запрещает для наблюдаемости: поломка обязана оставить сигнал,
видимый потребителю, а не только строку в файле.

## Решение

1. **Статус-строка в существующем meta-канале.** `CriticGate` уже получает
   `deps.onMeta` (тем же путём идут `ui.draft_retracted` и `retract`). При
   деградации гейт эмитит одну строку статуса:

   ```
   ↳ проверка не состоялась · <класс причины>
   ```

   Нового SSE-события и правок фронтенда не требуется: SSE `meta` без
   `kind: "tool"` рендерится всегда (`feed/stream.ts::onMeta`), а в REPL это
   та же статусная мета, что и строка ретракта черновика.

2. **Класс причины вместо технической строки.** Техническая причина
   (`call_timeout (125000ms)`, `unparseable_verdict (pass-1): …`) остаётся в
   `session.jsonl` и app-логе — в чат она не идёт (STYLE: внутренняя диагностика
   петель в чат не рендерится). В ленту попадает класс:

   | префикс причины | ключ | ru |
   |---|---|---|
   | `call_timeout` | `ui.critic_reason.timeout` | таймаут проверки |
   | `unparseable_verdict` | `ui.critic_reason.unparseable` | вердикт не распознан |
   | `checks_loop_failed` | `ui.critic_reason.checks` | сбой проверок |
   | `llm_error` | `ui.critic_reason.llm` | ошибка проверяющей модели |
   | иначе / `no verdict returned` | `ui.critic_reason.none` | вердикта нет |

   Классификация — чистая функция `criticDegradeClass(reason)` в
   `src/core/agent/critic-degrade-line.ts` (файл `critic-gate.ts` уже 294 строки,
   правило 6). Строка собирается там же: `t("ui.critic_skipped", { reason })`.

3. **Одна строка на деградацию, не на ход.** Эмит в `logDegraded` — единственной
   точке, где гейт уже знает причину и пишет `critic_error`. Успешная проверка,
   `ok`-вердикт и выключенный критик строку не дают: сигнал значит «проверки не
   было», а не «проверка была».

## Что сознательно НЕ делаем

- **Новое SSE-событие (`verify_skipped`) и карточка в ленте.** Контракт
  «статус хода» уже есть (`OnMeta` с `kind: "status"` → SSE `meta`), дублировать его вторым
  каналом — второй путь исполнения для одного сигнала. Выделенное событие
  понадобится только если у строки появится интерактив (например, «повторить
  проверку»).
- **Вывод технической причины в чат.** `call_timeout (125000ms)` — диагностика
  для разбора сессии, не текст для пользователя; STYLE требует человеческих
  слов и короткой строки.
- **Смена поведения гейта.** Fail-open остаётся: критик по-прежнему не
  блокирует ответ. Меняется только видимость факта отказа.
- **Строка в чате при каждом ходе с выключенным критиком.** «Критик выключен» —
  настройка, а не деградация; шуметь о ней в каждом ходе нельзя.

## Проверка

- `tests/critic-degrade-feed.test.ts`: гейт с деградацией эмитит ровно одну
  status-мету с `ui.critic_skipped` и классом из причины; успешный вердикт и
  выключенный критик — ни одной. Тест падает без эмита (правило 7).
- `tests/critic-degrade-feed.test.ts`: классификация всех четырёх префиксов +
  фолбэк.
- `tests/critic-degrade-feed.test.ts`: форвардер превращает эту мету в
  `meta`-событие **без** `kind: "tool"`, то есть клиент её не quiet-гейтит.
- Живой прогон `mma web` (2026-10-24, изолированный `MMA_CONFIG_DIR` + mock
  openai-compat провайдер: за агента отвечает, за критика отдаёт 500). Результат:
  SSE `meta` с `kind: "status"` и текстом `↳ verification did not run · verifier
  model error` перед финалом хода, `turn_end.success: true`, а в `session.jsonl` —
  `critic_verdict {status:"none", degraded:true}` и `critic_error` с полной
  причиной `llm_error: LLM request failed after retries`.

## Риски

- **Шум.** Одна строка на деградировавшую проверку; при повторных ходах подряд
  строк будет столько же, сколько отказов. Это честно: несколько несверенных
  ответов подряд — сигнал, который пользователь должен увидеть.
- **Ложное впечатление «проверка всегда есть».** Строка не появляется, когда
  критик выключен, — но об этом пользователь знает из настроек, а деградация
  молчать не должна.
