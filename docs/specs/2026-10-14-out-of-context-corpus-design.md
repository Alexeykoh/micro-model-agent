# Корпус вне контекста: агент поверх информации, многократно превышающей окно

**Дата:** 2026-10-14 · **Статус:** проект (к ревью) · **Ветка:** `docs/architecture-v2`
**Модель-ограничение:** малая модель, окно 32K (`qwen/qwen3.5-9b`)
**Дополняет:** [`2026-10-13-context-preservation-design.md`](./2026-10-13-context-preservation-design.md)
**Основание:** [`2026-10-13-context-loss-live-probe.md`](../analysis/2026-10-13-context-loss-live-probe.md),

**Внешние опоры:** RLM (arXiv:2512.24601), RAPTOR (ICLR 2024), ToM (arXiv:2511.00489)

Спека отвечает на вопрос «что правильно». Порядок работ — отдельный документ.

> **Зона.** Спека меняет **контракт** (путь данных через `ToolExecutor`, контракт результата
> тула, содержимое блока компакции, схему бюджета). По правилу 2 (AGENTS.md) это требует
> спеки — она здесь. По правилу 3 работа дробится на волны (§10).

---

## 1. Проблема

Агент на окне 32K входит в петлю: широкое чтение → переполнение → компакция → потеря
**содержимого и его адреса** → снова широкое чтение. Завершается смертью сессии, а не
бесконечностью (см. `context-loss-live-probe`, §2.1 D1–D6 там).

**Ложная цель — «лучше сжимать».** Компакция по построению не разрывает петлю, если рабочий
набор для вопроса больше окна: после сжатия агент снова не знает, где нужное, и читает
широко (это зафиксировано в спеке-предшественнике, §2.2). Улучшение саммари меняет качество
ответа, но не устраняет петлю.

**Настоящая цель.** Смысл не должен храниться в контексте. Контекст — оперативная память;
смысл живёт в трёх неразрушаемых местах: **исходник** (на диске), **леджер адресов**,
**артефакты** (материализованные сводки/выводы). Утеря содержимого из окна безопасна, если
адрес сохранён, а узкое повторное чтение влезает по построению.

**Сценарии-цели (все):** ответ на вопрос по корпусу; сводка/суть всего корпуса; новый
артефакт-вывод длиннее окна; сквозной поиск причины бага в модульной архитектуре по многим
файлам.

## 2. Принцип и инварианты

**Принцип.** Масштаб берётся из двух источников: **делегирование** (дерево окон — субагент
на каждый кусок корпуса, в корень только evidence) и **программное сужение** (`search`,
узкий slice, map-reduce-вопрос). Сырьё в корневой контекст не входит.

Инварианты помечены `OO-N` (Out-Of-context). Они нормативны для нового кода и получают
проверку (правило 5).

- **OO-1 (недопуск).** Результат тула объёмом больше `context.admitMaxTokens` **не входит**
  в корневой контекст дословно. Он заменяется **дескриптором**: ссылка на сырьё + размер +
  дайджест + превью. Сырьё, если его нет на диске, сохраняется в артефакт.
- **OO-2 (пере-подъём).** Дескриптор всегда содержит всё для узкого re-read: путь (или путь
  артефакта) и диапазон/совпавшие строки. Узкий re-read по построению помещается в окно.
- **OO-3 (леджер адресов).** Каждое чтение/поиск/находка фиксируется как `path:line — …` в
  **durable-леджере**. Компакция не может удалить леджер; в блоке компакции — только указатель.
- **OO-4 (делегирование вместо свалки).** Если для вопроса нужно просмотреть больше
  `admitMaxTokens`, харнесс ведёт это через оркестрованный скан (§4) с субагентами и
  возвращает в корень только evidence-записи.
- **OO-5 (вывод больше окна).** Длинный вывод собирается **инкрементально в артефакт**
  (append). Корень никогда не держит итог целиком.
- **OO-6 (детерминированный адрес).** Адрес в леджер пишет **харнесс из метаданных тула**
  (путь, диапазон, был ли матч), а не только модель. Гарантию даёт механизм, не дисциплина
  малой модели.
- **OO-7 (один вход сырья).** Сырьё попадает в корневой контекст только через узкий
  re-read по адресу (OO-2) или как evidence-запись (OO-4). Никакой другой путь не вводит
  большой объём.

## 3. Архитектура: где проходит граница

```
Корень (окно ~32K)     держит: задача, план, дескрипторы, evidence-записи, указатель на леджер
   │  tools (single enforcement: ToolExecutor)
   ├─ search / grep ───────────► path:line (только совпадения, не содержимое)
   ├─ read_file(slice) ────────► узкий диапазон; большой запрос → дескриптор (OO-1)
   ├─ scan_corpus(question) ───► locate → cluster → MAP(субагенты) → REDUCE (OO-4)
   ├─ chunk_query(path, q) ────► map-reduce-вопрос по большому тексту (уже существует)
   └─ subagent(result_mode:file)► своё окно; в корень — bounded evidence + артефакт
                                 ▼
Диск: исходники · леджер (NOTES.md) · артефакты (.mma/artifacts, spill)
```

**Почему это не теряет смысл (нормативно).**

1. **Недопуск** (OO-1/OO-7): переполнения не возникает, потому что большое не входит; значит
   нет вынужденной потери.
2. **Адрес переживает компакцию** (OO-3): после сжатия агент знает, где искать, и делает
   узкий re-read вместо широкого. Именно адрес, а не саммари, разрывает петлю.
3. **Запись до, а не потом**: находка фиксируется в момент получения. После первой компакции
   записывать уже нечем.
4. **Делегирование** (OO-4): кусок корпуса целиком помещается в окно **субагента**; в корень
   возвращается дистиллят + адрес. Нет куска, который надо было бы держать целиком в корне.
5. **Дерево сводок** (для «сути всего корпуса»): вход каждого уровня — детские сводки, а не
   исходник; сжатие осмысленное, а не аварийное. Никакой уровень не переполняется.
6. **Инкрементальный вывод** (OO-5): длина вывода не ограничена окном, потому что он
   строится в файле.

**Честная граница.** Гарантия — не «контекст ничего не теряет» (на 32K это невозможно), а
**«ничего не потеряно навсегда»**: утраченное из окна либо в исходнике, либо в леджере, либо
в артефакте, и восстановимо узким запросом. Контекст становится lossy by design — и это
норма, а не дефект. Успех частично зависит от поведения модели (ведёт ли она аннотации в
леджер), поэтому система гарантирует обнаружимость потери (§6.2, диагностика «прочитано, но
не записано»), а не её отсутствие.

## 4. Контракты

### 4.1 Дескриптор результата (замена сырому output, OO-1)

Когда результат тула превышает `admitMaxTokens`, в историю вместо сырья попадает дескриптор:

```
{ handle, source, bytes, lines, digest, preview }
```

- `handle` — непрозрачный id (для повторных ссылок и кликов в UI);
- `source` — для файлов исходный путь; для прочего — путь артефакта в `.mma/context/<session>/`;
- `digest` — детерминированный дешёвый дайджест, **без вызова модели** (иначе модель
  тратится на каждой тул-итерации). Источник по типу: код → индексатор/символы
  (`src/modules/indexer`); текст → заголовки + первые строки; прочее → превью;
- `preview` — первые N строк/символов.

Дескриптор обязан содержать достаточное для OO-2 (путь + диапазон или путь артефакта).

`boundedOutput` (`executor.ts:489`) остаётся, но перестаёт быть единственной защитой: admission
применяется ко **всем** результатам, а не только к объявившим флаг. `file.read_truncated`
(`read-file.ts`) для больших файлов заменяется на дескриптор + hint (§6.1).

### 4.2 Evidence-запись (единица обмена в скане/делегировании, OO-4)

```
{ claim, quotes: ["path:line", …], confidence }
```

В корень из субагента/скана попадают **только** такие записи (плюс, при необходимости,
путь артефакта с полным отчётом). `claim` — одна фраза; `quotes` — адреса, а не цитаты.

### 4.3 Леджер (`context.notesPath`)

- Конфиг-ключ `context.notesPath`, тип `string`, дефолт `NOTES.md` относительно корня
  проекта (объявляется в `src/config/registry-extra.ts`; согласовано со спекой-предшественником §3.3).
- Формат — append-only строки `path:line — заметка`.
- **Кто пишет:** харнесс — адреса из метаданных тула (OO-6); модель — содержательные аннотации.
- **Дедуп:** адрес (`path:line`) не дублируется; повторная находка обновляет заметку.
- **Кап и свёртка:** при числе записей > `context.ledgerMax` харнесс сворачивает старейшие в
  индекс по файлам (`path — обнаружено: …`), а не удаляет бесследно.
- **Кто чистит:** только харнесс; компакция леджер не трогает.
- **Блок компакции** (`manager.ts:buildCompactionBlock`) вставляет не содержимое, а указатель
  `[Notes: <path>, N]`. Сам файл леджера компакция не трогает.

### 4.4 `scan_corpus` — тул-оркестратор (OO-4)

Для кейса «просканить много файлов» (диагноз бага, сводка корпуса). Планирование — в
харнессе, не в голове 9B.

Параметры: `question` (обяз.), `paths?`, `strategy?`.

Конвейер:
1. **Locate** — `grep`/`rg` по ключам из `question` → список `path:line` (bounded до N).
2. **Cluster** — группировка по файлу/директории.
3. **MAP** — на каждый кластер вызывается **существующий** движок (не новый): `chunk_query`,
   если ребёнку тулы не нужны, или `subagent` с `result_mode:"file"`, если нужны. Полный кусок
   корпуса — в *его* окне; в корень — evidence-записи; полный отчёт — в артефакт.
4. **REDUCE** — корень получает evidence-записи; если их больше K — рекурсивная редукция
   (дерево, §3 п.5), как синтез в `chunk_query`.
5. **Output** — ответ в корне или сборка артефакта (OO-5).

Это «двигатель порядка величины»: N файлов × окно ребёнка переработаны, корень увидел только
findings. Движок не дублируется — границы зафиксированы в §4.6.

### 4.5 Spill результатов `bash`/`web`

Результаты, у которых нет файлового источника и которые превышают лимит, пишутся в
`.mma/context/<session>/` (спил), в контекст — дескриптор с путём. Очистка — по завершении
сессии.

### 4.6 Границы механизмов (правило 4)

Три механизма обслуживают один класс задач (`src/tools/chunk-query.ts`, `src/tools/subagent.ts`
и новый `scan_corpus`). Границы фиксируются, чтобы они не разъехались:

| механизм | вход | движок MAP | когда использовать |
|---|---|---|---|
| `chunk_query` | один текст (файл/inline), расширяется до `paths`/glob | простые LLM-вызовы, без тулов | вопрос по большому тексту, читается линейно |
| `subagent` | одна задача | полный агент со своим окном и тулами | ребёнку нужны тулы / многошаговая работа |
| `scan_corpus` | много источников + вопрос | **переиспользует** первых двух | нужен locate + reduce по многим источникам |

Правило: `scan_corpus` — **оркестратор, не третий движок**. Его MAP вызывает `chunk_query`
(тулы не нужны) или `subagent` (нужны); REDUCE — рекурсивный. Новой логики чанкинга или
субагента не появляется.

Стоимость и остановка: `maxFanout` (число MAP-веток), `maxDepth` (глубина reduce), бюджет —
из `history − toolTokens` (§5). REDUCE прекращается, когда evidence-записей ≤ K.

## 5. Бюджет с учётом зарезервированного

Сейчас `budgetBreakdown` (`src/config/budget.ts`) делит окно на `system` + `reserve` +
`history`, **не выделяя схемы тулов** (~6.3K по замеру спеки-предшественника §2.4). Скрытый
перерасход — источник части переполнений.

Спека вводит:

- `contextBudget.tools` (доля или токены) — явный резерв под описания тулов; дефолт по замеру.
- `context.admitMaxTokens` — порог OO-1 (дефолт ~1500–2000).
- **Реальный рабочий бюджет** = `history − toolTokens`. Именно он — мера admission (OO-1) и
  порог, выше которого скан обязателен (OO-4), а не `contextWindow`.

Сравнение **оценки** с окном как предиктивного правила не вводится (унаследовано из
спеки-предшественника §3.2: при завышенной оценке это давало бы ложные компакции).

## 6. Точки enforcement

### 6.1 Единый вход сырья

- **`ToolExecutor.execute()` — единственное место** применения OO-1/OO-7 (INV-9/10 arch v2,
  W2). После хендлера, до входа результата в историю: применить admission (spill +
  дескриптор). Хендлер политику не реализует и security-примитивы не импортирует.
- **Леджер** пишется там же из метаданных результата (OO-6).
- **Подсказка-роутинг**: если `read_file` запрошен на весь файл/диапазон больше
  `admitMaxTokens`, результат — дескриптор + подсказка `scan_corpus` / `chunk_query` /
  узкий slice. Тул «сам режет» только как fallback; решение принимает enforcement.
- **Компакция** (`manager.ts:buildCompactionBlock`) — замена сырых строк на указатель на
  леджер; леджер как файл не чистится.

### 6.2 Наблюдаемость

- Чтение логирует объём (уже есть) — сигнал утраты: ненулевой объём чтений при отсутствии
  `[Notes]` в блоке.
- Инвариант «прочитано, но не записано»: рост объёма чтений без роста леджера между двумя
  компакциями → диагностика `kind: "degraded"`, `source: "core"` (стоит ноль токенов, ловит
  петлю на ранней стадии).
- Детектор петли «компакция без прогресса» — из спеки-предшественника §3.4 (не дублируется).

## 7. Границы задачи (YAGNI)

**Не входит:**

- поднятие окна;
- автоматическое извлечение знаний без участия агента;
- векторные эмбеддинги / иерархический retrieval-индекс (подход C) — отдельная спека;
- правка `MAX_FACTS` (`fact-extractor.ts`);
- изменение интерфейса пользователя (кроме имён, видимых модели, — через `t()`);
- 「очерк файла как средство навигации」 — отменён замерами спеки-предшественника.

**Входит:** OO-1…OO-7, контракты §4, бюджет §5, enforcement §6, тесты §8 и живая приёмка.

**Отношение к спеке-предшественнику.** `2026-10-13-context-preservation-design.md` закрывает
*механику петли* (D1 фабрика ошибок, D2/D3 аварийное сжатие, D4 канонизация, D5/D6 адреса как
конвенция + детектор петли). Настоящая спека добавляет **структурный слой**: недопуск сырья,
харнесс-владеемый леджер, оркестрованный скан, учёт бюджетных частей. Пересечение — только
`context.notesPath` и диагностика утраты; они формулируются один раз (§4.3, §6.2) и
используются обеими.

## 8. Приёмка

### 8.1 Юнит-тесты, падающие без правки

1. **OO-1**: результат > `admitMaxTokens` → в истории нет сырья; есть дескриптор с `source` и
   `preview`; сырьё читаемо по `source`.
2. **OO-2**: дескриптор разрешается в узкий re-read; диапазон не превышает лимита.
3. **OO-3**: после **двух** компакций леджер на месте, адрес разрешается в узкий re-read;
   леджер не был вычищен.
4. **OO-4**: `scan_corpus` на N файлах → корень получил ≤ K evidence-записей; окно не
   превышено на ни одной итерации.
5. **OO-5**: вывод > окна собирается в артефакт; корень его не держит.
6. **OO-6**: адрес записан в леджер **без участия модели** (из метаданных тула).
7. **OO-6/наблюдаемость**: рост объёма чтений при нулевом росте леджера порождает `degraded`.
8. **Бюджет**: `history − toolTokens` используется как мера admission; `contextBudget.tools`
   учитывается в `budgetBreakdown`.
9. **Границы механизмов (§4.6)**: MAP `scan_corpus` вызывает `chunk_query`/`subagent`, а не
   дублирует чанкинг/субагента (проверка через швы/моки).
10. **Леджер**: дедуп адреса; при > `context.ledgerMax` — свёртка старейших в индекс по файлам,
    а не потеря.
11. **Остановка**: REDUCE прекращается при числе evidence-записей ≤ K; `maxFanout`/`maxDepth`
    соблюдаются.

### 8.2 Живая приёмка (прогоны)

| # | Прогон | Условие приёмки |
|---|---|---|
| 1 | Баг в модульной архитектуре на корпусе из многих файлов | причина найдена; в логе — `scan_corpus` и evidence; вызовов ≤ согласованного лимита; сессия жива |
| 2 | Сводка корпуса, многократно большего окна | сводка получена; корень ни разу не держал весь корпус |
| 3 | Артефакт-вывод длиннее окна | артефакт собран инкрементально; корень жив |
| 4 | Регрессия узкого чтения (B2) | без регрессии: ≤6 вызовов, 0 компакций |

**Гейт:** `bun test` зелёный, `bun run quality` зелёный.

## 9. Риски

| Риск | Основание | Что делаем |
|---|---|---|
| 9B не зовёт `scan_corpus` | слабое планирование малой модели | харнесс роутит сам при превышении `admitMaxTokens` (OO-4/§6.1) |
| Spill копит мусор | `.mma/context/<session>/` | очистка по завершении сессии |
| Двойной источник правды (файл-леджер vs блок компакции) | §4.3/§6.1 | в блоке — указатель, а не копия |
| Леджер растёт неограниченно | §4.3 | дедуп, кап `context.ledgerMax`, свёртка старейших в индекс по файлам |
| `digest` без модели слабоват | §4.1 | при нехватке — `chunk_query` по `source`; отдельный шаг, не в пути каждого чтения |
| Утечка леджера/спила за пределы проекта | security | под `protected-paths`/scope; спил — в конфиг-каталоге |
| Правило 3 (одна задача — один контракт) нарушается | затронуты core/tools/context/config | дробление на волны (§10) |

## 10. Волны (порядок работ — отдельный документ)

Нарезка по правилу 3, у каждой волны проверяемый результат:

- **W-a.** Бюджет: `contextBudget.tools` + `context.admitMaxTokens` (§5) — без admission.
- **W-b.** Admission + дескриптор + spill в `ToolExecutor` (OO-1/2/7) + тесты 1,2.
- **W-c.** Леджер (OO-3/6): запись, дедуп, кап/свёртка + указатель в блоке компакции + тесты 3,6,7,10.
- **W-d.** `scan_corpus` — оркестрация поверх `chunk_query`/`subagent` (§4.6) + тесты 4,5,9,11 + живая приёмка.
- **W-e.** Инкрементальный вывод в артефакт (OO-5).

Спека-предшественник (D1/D2/D4 + адреса) идёт параллельно как отдельная ветка; пересечение —
`context.notesPath`, которые объявляются один раз в W-c.

## 11. Открытые вопросы

Границы механизмов (§4.6) и формат `digest` (§4.1) — решены.

1. **Точный дефолт `admitMaxTokens`** — по замеру, а не на глаз (зависит от окна и числа
   тулов). Гейт: замер до фиксации значения.
2. **`contextBudget.tools`: доля или токены** — токены точнее (схемы тулов почти константны),
   доля переживает смену набора тулов. Решение — в волне W-a.
3. **`context.ledgerMax`** — дефолт капа леджера до свёртки в индекс; уточнить на стенде.
4. **Гейт «ведёт ли 9B аннотации»** — унаследован из спеки-предшественника §6.1. Если
   аннотации не ведутся, леджер всё равно живёт (OO-6: адреса пишет харнесс), но связность
   снижается; проверить живым прогоном.
