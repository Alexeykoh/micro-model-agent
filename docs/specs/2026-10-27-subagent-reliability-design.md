# A. `bash` в субагенте: джейл — `baseDir`, скоуп — файловые тулы

## Проблема

`validateWorkdir` (`src/modules/security/path-validator.ts:174-189`) требует, чтобы cwd
`bash` лежал **внутри одной из записей `scope.allowed_files`**. Скоуп субагента — это
список файлов (`src/App.tsx`, `src/`), поэтому cwd проекта (`baseDir`) в него не попадает
и **любой** `bash` внутри такого субагента блокируется. В сессии `ses_mvoac9q9` это дало
10 из 13 `security_block`; прогон, которому нужно было прочитать 8 файлов и запустить
сборку, вместо работы пошёл искать обход (`find C:\ -maxdepth 2`, `cmd.exe /c dir`) и
сжёг бюджет генерации.

При этом проверка **не защищает от чтения вне скоупа**: команда, запущенная с cwd
`src/`, всё равно может выполнить `cat ../package.json`. То есть это правило фокуса, а не
граница безопасности, и как правило фокуса оно неверно: задача «собери проект» требует
корня.

## Решение

| Что | Было | Стало |
|---|---|---|
| cwd внутри `baseDir` | обязательно | обязательно (без изменений) |
| cwd не уходит наружу через symlink/junction | обязательно | обязательно (без изменений) |
| cwd внутри `allowed_files` | обязательно | **не проверяется** |
| у субагента есть хотя бы одна запись в `allowed_files` (право записи) | обязательно для `bash` | обязательно (без изменений) |
| пути файловых тулов (`read_file`/`write_file`/`grep.path`/…) | скоуп | скоуп (без изменений) |
| список команд, protected-пути, ADS, чёрные списки | политика тула | без изменений |

Почему это не ослабление границы, а её честная формулировка:

1. `bash` — тул с `security.manual` и собственным command-validator; его реальная граница
   всегда была `baseDir` (родитель работает ровно в ней же). Скоуп субагента не ограничивал
   содержимое команд — только cwd.
2. Настоящий ограничитель shell у субагента — **набор тулов**: `bash` имеет тег `shell`;
   родитель, который не хочет давать shell, не передаёт тег в `tool_tags`, и тула у
   ребёнка просто нет.
3. Право записи остаётся: субагент только с `read_only_files` по-прежнему получает
   «no writable scope for bash» (иначе `rm` в read-only прогоне — новая дыра, а не фикс).

## Изменения

- `src/modules/security/path-validator.ts` — `validateWorkdir`: убрать сверку cwd с
  `scope.allowed_files`; оставить `baseDir`-джейл, symlink-контейнмент и проверку
  «скоуп без `allowed_files` → `bash` запрещён». Комментарий функции — переписать под
  новый контракт (иначе следующий читатель вернёт проверку «для порядка»).
- `src/tools/path-guards.ts` — комментарий к `assertWorkdirAllowed`.
- `src/tools/subagent.ts` — описания `allowed_files`/`read_only_files`/`tool_tags`:
  «`allowed_files` ограничивает файловые тулы и является правом записи; shell видит весь
  проект и выдаётся тегом `shell`».
- `tests/tools/bash-scope.test.ts` — тест «blocks a workdir outside the sub-agent scope»
  заменяется на обратный + два новых: cwd вне `baseDir` по-прежнему блокируется;
  `bash` при скоупе только из `read_only_files` по-прежнему блокируется.

## Тесты (падали бы до правки)

1. `subagent`-скоуп `allowed_files: ["src"]` → `bash {command: "echo hello", workdir: baseDir}`
   выполняется (сегодня — `[SECURITY BLOCKED]`).
2. Тот же скоуп → `bash {workdir: dirname(baseDir)}` блокируется.
3. Скоуп `read_only_files: ["src"]` → `bash` блокируется.
4. Скоуп `allowed_files: ["src"]` → `read_file("package.json")` блокируется (скоуп файлов
   жив).

# B. Усечение до первого символа ответа: классификация и восстановление

## Проблема

`finish_reason=length` при `!sawText` и без tool_call означает, что бюджет генерации
съели **рассуждения** — модель не успела начать ответ. Сейчас
(`src/llm/openai-compat.ts:625-638`) это бросается как `llm_truncated` с текстом
«разбейте задачу на меньшие порции вывода». Восстановление в петле
(`src/core/agent/loop-llm.ts:242-266`) повторяет **тот же** запрос, а reasoning-политика
(`src/modules/reasoning/policy.ts:49-52`) на `recoverableLlmError` поднимает уровень до
`high` — то есть делает следующий заход ещё дороже по рассуждениям. Итог: 2 гарантированно
провальных повтора (в сессии — 284 с и 219 с) и пустой `Частичный вывод:`.

Дополнительно: `withTokenCap` (`src/llm/token-cap.ts:30-32`) клампит любой явный
`options.maxTokens` вниз до `cap`, поэтому петля не может поднять бюджет на повтор.

Замер из сессии: задача «прочитай один файл и ответь 8 строками» упала при
`max_tokens: 900`, тот же файл при `max_tokens: 4000` — успех за 9 с. Ответ в обоих
случаях короткий: разница только в бюджете рассуждений.

## B.1 Классификация (llm-слой)

`LlmError` получает поле `limit?: number` — эффективный `max_tokens` этого запроса.
Ветка `finish_reason=length` делится на две:

| условие | `kind` | сообщение |
|---|---|---|
| обрезан tool_call | `truncated_tool_call` | как сейчас (`error.llm_truncated_toolcall`) |
| текста и tool_call нет | `truncated_no_content` | новый ключ: «Лимит генерации ({tokens}) исчерпан **до первого символа ответа** — его потратили рассуждения модели. Увеличьте `max_tokens`/`maxCompletionTokens`; уменьшать и дробить вывод бесполезно» |
| текст уже ушёл | — | как сейчас (warning + `error.llm_output_truncated`) |

`st` в `doStream` получает `sawReasoning`, чтобы сообщение говорило о рассуждениях только
когда они были (для не-reasoning модели формулировка остаётся нейтральной: «до первого
символа ответа»).

## B.2 Политика петли

`loop-llm.ts`, ветка **до** общего recoverable-обработчика:

1. Счётчик `state.truncationRetries` ≤ `MAX_TRUNCATION_RETRIES = 1`.
2. Reasoning на повтор — **выключить**: `state.iterForceNoReasoning = true`;
   `ReasoningEffortResolver` отдаёт `"none"` с источником `agent_override` и не пускает
   политику (иначе она поднимет до `high`). Там, где эндпоинт не умеет выключать
   thinking (deepseek: кэш пробы `…|openai-effort|nooff`), поле на провод не уйдёт —
   это известный долг `hosted-reasoning-discovery`, а не регресс.
3. Директива `truncated` (переживает компакцию, реестр `directives.ts`): «Бюджет
   рассуждений исчерпан. Ответь сразу, без рассуждений, коротко».
4. Бюджет на повтор — `min(limit × 2, 32000)`: единственный рычаг, который работает и
   там, где thinking не отключается. Поднимать потолок бесплатно (модель платит только
   за сгенерированное), а первый заход уже доказал, что бюджета не хватило.
5. `iterRecoverableLlmError` в этом случае **не ставится** — иначе политика поднимет
   reasoning (см. п. 2).

Если и повтор усечён до ответа — обычный текст ошибки уходит модели/вызывающему с
честной причиной, без третьей попытки.

## B.3 `withTokenCap`: явный лимит вызывающего главнее

`withTokenCap` остаётся источником **дефолтного** бюджета субагента, но больше не
клампит явный `options.maxTokens` вниз: явный лимит проходит до `maxExplicit`
(`MAX_TOKENS_MAX = 32000`, его передаёт `subagent-run`). Иначе эскалация из B.2 не
доходит до провайдера и фикс бесполезен для субагентов. Первый заход петли `maxTokens`
не передаёт — значит `max_tokens` тула действует как раньше.

Описание `max_tokens` у тула уточняется: это бюджет **одной** генерации; при усечении до
ответа харнесс может один раз повторить с удвоенным бюджетом.

## B.5 Раскладка кода

`loop-llm.ts` стоит на потолке `.arch-allowlist.json`, поэтому новый код разложен по
швам (правило 6), а потолок файла **уменьшен** 399 → 332:

- `src/llm/truncation-error.ts` — конструктор ошибки обрыва (общий для стрима и
  non-stream-фолбэка);
- `src/core/agent/truncation-recovery.ts` — подготовка повтора (флаги, директива,
  бюджет);
- `src/core/agent/loop-llm-errors.ts` — весь разбор ошибок вызова LLM, вынесенный из
  `loop-llm.ts` (`handleLlmError`).

Потолок `src/llm/openai-compat.ts` тоже пересчитан вниз: 962 → 956.

## B.4 Вне скоупа

- Автодетект «эндпоинт умеет `reasoning_effort: "none"`» — долг
  `hosted-reasoning-discovery` (нужен сетевой проб + кэш).
- Раздельный бюджет reasoning/ответ на уровне провайдера — его нет в OpenAI-совместимом
  контракте; `max_tokens` остаётся общим потолком.
- Запись прогона субагента в `session.jsonl` (D4) и видимость 403 (D6) — долги
  `subagent-run-invisible-in-session-log`, `llm-provider-error-invisible-to-user`.

## Тесты (падали бы до правки)

1. `tests/core/llm-truncation-recovery.test.ts` — провайдер-заглушка: первая попытка
   бросает `LlmError(kind="truncated_no_content", limit=900)`, вторая отдаёт текст.
   Проверить: второй вызов получил `reasoningEffort: "none"` и `maxTokens: 1800`;
   в контексте есть директива; результат успешный; третьей попытки нет.
2. Там же — повтор тоже усечён: ровно 2 вызова, честная ошибка, без `reasoning: high`.
3. `tests/openai-compat.test.ts` — существующий тест «empty and length-capped»
   дополняется: `kind === "truncated_no_content"`, `limit` заполнен, текст про
   рассуждения.
4. `tests/tools/subagent-max-tokens.test.ts` — явный лимит больше капа проходит
   (эскалация), явный меньший — остаётся меньшим.

## Риски

- Скоуп `bash` (A): субагент может прочитать через shell файл вне `allowed_files`.
  Декларируем это явно в описании тула; для egress-политики уже есть долг
  `file-content-bypass-non-path-tools`. Родитель имеет те же права — прироста доверия нет.
- Эскалация (B): один лишний запрос на провальный ход. Ограничено одним повтором и
  потолком 32000; срабатывает только при нулевом выходе, то есть когда терять нечего.
- Эскалация может упереться в потолок модели: провайдер, у которого вывод физически
  меньше удвоенного бюджета, ответит 400 — ход завершится `error.llm_api` вместо
  `truncated_no_content`. Живой пробы хостед-эндпоинта в этой задаче не было (ключ в
  `~/.mma` не прошёл аутентификацию на момент проверки). Если это станет реальностью —
  потолок эскалации привязывается к `modelCapabilities`.
