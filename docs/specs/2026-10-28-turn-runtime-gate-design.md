# Гейт поведения в ходе: чем подтверждается «шаг выполнен»

_Дата: 2026-10-28. Ветка: `docs/turn-gate-lsp-specs`. Долги `turn-runtime-gate` и
`turn-browser-gate` оплачены 2026-10-29 (W1–W4 реализованы). Источник: стресс-тест, волна 21 (D-15)._

**Статус:** W1–W4 реализованы (`0c8bc7d0`, `8f31f048` + этот коммит); **D-15 закрыт**. Гварды
`tests/execution/*` зелёные. Открытых долгов по этой спеке нет.

## Что показала проблема (наблюдение)

Один ход на e4b: сборка зелёная (`bun run build` → exit 0), дифф аккуратный
(+36/−4, один файл), отчёт модели «все требования реализованы» — а приложение
не открывается:

```
TypeError: selectedBikeIds.has is not a function
```

`JSON.parse(...) as Set<string>` — массив вместо `Set`; `tsc` приведение типа
принимает, страница пустая. В том же ходе `verify` вызывался 5 раз, `lsp_check`
— 4, `bash` с `bun run build` — 4. Ни один гейт не мог этого увидеть, потому
что все они проверяют **статику**: наличие файла, код возврата сборки, типы.

При этом контракт проверок в плане уже шире, чем то, чем пользуется модель:
`plan` принимает `file-exists:<path>`, `command:<cmd>` и `manual:<что проверить
глазами>` (`src/i18n/ru.json:309`). Модель ставит `command: bun run build` —
формально «команда выполнена», фактически — не доказательство поведения.

## Решение

Три правки в одной точке исполнения (`verify`) плюс одна в аудите хода. Ни одна
не требует браузера.

### 1. Классификация доказательств

`verify` делит доказательства на два класса:

| класс | примеры | что доказывает |
|---|---|---|
| статическое | `file-exists:*`, `command:` с build/typecheck/lint (`bun run build`, `tsc`, `eslint`, `biome`) | «код компилируется» |
| поведенческое | `command:` с тестами/запуском (`bun test`, `npm test`, `pytest`, `curl`), `http:` и `browser:` (проба страницы), `manual:` | «что-то работает» |

Классификация — по **первому слову команды** из фиксированного списка
(`BUILD_COMMANDS`), а не по эвристике «содержит build»: список короткий и
тестируемый, расширяется одной строкой.

### 2. Требование к шагу, меняющему поведение

У шага есть признаки поведения: описание содержит `UI`, `компонент`, `страниц`,
`экран`, `стил`, `интерфейс` (ru) или `UI`, `component`, `page`, `screen`,
`style`, `layout` (en). Для такого шага статического доказательства **не
достаточно**: `verify` возвращает `success: false` с подсказкой

> шаг меняет поведение: нужна поведенческая проверка (`command:` с тестами или
> `http:<url>`) либо `manual:` с наблюдением

и не двигает шаг в `done`. Остальные шаги (рефакторинг, доки, конфиг) — как
сейчас: `file-exists` + build достаточно.

### 3. `manual:` перестаёт быть самоподтверждением (для шагов про поведение)

Сейчас `manual:` принимается на слово. Новый контракт: при `plan_step
status=done` шаг, **меняющий поведение/UI**, с `manual:` обязан нести
наблюдение (`note`), и это наблюдение пишется в `session.jsonl` событием
`verify_evidence`:

```json
{"type":"directive","source":"module:execution","event":"verify_evidence",
 "step":2,"text":"открыл /, видны 6 карточек, поиск «город» → 1"}
```

Фактический формат — запись `directive` (`SessionLogger.logDirective`) с
`event: "verify_evidence"`, номером шага в поле `iteration` и наблюдением в
`detail`; отдельного типа события `verify_evidence` нет.

`audit` считает такой шаг подтверждённым, только если у него есть наблюдение.
Нет записи → шаг попадает в `pendingSteps`, ответ помечается как
неподтверждённый (как сейчас с «✗ Задача не может быть подтверждена»).

Для шагов, которые поведение не меняют (research, советы, доки), `manual:`
остаётся самоподтверждением: требовать «что я увидел» от текстовой задачи —
шум, а не сигнал. Это сужение относительно первой редакции спеки: полный
запрет ломал легитимные некодовые планы.

### 4. Новый вид проверки `http:`

```
http:<url>                 → GET, ожидается 2xx
http:<url>~<подстрока>     → GET, 2xx и подстрока в теле
```

Исполняется `verify` (не моделью). Таймаут 3 c, тело читается до 256 KiB,
редиректы не разыменовываются, ответ показывается модели одной строкой
(`200 · 1234 B · marker found` / `не найдено`). Проверка учитывается в шаге как
поведенческая.

### 5. Новый вид проверки `browser:` (закрывает D-15)

```
browser:<url>                  → страница грузится без ошибок консоли
browser:<url>~<подстрока>      → плюс подстрока в видимом тексте/HTML
```

Исполняется `verify` (не моделью), тем же путём, что `http:`. Проба:

- одна навигация по одному URL, headless, без интерактива и скриншотов;
- бюджет 7 c на запуск + навигацию + чтение DOM (плюс 300 мс на поздние ошибки);
- `goto` — обычная браузерная навигация (редиректы разыменовываются браузером),
  тело/время ограничены бюджетом;
- отказ, если есть `console.error`/`pageerror` после фильтра известного шума
  (React DevTools, `ResizeObserver loop`, favicon); ошибка не глотается;
- маркер ищется в `document.body.innerText` и HTML;
- ответ модели — одна строка `ok · N console errors · marker found/not found`;
- `page`/`context`/браузер закрываются в `finally`, проба не оставляет
  долгоживущий Chromium; проверки идут по одной (verify последователен).

**Опциональность.** Chromium/Playwright — необязательная зависимость среды.
Если Chromium не установлен или драйвер не поднялся, проверка возвращает
`success:false` с причиной (`browser unavailable: …`, команда установки) — это
не fail-open (INV-G4). Автоматического `skipped` нет: «не проверили» не значит
«прошло». Пользователь может не использовать `browser:` в своих планах.

**Чего проба не делает:** не кликает, не заполняет формы, не снимает скриншоты,
не проверяет несколько URL и не заменяет `manual:` для визуальной оценки.
Она отсекает класс «200, но страница пустая из-за `TypeError`», а не
доказывает корректность UI.

## Что это НЕ решает (честно)

`http:` с 200 не доказывает рендер: пустая страница тоже отдаёт 200 — ровно
случай волны 21. `browser:` закрывает этот класс (ошибки консоли/pageerror и
маркер), но не интерактив: клики, формы и визуальная оценка остаются за
`manual:` с записью. Браузерный прогон в ходе — по-прежнему дорогой путь
(Chromium, дев-сервер, таймауты), поэтому он ограничен одним URL и 7 c.

## Инварианты

- **INV-G1.** Требование доказательства живёт в `verify` (точка исполнения), а
  не в промпте и не в хендлере `plan_step`. Отключить его нельзя без изменения
  `verify`.
- **INV-G2.** `manual:` без `verify_evidence` не подтверждает шаг; запись
  создаётся в том же месте, где шаг переводится в `done`.
- **INV-G3.** Классификация команд — фиксированный список, а не regex по
  описанию; новое «статическое» доказательство добавляется только туда.
- **INV-G4.** Ошибка исполнения проверки (`http:`/`browser:` таймаут, недоступный URL
  или браузер) — это `success: false` с причиной, а не fail-open «ладно, пройдёт».

Тесты браузера не требуют Chromium: лаунчер инжектируется, как `fetchImpl` у
`http:` (`BrowserProbeLauncher`).

## План

1. **W1.** Классификация доказательств + `http:` в `verify`, подсказки в
   `plan.checks_*`. Гейт: два первых теста.
2. **W2.** `manual:` → `verify_evidence` + учёт в `audit`. Гейт: третий тест.
3. **W3.** Текст системного промпта и `plan.checks_required`: примеры для
   UI-шагов (`http:`/`browser:`/`manual:`), без увеличения бюджета промпта (≤300 токенов
   на блок — проверяется `tests/core/system-prompt-freeze.test.ts`).
4. **W4.** `browser:<url>[~marker]` в `verify` (D-15): headless-проба страницы через
   существующий браузерный модуль, инжектируемый лаунчер, отказ на ошибках консоли и
   недоступном Chromium. Гейт: `tests/execution/browser-check.test.ts`.

Порядок важен: W2 меняет контракт `plan_step`, поэтому идёт после W1 (когда
модель уже получает подсказку, чем заменить build-доказательство).
