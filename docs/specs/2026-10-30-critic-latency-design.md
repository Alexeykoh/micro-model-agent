# A15: пост-обработка после ответа модели — бюджет и измеримость

**Дата:** 2026-10-30 · **Статус:** реализовано (A15, P0) · **Ветка:** `fix/a15-post-answer-latency`

## 1. Симптом

Ответ уже в ленте (`assistant` + `turn_end` нет), но ход не завершается ещё ~120 с:
финальный статус (`успех`/`ошибка`, номер итерации) приходит через две минуты.
Пользователь видит готовый ответ и «зависший» спиннер.

## 2. Где реально уходит время (по фактам из кода)

Порядок после последнего текстового ответа (`src/core/agent/loop-gates.ts`):

```
hallucination gate → critic gate (await) → audit gate (await) → break
```

и форс-финал (`src/core/agent/loop-run.ts:156`) повторяет цепочку
`critic.evaluate(...)` → затем результат хода.

Факты, каждый проверяемый по коду:

| #   | Факт                                                                                                                                                                                                                                                 | Следствие для латентности                                                                                                                        |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| F1  | `DEFAULTS.critic.timeoutMs = LLM_REQUEST_TIMEOUT_MS + WRAPPER_OVERHEAD_MS` = **125 000 мс** (`src/config/defaults.ts:43`)                                                                                                                            | один вызов критика может держать ход 125 с                                                                                                       |
| F2  | `CriticClient.verify` делает **до трёх** LLM-проходов, у каждого свой таймаут (`src/modules/critic/client.ts:110–113`, `:157–178`)                                                                                                                   | худший случай цепочки — 3 × 125 с; per-call бюджет был введён намеренно (W2/D7), но общего потолка на гейт нет                                   |
| F3  | Гейт `CriticGate.evaluate` не имеет собственного дедлайна: единственный ограничитель — таймаут клиента                                                                                                                                               | если провайдер игнорирует `signal`, гейт ждёт, пока клиент не выиграет гонку дедлайна (83–120 с в живом кейсе, комментарий `client.ts:209–211`)  |
| F4  | `AuditGate.evaluate` → `ExecutionModule.runFinalAudit` → `Auditor.audit` **синхронно запускает тесты проекта** (`runTests`, кап 90 с) и **`tsc --noEmit`** (`runTypecheck`, кап 90 с) — `src/modules/execution/audit-runners.ts:118–122`, `:202–209` | на этом репозитории полный `bun test` не успевает за 90 с → это «inconclusive», то есть **90 с потрачены без результата**; затем ещё до 90 с tsc |
| F5  | В `session.jsonl` нет длительностей: `critic_check` пишется **до** вызова и без `duration`, вердикт `ok` не пишется вовсе (`critic-gate.ts:70`), успешный аудит не пишется вовсе (`audit-gate.ts:65`)                                                | по логу нельзя сказать, где именно 120 с                                                                                                         |
| F6  | `critic.maxTokens` прокидывается (`loop-setup.ts:110` → `client.effectiveMaxTokens`) и покрыт тестами (`client-budget.test.ts:222–237`)                                                                                                              | кап токенов уже работает, правки не требует                                                                                                      |
| F7  | Повторный вызов на неизменном вердикте: `isRepeatedVerdict` не даёт **тратить ремонт**, но LLM всё равно вызывается (`critic-gate.ts:76–90`)                                                                                                         | после совета модель может ответить тем же текстом — платим второй вызов ни за что                                                                |

**Вывод:** 120 с — это не «критик вообще», а два независимых слагаемых:
(а) критик без общего дедлайна (F1–F3), (б) финальный аудит, который гоняет
полный тест-сьют и tsc синхронно (F4). До этой правки отличить их было нельзя —
в логе не было ни одной длительности (F5).

## 3. Решения

### 3.1 Два разных таймера, а не один (F1–F3)

`critic.timeoutMs` остаётся **обёрткой вокруг одного провайдерского запроса**
и по-прежнему обязан быть длиннее `LLM_REQUEST_TIMEOUT_MS`
(`tests/arch/timeout-relations.test.ts`): иначе обёртка всегда проигрывает гонку
провайдеру и диагностика `call_timeout` недостижима (инвариант W2/D7).

Латентность хода регулирует **новый отдельный бюджет** — `CRITIC_GATE_BUDGET_MS`
(`src/config/timeouts.ts`), потолок на весь гейт критика за одну проверку
(все проходы `verify`):

- 45 000 мс, строго меньше `LLM_REQUEST_TIMEOUT_MS`;
- 45 с, а не 25 % (30 с): один проход критика на локальной 9B с пакетом
  ~40 тул-событий занимает 20–40 с; 30 с отправили бы в fail-open почти каждый
  вердикт, то есть тихо отключили бы гейт. 45 с сохраняют достижимость вердикта
  и срезают хвост в 2,7 раза;
- **это константа реестра таймаутов, а не ключ конфига.** Бюджет — инвариант
  латентности: настраиваемый ключ означал бы «двухминутный хвост возвращается
  настройкой». Плюс запись в `DEFINITIONS` раздувает `src/config/registry.ts`
  за его потолок в `.arch-allowlist.json` (правило 6: потолки только
  уменьшаются). Гейт берёт константу в `loop-setup.ts`; это закреплено тестом
  `tests/arch/timeout-relations.test.ts`;
- по истечении бюджета гейт **прерывает** вызов (`AbortController` в сигнал
  клиента) и делает fail-open `pass` с записью: `critic_verdict {degraded:true,
timedOut:true, duration}` + `critic_error {cause:"turn_budget (45000ms)"}` +
  одна статус-строка в ленту (класс `budget`). Молчаливого pass нет (INV-15);
- если бюджет истёк на проходах 2–3, клиент возвращает вердикт прохода 1
  (существующая семантика `verifyWithChecks`), а не теряет его.

Разница двух чисел — не противоречие: 125 с отвечают на вопрос «не оборвать
живой запрос раньше провайдера», 45 с — «сколько ход стоит в проверке после
того, как ответ уже доставлен».

### 3.2 Измеримость (F5)

- `critic_verdict` (включая degraded) получает `duration` (мс) и, при таймауте,
  `timedOut: true`;
- `critic_escalation` получает `duration` того же вызова;
- `critic_check` получает `budgetMs` — по логу видно, какой потолок действовал;- новый сессионный евент **`gate_timing`** (одна запись на проход гейтов):
  `{ iteration, duration: total, gates: { hallucination, critic, audit } }`.
  Пишется из `loop-run.ts` в единственной точке, где гейты возвращают сигнал,
  поэтому покрывает все исходы (`continue`/`break`/`return`). Тип добавлен в
  `SessionLogEntry` (`src/modules/session/store.ts`), поле `gates` — опциональное;
- потребитель агрегата — **`mma session diagnose`**: новая сигнатура
  `gate_stall` срабатывает на `gate_timing.duration > thresholds.gateStallMs`
  (30 000 мс) и печатает разбивку по гейтам. Иначе это был бы лог «в никуда»
  (правило 5: инвариант без проверки / событие без потребителя не считается).

### 3.3 Повторный вызов на неизменном вердикте (F7)

Гейт помнит «отпечаток» входа (форма тул-событий хода + текст ответа, с хешем).
Если пакет не изменился **и** сказать модели больше нечего (советный цикл
израсходован, прошлый вердикт был не-ok, а все его жалобы уже показаны), LLM-вызов
не делается: пишется `critic_check {skipped:"unchanged_pack"}` и гейт отвечает
`pass`. Ремонт и совет не затрагиваются: пока есть свободный советный цикл,
вызов происходит, и модель слышит «смени подход» (`tests/critic-gate.test.ts`
держит INV-C6).

### 3.4 Параллельность critic/audit — **нет** (осознанный отказ)

Формально аудит не читает вердикт критика, но параллелить нельзя без смены
контракта, и смена контракта тут дороже выигрыша:

1. `runFinalAudit` **меняет состояние плана**: `autoCloseEvidenceSteps`,
   `store.saveActive`, `flushSessionPlan`, декремент `auditSkipsRemaining`
   (`src/modules/execution/final-audit.ts:95–133`). Спекулятивный прогон
   выполнит эти мутации для ответа, который критик тут же отзовёт на ремонт.
2. Семантика `retry`/`break`/`exhausted` живёт в `AuditGate` **после** вердикта
   критика; при параллельном запуске пришлось бы инжектить `<system-summary>`
   от аудита, а потом отзывать сообщение — модель получила бы два
   противоречащих указания в одном контексте.
3. Порядок логирования (`critic_verdict` → `audit`) — часть разбора сессии.

Выигрыш от параллелизма был бы только при «критик медленный **и** аудит
медленный»; в наблюдаемом профиле доминирует аудит (F4), который
параллелизмом не сокращается. Реальная правка аудита — отдельная задача в
`src/modules/execution/` (см. долг `audit-final-gate-full-test-run`).

### 3.5 Видимость для пользователя

Инвариант «проверка, которая прошла успешно, молчит» (`tests/critic-degrade-feed.test.ts`)
сохранён: строка появляется **только если проверка действительно долгая**.

- критик: через `CRITIC_SLOW_NOTICE_MS = 2 000` после старта — одна статус-строка
  `↳ проверяю результат…` (`ui.critic_checking`);
- аудит: через `AUDIT_SLOW_NOTICE_MS = 3 000` — `↳ проверяю план и тесты…`
  (`ui.audit_checking`). Это та проверка, которая реально держит ход 90+ с,
  и раньше она была полностью невидима.

Оба сообщения идут через `onMeta(text, "status")` — существующий канал, который
веб показывает всегда (не quiet-гейтится). Новых SSE-событий нет; фронтенд
(`src/modules/webui/assets/**`) не меняется.

## 4. Что осталось долгом

`audit-final-gate-full-test-run` (см. `docs/agents/debt.md`): финальный аудит
синхронно гоняет полный тест-сьют (кап 90 с) и `tsc` (кап 90 с), причём на
большом репозитории прогон не укладывается в кап и результат «inconclusive»,
то есть время потрачено без пользы. Выход: скоупить прогон (только
затронутые тесты) или вынести в фон с отчётом после `turn_end`.

  `signal`, не держит гейт дольше бюджета → fail-open с записью; (в) на
  неизменном пакете повторного вызова нет; (г) длинная проверка даёт одну
  статус-строку, быстрая — ни одной.
