# Критик: провенанс вердикта и улики в журнале (design)

**Дата:** 2026-11-03 · **Ветка:** `fix/critic-evidence-provenance` · **Статус:** принято

**Источник:** `TODO.md` §1.8, пункт **A6** (живые сессии `ses_mvv8mr4z`,
`ses_mvzp8cuk`).

## Проблема

1. Критик эскалирует до `critical` числа/факты, не подкрепляя жалобу уликой
   («заявлен 1487, а на самом деле >4000»). Гейт на такую жалобу тратит
   repair-цикл и лишние итерации, хотя проверить утверждение нечем.
2. В `session.jsonl` строка `critic_check` содержит только **имена** тулов
   («checked 3 tool call(s): load_skill, list_dir») — по ней нельзя понять, что
   именно критик видел: путь? команда? вывод? Проверки невидимы.

## Решение

### 1. `critical` с перечисленными жалобами требует улики

Если вердикт `critical` и в `issues` есть хотя бы одна жалоба severity
`critical`, то хотя бы у одной такой жалобы поле `evidence` обязано быть
непустым. Иначе вердикт **понижается до `concern`** (жалобы тоже становятся
`concern`), в журнал пишется `critic_verdict` с `downgraded: "no_evidence"`.

Это не ослабление проверки: жалоба по-прежнему доходит до модели советом
(`concern` → advice → retry), но не тратит repair-бюджет «критического»
вердикта. Требование уже стоит в промпте критика («Every issue must reference
concrete evidence»), теперь оно обеспечено исполнением, а не надеждой.

**Не трогается:** `critical` без перечисленных жалоб (критик сказал «задача не
выполнена» списком без issues) — там требование улики неприменимо, и текущее
поведение (ремонт) сохраняется. `ok`/`concern` — без изменений.

### 2. Улики — в журнал

`critic_check` получает поле `evidence`: до 8 тул-событий в виде
`tool(ключ-аргумента)`, где ключ — `path` / `from` / `to` / `command` / `url`
(обрезано 60 симв.). Имена тулов остаются в `tools`. По строке видно, что
именно проверялось, без раскрытия тел файлов и секретов (аргументы уже
редактируются фильтром лога контекста на уровне сессии).

## Инварианты

- **INV-P1** `critical` не эскалирует ремонт без `evidence` в перечисленных
  критических жалобах.
- **INV-P2** Понижение видно в журнале (`downgraded`) — молчаливой смены
  статуса нет (INV-15).
- **INV-P3** `critic_check.evidence` не содержит тел файлов/вывода и не растёт
  с числом событий (кап 8).

## Тесты

- `tests/modules/critic/provenance.test.ts` — чистая функция понижения:
  с уликой не меняется; без улики `critical`→`concern` + severity жалоб;
  критический вердикт без issues не меняется.
- `tests/core/critic-gate-evidence.test.ts` — гейт: `critical` без улики идёт
  советом (`retry`, `criticRepairCycles` не растёт), с уликой — ремонтом;
  `critic_check.evidence` содержит путь аргумента.

## Вне объёма

- Автоматическая проверка числовых утверждений против `node_modules`
  (индекс/диск) — отдельная задача, здесь только требование улики.
- Промпт критика не меняется (требование уже есть).
