# Спека: инвариант «модель принадлежит провайдеру» и честный статус списка моделей

Дата: 2026-11-17 · Ветка: `v0_26_0` · Связано: память моделей (INV-19)

## Проблема

1. **Чужая модель после смены провайдера.** Память `provider.models[name]`
   восстанавливает модель записи, но если у нового провайдера памяти нет,
   `syncProviderModelMemory`/`Agent.setProvider` оставляли текущую модель
   прошлого бэкенда. Карточка «Активная модель» и запросы показывали
   `qwen3.8-27b` (opencode-go) после переключения на `llama.cpp` — модель,
   которой у нового провайдера может не быть. Симптом: свитч «успешен», а ход
   падает 404 `model not found`.
2. **Неразличимые состояния списка моделей.** `GET /api/models` для активного
   провайдера отдавал только `models`. Клиент не знал, идёт ли загрузка,
   провайдер не ответил или он честно вернул пустой список, и во всех трёх
   случаях рисовал «провайдер не сообщил моделей».
3. **Список не перерисовывался.** SSE-событие `models` вызывало `loadModels`,
   но обновляло только селекторы композера; открытая панель настроек оставалась
   со старым/пустым списком до ручного пере-рендера.

## Инвариант

**INV-P1: активная модель либо выбрана для активного провайдера, либо пуста.**
Чужой id не наследуется и не выдаётся за рабочий.

- Свитч `provider.active` восстанавливает `provider.models[name]`; памяти нет —
  `config.model = ""` (в UI «модель не выбрана»), а не модель прошлого бэкенда.
- `Agent.setProvider` ведёт себя так же и не записывает пустую модель в память.
- Откат по TOCTOU (`409 busy`) возвращает и `provider.active`, и `model`.
- Очистка модели (или уже пустая модель) возвращает окно контекста в `auto`
  (дефолт): ручное окно принадлежало удалённой модели, и применять его к
  следующей нельзя.
- Очистка применяется и к живым раннерам (main + `pool.runnerIds()`), а не
  только к основному агенту.
- Проверка выполняется после каждого успешного обновления списка (boot,
  reconfigure, кнопка «повторить»), а не только на старте.
- Алиасы, которых провайдер не отдаёт в `/models`, разрешаются явно:
  `ProviderEntry.unlistedModels` (поле формы «модели/алиасы вне списка»).
  Такие id не очищаются; всё остальное вне списка — очищается.
- Карточка активной модели не выдаёт неподтверждённое имя за рабочую: пока
  список грузится — «проверяем по списку провайдера…», при ошибке — «не
  проверена: провайдер не отдал список», а после успешного списка без модели —
  «нет в списке провайдера». Неподтверждённое имя гасится.
- «Контекстное окно» в карточке показывается только при выбранной модели:
  без неё число было бы памятью о прошлой модели (ни `entry.contextWindow`,
  ни `config.contextWindow` не доказывают окно для несуществующего выбора).
- Исчерпание поллинга `loading` больше не оставляет вечный спиннер: статус
  становится `error` с кнопкой «повторить». SSE-реконнект (сервер
  перезапустился) перечитывает конфиг и список моделей — раньше страница жила
  со старым кэшем до ручной перезагрузки.
- После первого списка при boot сервер рассылает SSE `models`: иначе панель,
  открытая до завершения фонового refresh, оставалась на «загрузке моделей…»
  (другого повода перезапросить список после старта не было).

## Честные состояния списка

`GET /api/models` (активный провайдер) аддитивно отдаёт `loading` и `error`:

```json
{ "models": [], "loading": false, "error": true }
```

- `loading: true` — списка ещё нет (первый запрос/фоновый refresh); клиент
  опрашивает до готовности и по SSE `models`. Если список уже получен, фоновый
  refresh его не прячет: `loading` не подменяет готовые данные (живой баг:
  32 модели и `loading:true` одновременно).
- `error: true` — списка нет, провайдер не построился или `listModels()` упал;
  пустой `models` нельзя трактовать как «моделей нет». Следующий `GET
  /api/models` после ошибки запускает повторную попытку (кнопка «повторить»).
  Прежний успешный список при неудачном refresh сохраняется.
- `loading/error` отсутствуют у легаси-стабов и per-provider запросов
  (`?provider=`) — там контракт не меняется.

Клиент (`settings.modelsStatus`): `idle → loading → ready | error`.
`ready` + пустой список = «провайдер не сообщил моделей»; `error` = «не удалось
получить список»; `loading` = «загрузка моделей…». Смена провайдера сразу
сбрасывает старый список (он принадлежал другому бэкенду) и включает `loading`.
Любое обновление списка перерисовывает открытую панель настроек. Открытие
вкладки «Модели» догружает список из состояния `idle` (boot/SSE могли быть
пропущены); `error` повторяется только кнопкой.

## Проверки

- `tests/config/registry.test.ts` — свитч без памяти очищает модель.
- `tests/core/provider-setprovider.test.ts` — `setProvider` очищает модель и не
  запоминает пустую.
- `tests/webui-models-per-provider.test.ts` — `getActiveState`: loading → ready,
  офлайн → error; провод `loading/error` в `/api/models`; готовый список не
  уходит в loading при фоновом refresh; повтор после ошибки.
- `tests/webui-model-panel-dom.test.ts` — loading / error / пустой список
  различимы, подпись провайдера, предупреждение о чужой модели, маркеры
  «проверяем»/«не проверена».
- `tests/webui-model-invariant.test.ts` — очистка только по непустому списку без
  ошибки; fail-open на loading/error/empty; персист обоих доменов; сброс
  ручного окна при пустой/удалённой модели; allowlist алиасов.
- `tests/webui-model-surface.test.ts` — boot-рассылка `models` и `config` при
  очистке модели; явный источник списка отключает фоновый refresh; очистка
  доезжает до раннеров; явный refresh перепроверяет модель.
- `tests/webui-providers.test.ts` — allowlist `unlistedModels` парсится,
  валидируется и переживает upsert.
- `tests/arch/provider-model-invariant.test.ts` — arch-гейт INV-P1: свитч без
  памяти, восстановление памяти, очистка вне списка, fail-open, allowlist,
  сброс пустого ручного окна.
