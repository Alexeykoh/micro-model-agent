# Авторитетное подтверждение: одноразовый токен `approve` вместо маркера в тексте

_Дата: 2026-11-01. Ветка: `feat/approve-token`. Статус: реализуется._
_Закрывает DEBT `approve-marker-not-authoritative`._

## 1. Что наблюдается

Запись в защищённый путь (`.env*`, `*.key|pem|p12|crt`, `.git/`, `.npmrc`, `.netrc`)
всегда блокируется `[PROTECTED PATH]`-директивой «спроси пользователя». Инструмент
`approve` существует и спрашивает Yes/No, но его ответ **ни на что не влияет**:
исполнитель не знает, что пользователь что-то подтвердил. Модель может написать
`[APPROVED]` в тексте ответа — это тоже ничего не разрешает (и не должно), но и
легального пути «пользователь подтвердил → запись прошла» нет вовсе.

## 2. Причина

Подтверждение не имеет состояния. `approve` возвращает только строку, а
`protectedPathBlock()` (`src/modules/security/protected-paths.ts`) проверяет лишь
путь. Между «пользователь нажал Yes» и «исполнитель выполняет запись» нет носителя
решения, поэтому единственный кандидат — текст модели, а он недоверенный.

## 3. Контракт

### 3.1 Разрешение — состояние, а не текст

`ApprovalStore` (`src/core/approvals.ts`) — per-process/per-session хранилище
одноразовых разрешений:

```ts
interface ApprovalGrant {
  token: string;      // randomUUID, только для аудита
  path: string;       // нормализованный абсолютный путь
  action: string;     // текст, который видел пользователь
  expiresAt: number;  // now + APPROVAL_TTL_MS
  usedBy?: string;    // tool call id, который уже потребил разрешение
}
```

- `grant(path, action)` вызывается **только** хендлером `approve` после
  положительного ответа пользователя.
- `consume(path, callId)` вызывается **только** enforcement'ом
  (`checkToolPath`) и возвращает разрешение один раз на `callId`.
  Повторный `consume` с тем же `callId` (TOCTOU-recheck перед операцией)
  возвращает то же разрешение и не «сжигает» вторую попытку.
- Просроченные разрешения не действуют и вычищаются при обращении.
- Текст ответа модели никогда не читается: `[APPROVED]` в сообщении не создаёт
  и не потребляет разрешение.

### 3.2 `approve` получает `path`

Схема тула дополняется необязательным `path` (обратная совместимость: без него
поведение прежнее — просто Yes/No без разрешения на запись):

```
path: "File path this approval covers (required to authorize a protected write)"
```

При Yes и заданном `path` хендлер нормализует путь относительно `baseDir`
(тем же `safeResolvePath`, что и enforcement) и минтит разрешение. Пользователь
видит путь в вопросе (`tool.approve_prompt` уже печатает `action`; в `action`
модель обязана назвать изменение, а путь печатается отдельной строкой).

Ответ хендлера: `tool.approved_path` — «одноразовое разрешение для {path} выдано;
повтори операцию один раз».

### 3.3 Enforcement потребляет разрешение

`checkToolPath(ctx, security, value, toolCallId)`:

1. Если путь защищённый и это пишущий тул:
   - `ctx.approvals?.consume(safeResolvePath(ctx.baseDir, value), toolCallId)` —
     если разрешение есть, путь разрешён, в аудит пишется `security_approval`
     (token, action, path, callId);
   - иначе — прежний `[PROTECTED PATH]`-блок.
2. Остальные проверки (scope, allowlist записи, SSRF) не меняются.

Разрешение одноразовое и привязано к точному пути; запись в другой защищённый
путь требует нового `approve`.

### 3.4 Директива учит модели правильному шагу

`file.protected_path_ask` (en+ru) дополняется: «если пользователь разрешит —
вызови `approve` с `path=<путь>` и затем один раз повтори операцию; маркер в
тексте ответа не считается подтверждением».

### 3.5 TTL

`APPROVAL_TTL_MS = 5 * 60_000` в `src/config/timeouts.ts`. Разрешение живёт
до первого использования или до истечения TTL, что раньше.

## 4. Не-цели

- Полноценный диалог «ожидает подтверждения» с кнопками в REPL/вебе: кнопки уже
  есть у `question`/`approve`; здесь меняется только авторитетность ответа.
- Подтверждение для `bash`-команд и удаления: `approve` с `path` покрывает
  файловые мутации; команды имеют свои чёрные списки.
- Изменение списка защищённых путей и always-on политики.
