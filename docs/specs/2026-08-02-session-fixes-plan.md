## P1. `TS5112` в пер-файловом `tsc` (11 повторов) — высокий

**Аргументы (доказательства):**
- Всё 11 «Syntax check failed» — одна и та же ошибка `TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline. Use '--ignoreConfig'`. Проект `mma_test` использует **TypeScript 7.0.2** (`devDependencies`), а TS 7 (native compiler) теперь **ошибкой** реагирует на наличие `tsconfig.json` при передаче файлов в командной строке — раньше просто игнорировал.
- Агент не смог распознать, что ошибка ложная, и «лечил» хаками: создал корневой `tsconfig.json`, потом `src/typescript.tsconfig.json`. Каждый виток ошибки забирал токены и толкал к компакции.
- Затронуто **два** места: `src/modules/plugins/builtin/lint-on-write.ts:45` и `src/modules/execution/verifier.ts:159`.

**Решение:**
1. В `checkSyntax` (lint-on-write.ts:42-58) и `validateSyntax` (verifier.ts:154-183) — если stderr содержит `TS5112`, возвращать «синтаксис ок» (`null`/`true`), т.к. это ошибка конфигурации, а не файла.
2. Бонус: отфильтровать и `TS2307`/`Cannot find module` в `checkSyntax` (в verifier это уже есть — verifier.ts:166) — иначе валидные файлы с алиасами путей будут давать ложные фейлы.
3. Нюанс: если хочется сохранить строгость, добавить `--ignoreConfig` в вызов `tsc` — но тогда файл проверяется с дефолтными опциями (теряются `paths`, `jsx` и т.п.), поэтому **фильтрация TS5112 проще и безопаснее**.

**Тесты:** в `tests/` кейс «temp-проект с tsconfig + валидный `.ts` → плагин не аппендит "[Syntax check failed]"», и «`.ts` с синтаксической ошибкой → аппендит». Аналог для `verifyStep`.

## P2. Вложенные `<system-summary>` при компакции — высокий

**Аргументы (доказательства):**
- В истории прямо видны вложенности: `<system-summary>[Compressed: 18 old turns removed] ... [Errors: <system-summary>...]</system-summary>`, и блок `Errors:` содержит предыдущие сводки целиком, повторяя один и тот же `TS5112` многократно. Компакция срабатывала на **17–18 витков за 11 минут** вместо 15-ти по интервалу — контекст раздувался квадратично.
- Причина в `src/modules/context/manager.ts:extractFacts` (157-209): она сканирует **все** сообщения, включая сами сообщения-сводки (`role: "user"` с `<system-summary>`). Из них повторно извлекаются `[Errors: ...Syntax check failed...]`, `[Decisions: Plan: ...]`, `Written ...` и накапливаются в факты → следующая сводка содержит предыдущую.

**Решение:**
1. В `extractFacts` **пропускать** сообщения, у которых `role === "user"` и контент начинается с `<system-summary>` (или добавлен `onCompact`-флаг).
2. Ввести **дедупликацию** фактов (Set по нормализованной строке).
3. Жёстко ограничить суммарную длину `compactedBlock` (например 1200 токенов) и обрезать факты (`slice` уже есть — оставить, но добавить общий лимит).
4. Опционально: не хранить `fileFacts` из сводок — только из «живых» tool-сообщений.

**Тесты:** в `tests/context-manager.test.ts` — два цикла `addMessage`+`compact`, затем assert: вторая сводка **не содержит** `<system-summary>` внутри текста и не дублирует факты из первой.

## P3. План/todo: вводящее в заблуждение сообщение и застрявший план — средний-высокий

**Аргументы (доказательства):**
- `plan update` без `step` (сессия, 21:06:07) вернул «Неизвестное действие плана: update» — потому что в `src/modules/execution/module.ts:136` ветка требует `args.step`, а без него код падает до `unknown_action` (158-161). Модель получила неверную диагностику.
- План застрял на **1/3**: шаги 2 и 3 так и не закрылись, хотя агент 4 раза заявил «готово». `advancePlanIfStepComplete` (module.ts:361-375) работает **только если** в описании шага есть пути с расширением (`stepPaths.length === 0` → return). У шагов «Создать каталог…», «Реализовать корзину» расширений нет → авто-продвижение никогда не срабатывает.
- `todo` хранит подзадачи в `currentStep.note` (module.ts:185-196), из-за чего чеклист плана показывал шаг 1 как `[x] 1. … — Создать каталог…, Реализовать корзину` (todo-список влез в note). А `todo done` (198-203) ничего реально не отмечает.

**Решение:**
1. Явная ветка `action === "update"` без `step` → понятное сообщение «plan.update_requires_step» (новая i18n-строка в en/ru).
2. В `onAfterTool` (module.ts:302-313): если после успешного `write_file`/`edit_file` у текущего шага **нет** файловых путей — добавлять user-сообщение-подсказку «Step N не имеет проверяемых артефактов — явно отметь его: plan update step=N status=done». Это учит модель закрывать шаг вручную.
3. Разделить todo и note: todo ведёт отдельный список подзадач текущего шага, а не пишет в `step.note`; либо вообще не рендерить `note` в чеклисте `PlanCreator.toPromptBlock` (planner.ts:48-49).
4. (Опционально) `plan update step=N status=done` должен также `advance()` к следующему шагу, а не оставлять current на месте.

**Тесты:** unit для plan-handler: `update` без `step` → корректная ошибка; `advancePlanIfStepComplete` с путями и без; `toPromptBlock` не содержит note после `todo add`.

## P4. Bash: 16 SECURITY BLOCK + кодировка Windows — средний

**Аргументы (доказательства):**
- Модель трижды подряд повторяла один и тот же заблокированный оператор (`&&`, `|`, `;`, `&`) — сообщение блока (bash.ts:63) не подсказывает альтернативу, поэтому модель не адаптируется.
- Вывод cmd в cp866 рендерился моибейком («Ошибка в синтаксисе команды.» → `�訡�� � ᨭ⠪��`), потому что `runner.ts:94-103` декодит чанки как UTF-8.
- Внутренние `grep`-попытки через системный grep падали («grep не является командой»).

**Решение:**
1. В сообщение `[SECURITY BLOCKED]` добавить подсказку (через `t()`): «Используй отдельную команду без операторов, или тулы grep/glob/read_file/process_list».
2. Кодировка: в `runCommand` (runner.ts) на win32 запускать `cmd.exe` с префиксом `chcp 65001 >nul & …` (инжектировать **после** валидации, в runner, чтобы не триггерить security-валидатор). Оставить `killTree` через taskkill. Декодирование UTF-8 останется корректным.
3. grep fallback: в `grep-tool.ts:45` на win32 заменить `grep -rn` на `findstr /s` (или не делать fallback вовсе — rg обязателен на Windows).

**Тесты:** e2e-прогон bash-тула с русским выводом на win32 → без моибейка; unit для формата сообщения блока (содержит подсказку).

## P5. Преждевременные «Задача выполнена ✅» и финальный аудит — средний

**Аргументы (доказательства):** агент объявил завершение 4 раза при плане 1/3. `runFinalAudit` (module.ts:49-73) существует, но нужно убедиться, что он реально срабатывает на финальный ответ при неполном плане, и что pending-шаги попадают в вывод модели.

**Решение:**
1. Проверить связку `agent.ts` → `runFinalAudit`: при `passed: false` гарантированно инжектить `<system-summary>` с `pendingSteps` (уже есть код в agent.ts:642-645 — проверить, что он не подавляется).
2. Усилить системный промпт плана: «Не объявляй задачу выполненной, пока в чеклисте есть `[ ]`/`[*]`». Это снимает и P3-симптом повторных «готово».

**Тесты:** unit аудита: план с pending-шагом → `passed:false`, pendingSteps перечислены; интеграционный — мок-ответ без tool_calls с активным планом → аудит-варнинг в контексте.
