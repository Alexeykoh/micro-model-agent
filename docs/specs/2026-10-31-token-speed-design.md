# Скорость генерации токенов в `mma web`

Дата: 2026-10-31 · Статус: принято · Ветка: `feat/token-speed`

## 1. Проблема

В веб-интерфейсе видно общую длительность хода, но не видно, с какой скоростью
модель генерирует токены. Из-за этого нельзя сравнить модели/провайдеров и
непонятно, где теряется время: в префилле, в генерации или в тулах.

Метрика должна отвечать на вопрос «сколько completion-токенов в секунду выдаёт
модель во время декодирования», а не «сколько длится весь ход».

## 2. Метрика

- **Числитель:** completion-токены вызова (текст + reasoning + JSON тул-вызовов),
  как их сообщил провайдер в `usage`. Если usage нет — локальная оценка
  `chars / 4`, результат помечается `≈`.
- **Знаменатель:** `decodeMs` — от **первого контентного чанка** (text,
  reasoning или tool_call) до конца вызова. Префилл, TTFT и паузы на тулы не
  входят.
- **Скорость вызова:** `completionTokens / (decodeMs / 1000)`.
- **Скорость хода:** `Σ completionTokens / Σ decodeMs` по всем LLM-вызовам хода.
- `decodeMs` измеряется монотонно и ограничен снизу 1 мс, чтобы не делить на 0.

### Живое число

Пока идёт генерация, клиент показывает оценку по скользящему окну 1.5 с
(`chars / 4` по `text`), всегда с `≈`. Окно сбрасывается при паузе ≥1.5 с. Как
только поток текста прекратился, число скрывается; точное значение за ход
появляется в чипе после `turn_end`.

### Итог хода

Итоговая скорость — точное среднее по ходу (если все вызовы дали usage) либо
`≈`-смесь (если хотя бы один вызов оценён). Хранится в `UsageSnapshot`, поэтому
переживает перезагрузку вкладки. В тултипе — разбивка: номер вызова, токены,
`decodeMs`, скорость, источник (`api` / оценка).

## 3. Контракт данных

`src/core/types.ts`:

```ts
export interface LlmCallSpeed {
  completionTokens: number;
  decodeMs: number;
  source: "api" | "estimate";
}
export interface LlmSpeedSnapshot {
  completionTokens: number;
  decodeMs: number;
  calls: LlmCallSpeed[];
}
```

- `AgentResult.llmSpeed?: LlmSpeedSnapshot` — агрегат хода.
- `LoopState` зеркалит накопители: `llmSpeedCalls`, `totalLlmDecodeMs`.
- `TokenTracker.logUsage` принимает `decodeMs` и добавляет запись в состояние.
- `SessionLogger.logLlmUsage` получает `decodeMs` (аддитивное поле строки
  `llm_usage`; старые читатели не ломаются).
- `SubagentUsageRecord.decodeMs?: number` — тот же шов `onUsage`, по которому
  живая скорость доходит до веба.
- `UsageSnapshot.llmSpeed?: LlmSpeedSnapshot`; `HostStateSnapshot.llmSpeed?`.
- `captureUsage` переносит `result.llmSpeed` в снимок; `buildHostState` отдаёт
  его клиенту вместе с остальными usage-полями.

## 4. Поток данных

```
loop-llm: первый чанк → firstTokenAt; конец вызова → decodeMs
    → TokenTracker.logUsage(decodeMs) → LoopState.llmSpeedCalls
    → AgentResult.llmSpeed → captureUsage → UsageSnapshot → /api/state
    → клиент: итоговый чип

    (live) SSE text → клиент: скользящее окно → ≈ tok/s в рельсе
```

Живая оценка считается на клиенте из уже существующих `text` SSE; новых
чанковых событий нет.

## 5. UI

- **Рельс активности** (`rail.ts`): новое поле `.speed` в `.rail-l1` после
  времени. Во время генерации — `≈ N tok/s`.
- **Итоговый чип** (`#speedChip` в `.selectors`, `margin-left:auto`): виден после
  хода до следующего старта; `N tok/s` или `≈ N tok/s`. Тултип — разбивка по
  вызовам.
- Пусто/нет данных — элемент скрыт, не `0 tok/s`.
- На узких экранах чип переносится вместе с остальными селекторами; рельс уже
  умеет переносить `.rail-l1`.
- Стиль: dim, без новых глифов; `tok/s` — обычный текст (STYLE.md, quiet by
  default).

## 6. Ошибки и края

- Провайдер не отдал usage → `source: "estimate"`, пометка `≈`.
- Провайдер отдал весь ответ одним чанком: `decodeMs` почти ноль, tok/s
  физически невозможен (тысячи). Такой замер не пишем — лучше нет числа, чем
  ложь. Порог правдоподобия — 1000 ток/с.
- Прерванный ход → показываем накопленное, без домыслов.
- `decodeMs = 0` или нет вызовов → поля нет, чип скрыт.
- Оценка не должна «разгоняться» на простое: окно живёт только при свежих
  чанках, пауза ≥1.5 с его очищает.

## 7. Проверки

- `tests/core/token-speed.test.ts`: `decodeMs` считается от первого чанка,
  агрегат хода = Σ токенов / Σ decode; fallback даёт `estimate`; `logLlmUsage`
  содержит `decodeMs`.
- `tests/webui-speed-dom.test.ts`: живое окно сбрасывается на паузе; чип
  форматирует точное/оценочное значение; тултип содержит разбивку.
- `tests/webui-assets.test.ts`: `#speedChip` и `.speed` присутствуют; `speed.js`
  подключён к SSE.
- `bun run quality` остаётся зелёным.

## 8. Вне рамок

- Скорость префилла/TTFT отдельными метриками.
- Графики скорости по ходу.
- Скорость субагентов (их `llm_usage` уже несёт `decodeMs`, но UI не трогаем).
