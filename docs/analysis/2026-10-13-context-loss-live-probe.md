# Потеря смысла в контексте: живой прогон на `qwen/qwen3.5-9b`

**Дата:** 2026-10-13 · **Ветка:** `docs/architecture-v2` (изоляция, коммитов в код нет)
**Модель:** `qwen/qwen3.5-9b`, LM Studio `localhost:1234/v1`, `loaded_context_length: 34048`
**Конфиг:** `contextWindow: 32768`, `contextAuto: false`, `compactionThreshold: 0.75`

Стенд: `_testing/live/ctx-probe/` — своя `MMA_CONFIG_DIR`, свой рабочий каталог, корпус
из 5000-строчного отчёта с закладками на известных глубинах + 6 файлов шума.
Реальный `~/.mma` не тронут.

## 1. Короткий ответ на исходный страх

Страх подтверждён, причём по трём разным механизмам, и все три сработали
независимо. Хуже всего — третий: **агент не просто «забывает», он честно
сообщает, что не помнит, и перекладывает работу на пользователя.**

Дословно из прогона A, после четырёх компакций:

> I do not have the actual content of those file reads in my current context.
> The system summary shows which files were accessed, but not their contents.

Агент прочитал нужную строку на **шаге 1**, до четырёх компакций, и к финалу не
мог её воспроизвести. Задание специально запрещало перечитывать файл — проверялась
именно память, а не доступ к файлу.

## 3. Находки

### F1 — критично: реактивная компакция не может сработать для LM Studio

**Где:** `src/llm/openai-compat.ts:614-618` и `src/core/agent/loop-llm.ts:224-229`

LM Studio сообщает о переполнении **посреди стрима**. Транспорт бросает:

```ts
if (st.midStreamError) {
  throw new Error(t("error.llm_provider_stream_error", { ... }));   // голый Error
}
```

Агент реагирует на context-length ошибку только так:

```ts
if (err instanceof LlmError && err.recoverable && err.kind === "context_length" && ...)
```

`Error` — не `LlmError`, условие ложно, реактивная компакция **не выполняется
никогда**. Сессия умирает на том запросе, ради которого страховка и написана.

Косвенное подтверждение, что классификатор regex здесь ни при чём — он текст
узнаёт: `context (?:length|window|size)` матчит «available context size»
(`openai-compat.ts:41`). Проверку теряет именно **обёртка ошибки**.

Путь «400 до старта стрима» (`openai-compat.ts:427-436`) сделан правильно:
`new LlmError(..., { terminal: true, recoverable: true, kind })`. Расходится
именно mid-stream ветка.

**Доказательство (сценарий B):**
```
request (48017 tokens) exceeds the available context size (34048 tokens)
⟡ qwen/qwen3.5-9b · lmstudio · 21.5s   ← сессия прервана
```

**Покрытие тестами:** нет. Есть тест, что mid-stream ошибка не проглатывается
(`tests/openai-compat.test.ts:1184`), и что она классифицируется как
transient/infra (`tests/modules/execution/transient-error.test.ts`) — но не про
связку «mid-stream context-length → реактивная компакция».

### F2 — критично: один вызов `read_file` вгоняет в контекст 5× окна

**Где:** `src/tools/read-file.ts:93` (`boundedOutput: true`) + `src/core/agent/tool-output.ts:18-41`

`toolOutputCharLimit()` для bounded-тулов возвращает `Number.MAX_SAFE_INTEGER` —
сознательный отказ от усечения. Но `read_file` лимитирован только моделью:
`DEFAULT_LIMIT = 300`, `MAX_READ_LIMIT = 2000` строк.

Взвешенная строка отчёта ≈ 143 символа, значит `limit=2000` ≈ 286K символов
≈ ~98K токенов за один вызов в окно 32 768.

**Доказательство (сценарий B), динамика истории:**

| ход | история по подсчёту MMA | к окну 32 768 |
|---|---|---|
| 1 | 195 | — |
| 2 | 35 945 | ×1.1 |
| 3 | 107 449 | ×3.3 |
| 4 | **179 096** | **×5.3** |
| 5 | 178 965 | после «aggressive» |

Реальный счёт провайдера на пике: **48 017 токенов** при `n_ctx: 34048`.
То есть переполнение настоящее, и агент его допустил.

Побочно: модель в этом прогоне сказала «The file was truncated at line 2000»
и продолжила читать с выдуманного `offset 4001` — то есть и маркер усечения
она читает как «файл кончается», а не как «читай дальше».

### F3 — высоко: компакция не может сократить контекст с большими tool-results

**Где:** `src/core/agent/compaction.ts:15-17`

```ts
computeMinReduction = Math.max(floor(hist * 0.02), floor(ctx * 0.03))
```

Порог сокращения **пропорционален завышенной оценке**. Чем больше оценка, тем
больше требуемое сокращение — то есть чем хуже ситуация, тем слабее реакция.
Плюс `keepLastN = 6` последних сообщений неприкосновенны: если они и есть
тяжёлые чтения, компьютер физически не может ужать контекст.

**Доказательство (сценарий B):**
```
it=5 reason=overflow (186723 > 24577) strategy=aggressive
     tokens 206723->173085 (reducedBy 33638)  messages 10->8
```
Сократили 16% от 186K — и продолжили с 173K, то есть в 5.3× выше бюджета.

### F4 — высоко: саммари компакции физически не может удержать смысл файла

**Где:** `src/core/context/manager.ts:680-726` (`buildCompactionBlock`)

Саммари истории **полностью детерминированное, модель в нём не участвует**
(LLM-саммари есть только для system-prompt overflow). Из содержимого файлов
в него попадает:

- `[Files/Deleted/Read/Decisions/Errors]` — факты, извлечённые regex'ами по
  служебным строкам (`fact-extractor.ts`);
- `[Tool ledger]` — **максимум 12 записей, по 120 символов, только первая
  строка результата**.

Первая строка результата `read_file` — это заголовок `── path (.md, N lines, lines 1-2000)`.
То есть саммари фиксирует **факт прочтения** и **полностью выбрасывает
прочитанное**.

Отсюда наблюдение агента из сценария A — он диагностировал механизм верно.

`compact()` при этом удерживает `[Task]` (первые 400 символов промпта) — это
единственное, что спасает: помнит, *зачем* он работал. Но не *что* он узнал.

### F5 — средне: учёт токенов расходится с реальностью под нагрузкой

| случай | оценка MMA | реально принял провайдер | расхождение |
|---|---|---|---|
| контрольный (2 чтения) | 10 937 | 13 094 | −16% (норма) |
| сценарий B (пик) | 179 096 | 48 017 | **×3.7 завышение** |
| сценарий A (итерация 18) | 67 849 | ~8 053 | **×8.4 завышение** |

Ключевое: LM Studio считает токены **абсолютно** — проверено отдельным запросом
известного размера, и на переполнение отвечает `HTTP 400` с
`n_prompt_tokens: 38274`. Поэтому расхождение — на стороне агента, не провайдера.

Калибратор (`context-calibration.ts`) выходит в `trusted` и «только уменьшает»
оценку, но не сближает её с реальностью: коэффициент схлопывается до 0.14–0.30.
Следствия: пороги смещены, а `computeMinReduction` (F3) считается от завышенной
величины — обе проблемы усиливают друг друга.

Отдельно: в `context`-событии `contextTokens` не совпадает с суммой своих же
компонент (67 849 против 2 197 + 4 098 + 45 060 = 51 657) — есть ещё
неучтённый вклад.

### F6 — средне: защита от повторов не сработала

Сценарий A: **12 вызовов `read_file` с одинаковыми аргументами и одинаковым
результатом.** Stuck-детектор среагировал только на шестой. В `[Tool ledger]`
одни и те же вызовы записаны как `read_file(path, offset, limit)` и
`read_file(path, limit, offset)` — порядок ключей не канонизируется, поэтому
сравнение «идентичных аргументов» их различает.

Сессия A стоила **233 579 токенов** суммарно, при том что реальный контекст ни
разу не превысил 24 644. Четыре лишние компакции + повторы.

## 4a. Существенная поправка: часть находок была спровоцирована самим прогоном

Прогон B задавал условие «Use read_file only (no grep)». Это было сделано, чтобы
измерить навигацию по файлу, а не качество поиска. Результат: 5 ходов, одна
компакция, оценка 179 096 токенов и смерть сессии на
`request (48017 tokens) exceeds the available context size`.

Тот же файл, тот же вопрос, `grep` разрешён (прогон B2):

```
FOUND: quarantine flush interval is 17 hours | audit threshold is 61.5 percent | ТИХИЙ ГРИФОН
CALLS: 3
METHOD: grep search for each PIN_ prefix
```

3 вызова, 11.5 с, 3/3 закладки верно (включая кириллическую), ноль компакций,
пик контекста 6 950 при окне 32 768.

**Вывод: навигация по большому файлу не сломана.** `grep` доступен по умолчанию
(теги `file`, `code`, `research`) и решает задачу. F2 (5× окна за один вызов
`read_file`) остаётся реальным риском, но он достигается только при
последовательном листании — то есть при отказе от более дешёвого инструмента.

Оговорка о честности: в промпте B2 слово `grep` названо явно как вариант, то
есть модель получила подсказку. Нейтральный прогон B3 (инструменты не названы)
проверяет, ведёт ли себя агент так без подсказки.

Прогон B3 — промпт нейтральный, инструменты не названы:

```
FOUND: quarantine flush interval is 17 hours | audit threshold is 61.5 percent | ТИХИЙ ГРИФОН
CALLS: 4
LINES: 2101, 3301, 4401
METHOD: grep for each PIN_ prefix
```

3/3 верно, 0 компакций, качество 85, пик контекста 6 950. **Агент выбирает
`grep` без подсказки** — поведение по умолчанию корректно, правки промпта не
требуются.

**Отменено по итогам B2/B3:** L1 «очерк файла» (навигация не сломана) и
любая правка промпта/состава тулов по умолчанию (агент сам выбирает дешёвый
инструмент).

## 4b. Структура расхода: 96% токенов — это повторные отправки

B3, по ходам:

| ход | prompt | completion |
|---|---|---|
| 1 | 7 493 | 105 |
| 2 | 7 689 | 74 |
| 3 | 7 860 | 92 |
| 4 | 8 041 | 770 |

Итого 32 124 токена, из них сгенерировано моделью **1 041** (3.2%). Остальное —
повторная отправка системного промпта и описаний 25 тулов (~6.3K) на каждом ходу.

Следствие для приоритетов: расход определяется **числом итераций × фиксированными
накладными**, а не размером задачи. Поэтому F1/F3 (лишние итерации и лишние
компакции) бьют по кошельку сильнее, чем содержание. Отсюда и 233 579 в прогоне
A при реальном потолке контекста 24 644.

Практический вывод: уменьшение числа итераций важнее уменьшения объёма чтения.
На 32K с 25 тулами каждый лишний ход стоит ~6.3K токенов.

**Отменённые следствия:**
- L1 «очерк файла» (структура + символы + номера строк) — лечит болезнь,
  которой нет. Не проектируется.
- V7 «поднять окно» — отменён окончательно: несколько файлов по 5000 строк
  дают ~540K токенов при физическом максимуме модели 262K. Настройка окна не
  решает задачу в принципе.

**Что остаётся реальным и подтверждённым:**
- F1 — реактивная компакция не срабатывает для LM Studio (сессия умирает).
  Не зависит от того, каким тулом пользуется модель: любая ошибка переполнения
  убивает сессию.
- F3 — при переполнении компакция не может ужать контекст с тяжёлыми чтениями.
- F5 — учёт завышает в 3.7–8.4× под нагрузкой.
- F6 — защита от повторов не канонизирует ключи аргументов.
- F4 — потеря содержания при компакции. Это единственная находка, отвечающая
  на исходный страх, и она подтверждена **именно прогоном A** (шум в контексте),
  а не прогоном B.

## 5. Варианты исправления (по цене, не по красоте)

Ранжировано по отношению «убрано / потрачено токенов».

**V1. Починить mid-stream контекст (F1) — обязательно, дёшево.**
`openai-compat.ts:614` бросает голый `Error`; заменить на
`LlmError` с `kind: classifyProviderError(text)` и `recoverable: kind === "context_length"`
— симметрично ветке 427-436. Тест: mid-stream SSE с `{"error":{...exceeds context size}}`
→ `compactAdaptive` вызван, сессия продолжается.
*Это превращает падение сессии в её продолжение — самый дешёвый выигрыш в наборе.*

**V2. Ограничить `read_file` бюджетом, а не только `limit` (F2) — обязательно.**
Сейчас бюджетное усечение отключено для bounded-тулов. Нужен предохранитель:
даже при `boundedOutput: true` результат не должен превышать долю оставшегося
бюджета истории, иначе он не помещается в окно физически ни при каком пороге.
Дешёвая промежуточная мера — снизить `MAX_READ_LIMIT` для автономных вызовов,
оставив 2000 только для явного `offset`.
*Требует решения: сколько это стоит в повторных чтениях. Измеряемо — в F6 повторы уже были.*

**V3. Считать `minReduction` от реального usage, а не от оценки (F3 + F5).**
У провайдера есть `usage.promptTokens` из прошлого запроса — он на порядок
ближе к истине, чем оценка по cl100k, именно в том режиме, где оценка врёт.
Опорная точка для `computeMinReduction` должна браться оттуда.

**V4. Разрешить прижимать `keepLastN`, если это тяжёлые tool-results (F3).**
Правило «последние 6 неприкосновенны» не должно пересиливать потолок бюджета:
если последние 6 сами по себе не влезают, надо давить и их.

**V5. Дать компакции сохранять содержание, а не только пути (F4).**
Тут есть развилка по цене:
- дёшево: поднять `TOOL_LEDGER_MAX_ENTRIES` и длину записи — с 12×120 символов
  до, скажем, 30×400. Стоимость — несколько сотен токенов, выигрыш — саммари
  начинает содержать факты, а не метаданные;
- дорого и правильно: пропустить извлечённые факты и «решения» через LLM
  в компакции — но это уже LLM-вызов в горячем пути каждой компакции;
- промежуточно: при чтении большого файла класть в контекст не сырой вывод,
  а выжимку, а сырой результат отдавать в `subagent`/`chunk-query`
  (механизм `chunk-query.ts` для этого уже существует и не используется).

**V6. Канонизировать аргументы в проверке повторов (F6).** Дёшево, чисто,
понятно. Сортировка ключей перед fingerprint'ом.

**V7. Поднять окно, раз LM Studio умеет 262 144 (F2, косвенно).**
`max_context_length` модели — 262 144, загружено 34 048. Это единственная
настройка, которая убирает класс проблем «контекст не влезает» целиком, без
правок кода. Но она лечит следствие: 9B на 128K+ контексте теряет качество
извлечения, и `instructions.summarize` перестанет справляться. Проверять
только замером recall, не «стало ли меньше ошибок».

## 6. Что НЕ проверено

- Сценарий C (длинная реальная сессия) не доведён: прогон A/показывает, что
  стенд упирается в F1–F3 раньше, чем набирается длинная сессия.
- Корневая причина расхождения учёта (F5) не локализована — воспроизведена
  и очерчена, но не объяснена. Гипотеза к проверке: вклад `toolTokens` или
  неучтённые сообщения плюс `estimateMessageTokensCached` с инвалидацией по
  сигнатуре содержимого при мутации `content`.
- Влияние `compactionThreshold` не перебиралось: все прогоны шли на дефолте 0.75.
