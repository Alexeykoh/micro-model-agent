## Особенность проекта, relevant для промпта

MMA — агент для маленьких моделей (класс Qwen3.5-9B, окно 32–64K).
Отсюда жёсткие требования, по которым судился каждый баг ниже:

1. Бюджет — это деньги итераций: системный промпт отъедает 10% окна
   (`contextBudget.systemPrompt`), ошибка учёта на ±30% стоит целого блока.
2. Маленькие модели теряются в строках 300+ символов и в прозе —
   канон `src/core/system-prompt.ts` (шапка файла): короткие `HEADER:`-строки
   ≤120 символов, одна директива на строку.
3. Prefix KV-кеш рвётся любым изменением начала системного сообщения —
   поэтому хвостовые (`tail`) блоки и заморозка карты (`frozenMapBlock`).
4. Модель нельзя заставлять гадать: факты (Bun, shell, LSP, MCP, команды
   проекта) собираются в `src/core/prompt-facts.ts` и обязаны быть
   честными (`unknown`, а не догадка).
5. Fail-open обязан оставлять след в `session.jsonl`, иначе «модуль не нужен»
   неотличим от «модуль сломался».

Цепочка формирования (факт по коду):

```
bootstrap workspace-phase: buildSystemInfo(config, baseDir, profile, collectPromptFacts(...))
  → systemInfoPrompt { critical, essential: true }                                   [статика]
bootstrap modules-phase: buildStaticPromptBlocks = systemInfo + moduleHost.collectPromptBlocks
  − ["indexer","session","skills"] + loadAgentsMdBlocks + plan-reminder          [статика]
bootstrap modules-prompt: dryRunStartupOverflow(статика + skills + map + hidden) [баннер]
agent run (turn-run → session-start):
  lazyPromptBlocks → deps.promptBlocks.push(...)          [мутация навсегда]
  resolvePromptOverflowOnce → promptOverrides + overflowHintBlock (одноразово)
  buildSystemPrompt = статика(overrides) + getDynamicPromptBlocks + pluginBlocks
    + overflowHintBlock → PromptBuilder.build → omittedBlocksNote (второй проход)
iteration-prologue каждой итерации: refreshSystemPrompt() → пересборка + updateSystemPrompt
```

## Найденные баги

### B1. Стартовый dry-run считает не тот набор блоков, что реальная сборка — high

**Статус:** ✅ исправлено — `buildStartupAuditBlocks` (единый синхронный набор) + тест паритета

Где: `src/core/bootstrap/modules-prompt.ts:79-98` (`dryRunStartupOverflow`)
против `src/core/agent/prompt-phase.ts:46-118` (`buildSystemPrompt`).

Dry-run складывает `promptBlocks + skills.getPromptBlocks() + indexer.map +
hiddenTools`, а реальная сборка добавляет сверху ещё: session-блок,
model-блок (`ACTIVE MODEL`), capabilities-блок плагинов, `pluginManager
.runOnBuildPrompt()`, lazy health-check-блок, `overflowHintBlock`.
Итог: баннер «сколько не влезло» врёт в обе стороны — ложная тревога
или, хуже, тишина при реальной обрезке. Для 9B-модели это потерянный
первый ход: она не получает честного `overflowHint`.

Рекомендация: dry-run обязан вызывать ту же функцию, что и сборка
(передать `getDynamicPromptBlocks` + `lazyPromptBlocks` + пустые
plugin/overflow-добавки как параметры), а не дублировать набор вручную.
Гейт: тест `tests/arch/` — «набор dry-run ≡ набор первого build»,
сравнение по `label+source`.

### B2. Два разных счётчика токенов в одном бюджете — high

**Статус:** ✅ исправлено — один `estimateTokens` во всём промпт-тракте, `countTokens` только у провайдера

Где: `src/core/agent/prompt-phase.ts:89` (`countTokens` провайдера для
plugin-блоков), `src/core/agent/prompt-phase.ts:61` (там же для
`service-job`), против `estimateTokens` везде в `PromptBuilder`,
`prompt-facts`, `skills/catalog`, `indexer/module`.

`estimateTokens` заявляет точность ±30% (`src/llm/token-counter.ts:7-13`).
При бюджете 10% от 32K (3200 токенов) ошибка — до ~1000 токенов, т.е.
целый блок каталога скиллов или половина карты. Приоритизация
(`PRIORITY_ORDER`) и решение «влез/не влез» принимаются по одной линейке,
а `/sysprompt` и фактический `llmProvider.countTokens` показывают другую.
Наблюдаемый симптом класса: «влез по estimate, порвал окно по факту».

Рекомендация: один источник правды на сборку. Вариант минимум —
всё через `estimateTokens`, а `getSystemPromptInfo` помечать как
приблизительный; вариант правильно — `PromptBuilder` принимает
`counter: (s: string) => number` и в проде получает `llmProvider.countTokens`,
в тестах — `estimateTokens`. Зафиксировать в гейте допустимое
расхождение.

### B3. Essential-блоки рвут бюджет молча — high

**Статус:** ✅ исправлено — `essentialTokens`/`essentialOverBudget` + warn с конкретным фиксом

Где: `src/core/prompt-builder.ts:148` (`fits = essential || ...`).

`systemInfoPrompt` — `critical + essential: true`
(`src/core/bootstrap/workspace-phase.ts:189-196`), `overflowHintBlock` и
`omittedBlocksNote` — тоже `essential: true`. Любой из них влезает всегда,
бюджет не проверяется, варнинга нет. Если раздуты AGENTS.md/карта/скиллы,
страдает не система, а история (ей остаётся `window − system − reserve`),
причём без записи «система превысила бюджет». Для малой модели это худший
обмен: инструкции целы, а контекста хода нет.

Рекомендация: гейт «сумма essential ≤ systemBudget», иначе — явный
`system_over_budget` в лог сессии + `overflowHint` пользователю
(поднять окно/долю, как в `src/core/prompt-overflow.ts:113-136`).
`omittedBlocksNote`/`overflowHintBlock` учитывать в бюджете честно
(см. B4).

### B4. Hint-блоки занижают свой вес и добавляются вне бюджета — medium

**Статус:** ✅ исправлено — вес hint-блока = `estimateTokens(content)`; `omittedBlocksNote` получает остаток бюджета и режется до одной строки (или опускается), если не влезает

Где: `src/core/prompt-overflow-resolve.ts:245-267`
(`estimatedTokens: HINT_BLOCK_TOKENS` — константа 60),
`src/core/agent/prompt-phase.ts:97-116` (второй проход `build()`).

Реальный текст hint-блока (`[Instructions note] ...` + строки по каждому
`warning` + `Read the full AGENTS.md ...`) легко длиннее 60 токенов при
2–3 сжатых блоках. Учёт идёт по константе, а не по `estimateTokens(content)`.
Плюс `omittedBlocksNote` (`essential: true`) добавляется вторым проходом
поверх уже собранного промпта — бюджет проверяется только для
не-essential, т.е. note проходит всегда.

Рекомендация: `estimatedTokens: estimateTokens(content)` для обоих
hint-блоков; во втором проходе проверять `used + note ≤ budget`, при
превышении — резать `excluded`-перечень (`+N more`), а не историю.
Тест: сборка с переполнением → `sum(included) ≤ budget` всегда.

### B5. Model-блок в раннере заморожен на конфиге спавна — medium

**Статус:** ✅ исправлено — модель читается из живого `configRef` (main и раннер)

Где: `src/core/bootstrap/session-runner-scope.ts:237-238`
(`model: input.config.model`) и `src/core/bootstrap/modules-prompt.ts:138`
(`model: input.config.model`).

Комментарий в `src/core/system-prompt.ts:19-28` требует: идентичность
переживает `/model use`. Замыкание берёт `input.config` — снимок момента
спауна/бутстрапа, а живой конфиг — `configRef.current` (см.
`src/core/bootstrap/session-phase.ts:202`). Если `reconfigure` заменяет
объект, а не мутирует in place, динамический блок врёт про модель до
рестарта. Именно такое расхождение уже наблюдалось (`ses_mv44qabg`).

Рекомендация: передавать в оба `buildRunnerDynamicBlocks` /
`collectDynamicPromptBlocks` геттер `() => configRef.current.model`
(или сам `configRef`), а не строку. Гейт: тест «смена модели →
`buildSystemPrompt` содержит новую» для main и раннера.

### B6. Половина фактов собирается, но не используется; часть — ложная — high

**Статус:** ✅ исправлено — `lsp.hasServer` честный, трёхвариантный VERIFY; `languages` заполняются (large)

Где: `src/core/prompt-facts.ts:147-183` (`collectPromptFacts`) против
`src/core/system-prompt.ts:75-229` (`buildSystemInfo`).

- `lsp: { enabled, hasServer: lspEnabled }` (`prompt-facts.ts:177`, `:217`) —
  `hasServer` всегда равен `enabled`. Реального наличия сервера нет.
  Промпт говорит «вызови `lsp_check`», сервера нет — 9B-модель жжёт
  1–2 итерации впустую.
- `mcp.connected` всегда `[]` (`:176`), хотя модуль MCP знает состояние.
  Модель не различает «сконфигурировано» и «подключено».
- `project.languages` всегда `[]` (`:174`), поле мёртвое.
- `platform`/`shell` собираются, но в текст не попадают вообще —
  мёртвый код или недоговорённая спека.

Рекомендация: либо убрать мёртвые поля (честно зафиксировать, что
промпт их не потребляет), либо дописать: `hasServer` — из реального
состояния LSP-модуля, `connected` — из MCP-модуля, `languages` — из
индексатора (у него есть разбивка по языкам, `mapInfo()`). Минимум:
`hasServer: false` по умолчанию + явный `unknown`, а не `enabled`.

### B7. `fallbackPromptFacts` угадывает платформу по строке профиля — low

**Статус:** ✅ исправлено — платформа из `process.platform`, не из строки профиля

Где: `src/core/prompt-facts.ts:190-204`.

Эвристика `profile.includes("win32"/"darwin"/"linux")` классифицирует
машину по тексту пользовательского профиля. Плюс `shell` выводится из
платформы, а не из реального исполнителя тула `bash`. На Windows
(cmd.exe против Git Bash) модель может получить неверные инструкции
по экранированию/путям.

Рекомендация: в фолбэке использовать `process.platform` напрямую
(как делает `detectPlatform` для `envReport`), а shell — из той же
таблицы, что продовый путь (`win32 → cmd`, иначе `sh`), с пометкой
источника в комментарии.

### B8. Усечение по `CHARS_PER_TOKEN=4` врёт на кириллице — medium

**Статус:** ✅ исправлено — итеративное усечение с проверкой `estimateTokens` + тест на кириллице

Где: `src/core/prompt-overflow-resolve.ts:15-16,87-94` против
`src/llm/token-counter.ts:14-34` и комментария в том же файле `:163-164`.

Сам файл признаёт: кириллица — ~2.5 символа/токен, цель надо считать
по 3. Но `truncateToTokens` режет по 4. Русскоязычный AGENTS.md
(основной язык репозитория) после «усечения до maxTokens» реально весит
в ~1.6 раза больше — бюджет рвётся именно на русском тексте.

Рекомендация: считать `maxChars` через `estimateTokens`-обратную
функцию (итеративно: резать → `estimateTokens` → докрутить) вместо
фиксированного делителя. Тест на кириллическом корпусе:
`estimateTokens(truncate(s)) ≤ maxTokens`.

### B9. Кэш суммаризаций инвалидируется бюджетом и слеп к модели — medium

**Статус:** ✅ исправлено — ключ кэша с моделью, sibling-reuse при смене бюджета

Где: `src/core/prompt-overflow-resolve.ts:30-32`
(`cacheKey = sha(kind|content|maxTokens)`).

- Любая смена `contextWindow`/`systemPrompt`-доли меняет `maxTokens` →
  весь дисковый кэш (`projectMmaDir/.mma/cache/prompt-summaries`) мимо,
  перед первым ходом — повторная LLM-суммаризация (видимое «зависание»
  старта, про которое предупреждает комментарий `:127-132`).
- Ключ не содержит идентификатора модели-суммаризатора: смена модели
  переиспользует чужую выжимку (стиль/качество различаются, для 9B —
  критично).

Рекомендация: ключ `kind|content|model|profile-бюджета` (доля, а не
абсолют), либо двухуровневый кэш: `sha(content|model)` + проверка
`tokens ≤ maxTokens` с докомпрессией без полного пересчёта.
Плюс TTL/лимит размера каталога кэша (сейчас — рост без bound).

### B10. `collectText` с `maxTokens*2` опасен для малых окон — medium

**Статус:** ✅ исправлено — `capCompletion` под окно контекста

Где: `src/core/prompt-overflow-resolve.ts:66-85,152,177-194`.

Запас `*2` «оценки эвристичны» при окне 8K и цели 2K просит у провайдера
4K генерации + вход (полный AGENTS.md + инструкции) — сам вызов
суммаризации может не влезть/упасть и уйти в `truncate` без попытки
меньшего куска. Ретрай один, затем жёсткий clamp — конкретные факты
(пути, команды), которые комментарий `:166` требует сохранять, могут
быть потеряны молча.

Рекомендация: cap запроса `min(maxTokens*2, window − input − reserve)`,
при недоступности окна — сразу `truncate`; ретрай с понижением цели
(`maxTokens → maxTokens/2`), а не один. Варнинг обязан содержать
`mode` (уже есть) + факт «суммаризация не сохранила N% конкретики» —
сейчас не измеряется.

### B11. Resume-раннер строит system без overflow-резолва и lazy-блоков — medium

**Статус:** ✅ исправлено — резолв переполнения на resume-пути + refresh

Где: `src/core/agent/surface.ts:105-118` (`setContext`) против
`src/core/agent/session-start.ts:36-96` (`ensureSessionStart`).

`seedRunnerHistory` (`session-runner-wiring.ts:243-254`) зовёт

Рекомендация: в `setContext` принимать уже резолвнутые overrides/hint

порядок в `ensureSessionStart` (lazy → overflow → build) сделать единой

### B12. Legacy-режим `filterBlocksForTags` показывает инструкции к несуществующим тулам — medium

**Статус:** ✅ исправлено — гейт по реально видимым тегам схемы (allowlist-aware)

Пустой `activeTags` = «все тулы», фильтр no-op. Но блок с

набору (`toolExecutor.getToolDefinitions(tags)`): блок с `requiresTags`
показываем, только если хотя бы один тег даёт хотя бы один видимый тул.
Пустой набор при `enableOnDemand: true` — тоже осознанное состояние,
а не legacy.

## Сопоставление с крупными моделями

Агент обязан работать и с крупными моделями (хостед-провайдеры
`openai` / `openrouter` / `opencode-zen/go`, окна 128K–1M против
дефолтных 32768 в `src/config/defaults.ts:91`). При переходе
32K → 200K+ бюджет 10% превращается из тисков (3.2K) в ангар (20K+):
набор B1–B20 не отменяется, но меняет знак. Ниже — переоценка каждого
пункта и новые баги, видимые только на большом окне.

### Переоценка B1–B20 на большом окне

| Баг | На малой (32K) | На крупной (200K–1M) | Вывод |
| --- | --- | --- | --- |
| B1 dry-run ≠ сборка | ложная тишина, потерянный ход | почти всегда «влезло», баннер молчит и прав | латентный: проснётся на монорепо, где и 20K мало; чинить всё равно (единая функция) |
| B2 два счётчика | ±1000 ток = целый блок | относительная ошибка та же ±30%, абсолютная — до ±6K; headroom маскирует, но счёт за токены и триггеры компакции едут | чинить в первую очередь: на больших деньгах ошибка дороже |
| B3 essential рвёт бюджет | худший обмен (история съедена) | никогда не срабатывает — нарушение спрятано до возврата на малую модель | добавить гейт сейчас, иначе «работает на GPT, падает на Qwen» |
| B4 вес hint-блоков | занижение на сотни токенов | не видно (блоков почти нет), но `/sysprompt` врёт одинаково | чинить вместе с B2 |
| B5 model-блок раннера | путаница провайдеров (кейс ses_mv44qabg) | та же путаница + цена: большая модель в биллинге чужой | чинить независимо от класса |
| B6 мёртвые/ложные факты | лишние итерации `lsp_check`, слепота к MCP | ущерб больше: большая модель реально умеет в 50 параллельных тулов, LSP-символы и MCP — а ей не говорят что подключено; `languages: []` и выкинутые `platform/shell` — недоиспользование | на large чинить расширением (дать больше правды), а не урезанием |
| B7 фолбэк платформы | неверный shell на Windows | то же + большие модели пишут сложные shell-цепочки, где ошибка экранирования дороже | чинить одинаково |
| B8 truncate на кириллице | разрыв бюджета в 1.6 раза | путь почти недостижим (влезает и так) — баг спит | тест на кириллицу всё равно нужен (монорепо разбудит) |
| B9 кэш по maxTokens | повторная суммаризация при смене бюджета | то же при переключении small↔large (окна разные — кэш мимо каждый раз) | добавить модель и профиль в ключ (см. L-фиксы) |
| B10 `maxTokens*2` | упрётся в окно 8K | безопасно по окну, но расточительно: суммаризация 40K генерации ради блока 20K | cap по окну нужен обоим классам |
| B11 resume без резолва | скачок system, рвётся кеш | окно большое — скачок незаметен, но prefix-cache крупного провайдера (платный cache-write) сбрасывается так же | чинить одинаково |
| B12 legacy-фильтр | галлюцинаторные вызовы | большая модель реже галлюцинирует, но при 100+ тулах лишний блок инструкций — шум, съедающий платный кеш | инверсия: на large лучше показать больше тулов, а не фильтровать |
| B13 model-блок low | вылетает первым | не вылетает (места много) — но при раздутом проекте вылетит так же | `normal` дёшево для всех |
| B14 stale-статика | врёт baseline до рестарта | врёт дольше (сессии больших моделей живут дольше, правок больше) | чинить одинаково |
| B15 `PRIORITY_ORDER` без фолбэка | случайный выброс блока | то же при монорепо; плюс длинные строки: большая модель длинные строки переваривает, но канон ≤120 — общий | фолбэк всем; лимит строк — оставить (дешёвый и большим не вредит) |
| B16/B17 без инвалидации | stale-сжатие | при переключении small↔large сжатие, посчитанное под чужое окно, — либо мусор (сжали то, что влезало), либо овербюджет | хранить `resolvedBudget+hashes`, пересчитывать при смене окна |
| B18 серверное время | ошибка 3–10 ч | та же; большие модели лучше в арифметике дат, но планировщик веба врёт всем | чинить одинаково |
| B19 два пути скиллов | расхождение приоритетов | то же | унифицировать |
| B20 service-job | нет security, другой счётчик | job на большой модели чаще с тулами — отсутствие security-строки жжёт платные вызовы | чинить в первую очередь для large |

Итог переоценки: ни один пункт не «отменяется» большим окном; B6, B12,
B20 меняют знак (на large вредят сильнее или инвертируются), остальные
уходят в латентность и возвращаются при смене модели назад или росте
проекта.

### L1. Потолок рекомендаций 262144 — large-модели занижены — medium

### L2. Фиксированные лимиты контента не масштабируются с окном — medium

**Статус:** ✅ исправлено — scale-aware карта/каталог + cap тел скиллов

Где: `src/config/defaults.ts:171` (`mapTokenBudget: 1500`),
