# MMA Enterprise: идея, а не спека

**micro-models-agent (далее — MMA)** — это программа, которая даёт языковой модели
память, инструменты и правила. На ноутбуке одного разработчика она уже работает.

**MMA Enterprise** — это тот же продукт, но в организации: с пользователями,
ролями, политиками, аудитом, лимитами и поддержкой.

Эта идея описывает картину простыми словами: что это, зачем, кто что делает, в
каком порядке и как это развернуть. Сначала — самое простое. Термины и сокращения
появляются постепенно и расшифровываются при первом упоминании.

---

## 1. Если коротко

MMA помогает человеку работать с моделью и своими данными: читать файлы, искать,
считать, писать, проверять. Но личный инструмент и инструмент компании — разные
вещи.

В компании появляется:

- **много людей** с разными правами;
- **данные**, которые нельзя отдавать всем;
- **журнал**, где видно, кто что сделал;
- **бюджет**, который нельзя превысить;
- **регламент**, что делать при сбое.

Поэтому enterprise — это не версия программы. Это режим, в котором MMA становится
частью инфраструктуры.

Что меняется:

| Кто           | Что получает                                      |
| ------------- | ------------------------------------------------- |
| Компания      | контроль над данными, ролями, бюджетом и аудитом  |
| Администратор | одно место для настройки людей, правил и агентов  |
| Сотрудник     | понятный вход, клиент, свои лимиты и статистику   |
| Безопасник    | политику, журнал и возможность остановить агента  |
| Разработчик   | программный интерфейс для своего портала или бота |

Дальше — по порядку: сначала зачем это нужно и кто что делает, потом устройство и
развёртывание.

---

## 2. Зачем это нужно

У компании обычно три боли.

| Кто           | Что болит                                                    | Что даёт MMA Enterprise                                |
| ------------- | ------------------------------------------------------------ | ------------------------------------------------------ |
| Компания      | Люди пользуются личными ИИ-чатами, данные уходят наружу      | Свой контур, защита от утечек и журнал                 |
| Администратор | Общие токены, нет ролей, нет лимитов, непонятно, кто виноват | Пользователи, группы, роли, квоты, аудит               |
| Сотрудник     | Непонятно, где скачать, что можно и почему закончился лимит  | Личный кабинет, установка, статистика, понятные ошибки |

### Что именно защищаем

- **секреты**: ключи, пароли, токены;
- **персональные данные** (Personally Identifiable Information, далее — PII);
- **файлы компании**: договоры, финансы, кадры;
- **доступ к моделям**: какая модель, куда уходят данные;
- **бюджет**: сколько токенов и денег потрачено.

Для этого в MMA уже есть **защита от утечек** (Data Loss Prevention, далее — DLP):
она классифицирует данные, маскирует чувствительное и блокирует запрещённое.

### Что появляется в enterprise

- вход через компанию;
- роли и группы;
- политика, которая приходит с сервера;
- журнал действий (далее — **аудит**);
- лимиты на человека и отдел;
- агенты, которые создаёт компания;
- свои правила обновления.

## 3. Кто есть кто

Сначала — люди и их роли. Это проще, чем устройство сервера.

**Рабочее пространство** (далее — **workspace**) — это отдел или проект. Например,
`Finance`, `Engineering`, `Support`. Внутри свои люди, агенты, лимиты и данные.

**Агент** — заранее настроенный помощник: инструкция, навыки, инструменты, модель и
правила. Сотрудник не собирает агента с нуля, а выбирает готового.

**Политика** — правила: что можно, что нельзя, что маскировать, что требует
подтверждения.

| Роль              | Простыми словами                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| `org_admin`       | Главный администратор компании: люди, отделы, глобальные правила                                          |
| `security_admin`  | Безопасник: политика, DLP, инциденты, аудит                                                               |
| `workspace_admin` | Администратор отдела: люди и лимиты своего workspace                                                      |
| `builder`         | Создаёт агентов, инструкции и навыки                                                                      |
| `user`            | Обычный сотрудник                                                                                         |
| `auditor`         | Смотрит аудит и экспортирует отчёты, ничего не меняет                                                     |
| `service`         | Бот или интеграция; работает через программный интерфейс (Application Programming Interface, далее — API) |
| `agent`           | Сам агент; получает права только на время задачи                                                          |
| `guest`           | Временный гость с ограниченным доступом                                                                   |

Роли не складываются автоматически. Если человеку нужны две роли, их выдают явно.
Один человек может быть и сотрудником, и администратором отдела, но это две
отдельные записи.

## 4. День пользователя

Так выглядит обычный сотрудник.

### Утро

1. Открывает `https://mma.corp`.
2. Нажимает «Войти через компанию».
3. Проходит вход в корпоративном **Identity Provider** (далее — **IdP**) — системе,
   которая подтверждает, кто он.
4. Если настроен **единый вход** (Single Sign-On, далее — **SSO**), пароль второй
   раз вводить не нужно.
5. Подтверждает вход через **многофакторную аутентификацию** (Multi-Factor
   Authentication, далее — **MFA**), если компания её требует.
6. Видит чат и список доступных агентов.

Вход в браузере обычно идёт по протоколу **OpenID Connect** (далее — **OIDC**).
Если компания использует другой протокол, это не меняет картину для пользователя.

### Личный кабинет

Страница `https://mma.corp/me` — это **личный кабинет**. Там видно:

- свой аккаунт и workspace;
- остаток лимита и статистику;
- доступных агентов;
- свои устройства;
- установку клиента;
- свои действия в аудите.

Это не чат и не админка. Только свои данные.

### Клиент на компьютере

Сотрудник скачивает клиент из личного кабинета. Клиент — это **интерфейс командной
строки** (Command Line Interface, далее — **CLI**): программа, с которой работают
из терминала.

```bash
mma login --server https://mma.corp
mma chat --workspace engineering
```

При первом запуске клиент спрашивает:

- **подключиться к компании** — тогда настройки, агенты и политика приходят с
  сервера;
- **работать локально** — тогда это личный режим, без данных компании.

На корпоративном устройстве локальный режим может быть запрещён.

### Что пользователь может

- задать вопрос;
- приложить файл, если разрешено;
- попросить агента прочитать документ;
- выбрать агента из списка;
- посмотреть свои лимиты и статистику;
- отозвать своё устройство.

### Что пользователь не может

- выбрать чужой workspace;
- вызвать инструмент, который ему не выдан;
- отправить запрещённые данные наружу;
- посмотреть чужой аудит;
- изменить политику безопасности.

## 5. День администратора

Администратор начинает не с чата, а с панели управления.

### Утро

1. Открывает `https://mma.corp/admin`.
2. Проверяет здоровье сервиса.
3. Смотрит алерты: ошибки, очередь, входы, файловые шары.
4. Проверяет, что обещание по доступности (Service Level Objective, далее —
   **SLO**) не нарушено.
5. Смотрит, доходят ли события до системы событий безопасности (Security
   Information and Event Management, далее — **SIEM**).

### В течение дня

- добавляет нового сотрудника;
- увольняет сотрудника и отзывает доступ;
- создаёт workspace;
- публикует политику;
- создаёт агента;
- подключает файловую шару;
- подтверждает опасные действия;
- разбирает инцидент.

### Чего администратор не делает

- не читает чужие промпты без аварийного доступа;
- не меняет себе роль;
- не совмещает изменение политики и деплой в одном лице;
- не правит рабочий конфиг руками на сервере;
- не передаёт токены в чат или тикет.

---

## 6. Порядок действий

Это быстрый маршрут. Детали — в следующих разделах.

### Компания

1. Выделить сервер или кластер.
2. Подготовить сеть, систему имён (Domain Name System, далее — DNS) и сертификаты
   защищённого соединения (Transport Layer Security, далее — TLS).
3. Подготовить IdP и группы.
4. Подготовить базу данных, объектное хранилище, хранилище секретов.
5. Подготовить внутренний registry для образов.
6. Настроить backup и мониторинг.
7. Согласовать, какие данные можно обрабатывать.

### Администратор

1. Получить и проверить релиз MMA.
2. Загрузить образы во внутренний registry.
3. Развернуть управляющий слой и исполнитель.
4. Подключить IdP.
5. Создать workspace.
6. Настроить роли и группы.
7. Опубликовать политику.
8. Создать первого агента.
9. Подключить файловую шару.
10. Включить мониторинг и backup.

### Пользователь

1. Зайти в личный кабинет.
2. Скачать клиент.
3. Войти через компанию.
4. Выбрать workspace и агента.
5. Работать в рамках лимита.
6. Смотреть свои лимиты и устройства.

### Проверка

- вход работает;
- отзыв пользователя работает;
- агент отвечает;
- файлы видны только тем, кому можно;
- лимит считается;
- аудит пишется;
- backup восстанавливается.

## 7. Что такое MMA Enterprise

Это тот же продукт, но вокруг ядра появляются управляющие сервисы. Их пять.

| Часть                                              | Простыми словами                                                                             | Что не делает                        |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------ |
| **Точка входа** (далее — **ingress**)              | Дверь: TLS, вход через компанию, маршрутизация                                               | Не решает, что можно данным          |
| **Управляющий слой** (далее — **control plane**)   | Диспетчерская: люди, роли, политика, лимиты, агенты, аудит                                   | Не читает файлы и не вызывает модель |
| **Исполнитель** (далее — **runtime**)              | Делает работу: агент, инструменты, DLP                                                       | Не хранит пользователей и правила    |
| **Шлюз к моделям** (далее — **model gateway**)     | Одна точка доступа к моделям, бюджету и резерву                                              | Не применяет политику данных         |
| **Брокер доступа** (далее — **credential broker**) | Выдаёт короткий пропуск к файловой шаре или серверу Model Context Protocol (далее — **MCP**) | Не решает, что разрешено             |

Плюс данные: база, объектное хранилище, хранилище секретов, журнал аудита.

### Control plane — это не модуль агента

Control plane — отдельный сервис. Он не живёт внутри runtime и не является
подключаемым модулем. Он отвечает на вопросы:

- кто этот человек;
- что ему можно;
- сколько ему можно;
- какие агенты доступны;
- кто и что менял.

Runtime спрашивает у control plane правила и применяет их. Если control plane
недоступен, runtime не работает «по старым правилам» бесконечно: у политики есть
срок жизни (Time To Live, далее — **TTL**), после которого изменения запрещаются.

### Три веб-страницы

| Адрес                    | Что это           | Кому                           |
| ------------------------ | ----------------- | ------------------------------ |
| `https://mma.corp/`      | Чат               | всем пользователям             |
| `https://mma.corp/me`    | Личный кабинет    | каждому пользователю           |
| `https://mma.corp/admin` | Панель управления | администраторам и безопасникам |

`/me` и `/admin` — один control plane, но разные права. Пользователь не видит
админку. Администратор не видит чужой личный кабинет без причины.

## 8. Как это поставляется

### Один релиз, несколько контейнеров

«Поставлять вместе» не значит «сложить всё в один контейнер». Это значит:

- один номер версии;
- один набор образов;
- один установочный сценарий;
- но разные процессы.

Как GitLab: один продукт, а внутри несколько сервисов. Как Kubernetes: один
дистрибутив, а управляющий слой и исполнитель — разные процессы.

Это **не форк и не вторая кодовая база**. Ядро одно; enterprise добавляет сервисы
вокруг него.

### Три варианта поставки

| Вариант                                         | Где работает    | Кому подходит                                                             |
| ----------------------------------------------- | --------------- | ------------------------------------------------------------------------- |
| **Docker-набор**                                | один сервер     | пилот, филиал, небольшая компания, изолированный контур                   |
| **Kubernetes + Helm**                           | кластер         | production, отказоустойчивость, несколько отделов                         |
| **Windows + Active Directory** (далее — **AD**) | серверы Windows | компания, где всё построено вокруг AD, файловых шар и веб-сервера Windows |

Docker-набор — это архив с готовыми образами, файлом `docker-compose.yml`,
скриптами установки и обновления. Kubernetes-вариант — Helm-чарт. Windows-вариант —
установщик Windows и службы Windows.

### Что такое HA и почему одного Docker мало

**Высокая доступность** (High Availability, далее — **HA**) — это когда сервис
продолжает работать при отказе отдельного компонента: сервера, диска, сети,
процесса или базы.

Это не «контейнер перезапустился» и не backup. Для HA нужны 2+ экземпляра,
балансировщик, реплика базы, общее хранилище и автоматический переход на живую
копию.

| Понятие                                | От чего защищает                                          |
| -------------------------------------- | --------------------------------------------------------- |
| **HA**                                 | От отказа компонента: упал сервер, под, диск              |
| **Backup**                             | От потери данных: удалили, испортили, вирус               |
| **Disaster Recovery** (далее — **DR**) | От катастрофы: потеря центра обработки данных или региона |
| **Масштабирование**                    | От нагрузки: больше пользователей                         |

HA не возвращает удалённые данные. Backup не спасает от падения сервера за секунду.
Поэтому HA, backup и DR нужны вместе.

Docker-набор на одном сервере — это не HA: один сервер, один диск, одна база.

### Что не надо делать

Не надо делать один огромный контейнер, внутри которого `supervisord` поднимает
control plane, runtime, базу и Keycloak. Это удобно на демо и плохо в жизни:

- падение одного процесса роняет всё;
- нельзя обновить политику, не трогая runtime;
- нельзя масштабировать;
- секреты и база в одном месте;
- сложно делать backup;
- сложно объяснить безопаснику, где граница.

Контейнер — это упаковка. Архитектура — это разделение ответственности.

## 9. Как развернуть

Ниже — путь для Docker-набора. Для Kubernetes шаги те же, но команды другие.

### Путь целиком

| #   | Шаг                                                                                                                                                                                              | Кто делает             |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------- |
| 1   | Подготовить сервер, DNS, TLS, сеть, синхронизацию времени (Network Time Protocol, далее — NTP), Postgres, объектное хранилище (Amazon S3-совместимое, далее — S3), Vault, registry, backup, SIEM | Организация            |
| 2   | Получить подписанный релиз MMA, проверить подписи и `sha256`                                                                                                                                     | Организация            |
| 3   | Загрузить образы во внутренний registry (Harbor/Nexus)                                                                                                                                           | Организация            |
| 4   | Создать namespace, секреты и bootstrap-конфиг                                                                                                                                                    | Организация + MMA      |
| 5   | Прогнать миграции базы                                                                                                                                                                           | MMA                    |
| 6   | Развернуть control plane                                                                                                                                                                         | MMA                    |
| 7   | Развернуть runtime                                                                                                                                                                               | MMA                    |
| 8   | Развернуть model gateway и credential broker                                                                                                                                                     | MMA                    |
| 9   | Настроить маршруты ingress на `/`, `/me`, `/admin`, `/v1`                                                                                                                                        | Организация + MMA      |
| 10  | Зайти в `/admin`: IdP, группы, роли, workspace, лимиты, политика, агенты                                                                                                                         | MMA                    |
| 11  | Пользователь заходит в `/me`, ставит клиент и логинится                                                                                                                                          | Пользователь           |
| 12  | Клиент получает политику и агентов с сервера                                                                                                                                                     | MMA                    |
| 13  | Свой портал или бот подключается к `/v1`                                                                                                                                                         | Интеграция организации |

### Откуда берутся компоненты

Компоненты не скачиваются с GitHub на рабочий сервер. Администратор получает
**подписанный релиз MMA Enterprise**:

```text
mma-enterprise-0.24.0/
├── images/          # control-plane, runtime, gateway, broker
├── charts/          # Helm-чарт
├── compose/         # docker-compose.yml
├── installers/      # MSI/DEB/RPM для клиентов
├── manifests/       # версии, digest, совместимость
├── sbom/            # состав
└── signatures/      # подписи
```

Состав поставки описывается в **перечне компонентов** (Software Bill of Materials,
далее — **SBOM**). Это нужно, чтобы безопасник видел, из чего собран продукт.

Дальше администратор:

1. Проверяет подписи и `sha256`.
2. Загружает образы во **внутренний registry** (Harbor/Nexus) или локально через
   `docker load`.
3. Берёт Helm-чарт или `docker-compose.yml` из того же релиза.
4. Задаёт начальные параметры: база, объектное хранилище, Vault, IdP, ingress.

| Компонент               | Что это                          | Откуда берётся                                         | Чем запускается                        |
| ----------------------- | -------------------------------- | ------------------------------------------------------ | -------------------------------------- |
| **ingress**             | вход, TLS, OIDC                  | обычно уже есть у организации; иначе nginx/traefik/ARR | Helm/Ingress или IIS                   |
| **control plane**       | админка, роли, политика, лимиты  | образ `mma/control-plane` из релиза                    | Deployment, Compose или служба Windows |
| **runtime**             | агент, инструменты, DLP          | образ `mma/runtime` из релиза                          | Deployment, Compose или служба         |
| **model gateway**       | доступ к моделям, бюджет         | образ `mma/model-gateway` или внешний LiteLLM          | Deployment/Compose                     |
| **credential broker**   | короткие пропуска к файлам и MCP | образ `mma/credential-broker` из релиза                | Deployment/Compose                     |
| **Postgres, S3, Vault** | данные и секреты                 | ресурсы организации                                    | managed-сервис или оператор            |

Ingress — не обязательно новый компонент MMA. Часто это уже существующий
корпоративный reverse proxy, которому добавляют маршруты на control plane и runtime.

### Порядок развёртывания

```text
1. Postgres, S3/MinIO, Vault, registry
2. namespace, секреты, bootstrap-конфиг
3. миграции базы
4. control plane
5. runtime
6. model gateway
7. credential broker
8. маршруты ingress
9. health-check и первый вход в /admin
```

В Docker-наборе это делает `./install.sh`. В Kubernetes — Helm-чарт и Job миграций.
В Windows — MSI и службы.

### Что должно быть готово

- сервер: 8 процессоров, 16 ГБ памяти, 200 ГБ диска (для пилота);
- Docker и Docker Compose;
- DNS-имя, например `mma.corp`;
- TLS-сертификат от внутреннего удостоверяющего центра;
- IdP: Entra ID, Keycloak или AD Federation Services (далее — AD FS);
- группа `MMA-Admins` в IdP;
- почта или контакт ответственного.

Если локальная модель — нужна видеокарта и драйверы.

### Шаг 1. Проверить пакет

```bash
./verify.sh
```

Скрипт проверяет:

- `sha256` образов;
- подпись;
- наличие всех файлов;
- версию.

Если подпись не сходится — не устанавливать.

### Шаг 2. Заполнить `.env`

```env
MMA_HOST=mma.corp
MMA_TLS_CERT=/etc/mma/tls/tls.crt
MMA_TLS_KEY=/etc/mma/tls/tls.key
MMA_DB_PASSWORD=...
MMA_ADMIN_EMAIL=admin@corp.example
MMA_IDP_ISSUER=https://idp.corp.example/realms/corp
MMA_IDP_CLIENT_ID=mma-web
MMA_IDP_CLIENT_SECRET=...
```

Секреты не коммитить. Для пилота можно `.env` с правами `0600`, для production —
Vault или Docker secrets.

### Шаг 3. Установить

```bash
./install.sh
```

Скрипт:

1. загружает образы из `images/`;
2. создаёт volumes;
3. поднимает Postgres и MinIO;
4. прогоняет миграции;
5. поднимает control plane;
6. поднимает runtime;
7. поднимает model gateway и credential broker;
8. ждёт `/healthz` и `/readyz`;
9. печатает URL.

### Шаг 4. Открыть админку

```text
https://mma.corp/admin
```

Вход — через IdP. Если админки нет, значит группа `MMA-Admins` не замаплена на
роль `org_admin`.

### Шаг 5. Подключить IdP

В админке:

1. Identity → Provider.
2. Указать issuer, client_id, secret.
3. Group mapping:

```text
MMA-Admins      → org_admin
MMA-Security    → security_admin
MMA-Audit       → auditor
MMA-Finance     → user
MMA-Contractors → user (ограниченный)
```

4. Включить автоматическую синхронизацию пользователей.
5. Проверить: войти тестовым пользователем, отключить его в IdP, убедиться, что
   сессия умерла.

### Шаг 6. Создать workspace

Workspace — это отдел или проект.

```text
Finance
  лимит: 1 000 $/мес
  класс данных: confidential
  агенты: reporting, contracts
```

### Шаг 7. Опубликовать политику

Начать лучше с простого:

```yaml
defaults:
  external_egress: deny
  unknown_data_class: mask
```

Потом добавить правила:

- `restricted` никогда не уходит наружу;
- `confidential` — только с маской;
- запись файлов — с подтверждением;
- аудитор не вызывает инструменты.

Первую неделю — режим предупреждений, потом — строгий режим.

### Шаг 8. Создать агента

1. Взять шаблон.
2. Описать инструкцию.
3. Выдать инструменты по возможностям, а не по именам.
4. Выбрать модель.
5. Привязать политику.
6. Запустить в тестовом workspace.
7. Опубликовать.

### Шаг 9. Подключить файловую шару

Об этом ниже, в разделе про Samba. Коротко: сначала права в AD, потом режим
«от имени пользователя», потом проверка двумя группами.

### Шаг 10. Поставить клиентов

- браузер — просто URL;
- CLI — установщик из внутреннего registry;
- агент — подписанный пакет настроек из control plane.

### Шаг 11. Включить мониторинг

Prometheus, Grafana, OTel, SIEM. Об этом ниже.

```bash
curl -fsS https://mma.corp/metrics | head
```

И вручную:

## 10. Клиент и первый запуск

### Установка клиента

Внутренний сервер раздаёт:

- Windows: **Windows Installer** (далее — **MSI**);
- Linux: **Debian package** (далее — **DEB**) или **RPM Package Manager** (далее —
  **RPM**);
- macOS: PKG, если нужно.

Ссылку, версию и checksum удобнее брать в личном кабинете `https://mma.corp/me` —
он сам определит операционную систему.

Установка:

```powershell
msiexec /i mma-cli-0.24.0.msi
```

или

```bash
sudo apt install ./mma-cli_0.24.0_amd64.deb
```

Внутри уже есть:

- CLI;
- доверенный корневой сертификат;
- адрес сервера;
- минимальная версия.

### Первый запуск: enterprise или локально

При первом запуске клиент спрашивает одно: **как вы хотите работать?**

```text
┌─────────────────────────────────────────────┐
│  Добро пожаловать в MMA                     │
│                                             │
│  [ Подключиться к компании ]                │
│    Данные компании, политики, аудит,        │
│    поддержка, обновления от компании.       │
│                                             │
│  [ Работать локально ]                      │
│    Личный режим. Без доступа к серверам     │
│    компании и без корпоративных данных.     │
└─────────────────────────────────────────────┘
```

|                 | Enterprise                                | Локально               |
| --------------- | ----------------------------------------- | ---------------------- |
| Сервер          | control plane компании                    | нет                    |
| Вход            | SSO через IdP                             | нет                    |
| Модель          | company gateway или локальная по политике | своя                   |
| Политика        | с сервера, изменить нельзя                | своя                   |
| Данные компании | по правам                                 | нет доступа            |
| Аудит           | в компанию                                | только локально        |
| Файловые шары   | по правам доступа                         | только локальные файлы |
| Обновления      | кольца компании                           | пользователь сам       |
| Поддержка       | компания                                  | сообщество             |

Что происходит после выбора:

**Enterprise:**

1. Пользователь вводит адрес сервера или он уже в установщике.
2. Открывается браузер, вход через IdP.
3. CLI получает токен и политику.
4. Появляются workspace и агенты.

**Локально:**

1. Пользователь выбирает провайдера и модель.
2. Проверяет, что модель отвечает.
3. Работает со своими файлами.
4. Никакие данные не уходят в компанию.

Когда выбор не показывают:

- клиент поставлен компанией через MSI, Group Policy Object (далее — GPO) или
  Intune — режим enterprise уже включён;
- в политике стоит запрет локального режима;
- устройство регулируемое — локальный режим запрещён.

Переключение режима:

- **local → enterprise**: можно через `mma login`; локальные настройки остаются
  в отдельном профиле.
- **enterprise → local**: только если компания разрешила; токены и кэш очищаются,
  корпоративные данные не остаются.
- если политика запрещает локальный режим, кнопки «локально» нет.

Важно не путать две разные вещи:

| Ось         | Значения           | Что значит                                    |
| ----------- | ------------------ | --------------------------------------------- |
| Подключение | enterprise / local | есть ли сервер компании                       |
| Исполнение  | thin / hybrid      | где выполняются инструменты, если сервер есть |

«Локально» — это не «гибридный режим». Гибридный клиент всё равно подключён к
компании и получает её политику.

### Первый вход в enterprise-режиме

```bash
mma login --server https://mma.corp
```

CLI показывает код и ссылку. Пользователь открывает ссылку в браузере, входит через
IdP, подтверждает код. Токен сохраняется в системном хранилище паролей, не в файле
конфигурации.

Ту же команду и код можно получить в личном кабинете `/me`.

### Откуда берётся агент

```text
CLI → control plane: какие агенты доступны?
control plane → CLI: список + версия + digest
CLI → control plane: дай пакет настроек агента
control plane → CLI: подписанный пакет
CLI → проверяет подпись и TTL
CLI → сохраняет в локальный кэш
```

Агент — это не бинарник, а описание: инструкция, навыки, инструменты, модель,
политика. Он подписан и версионирован.

### Какие настройки приходят с сервера

Главное правило: **пользователь не настраивает безопасность. Он получает её с
сервера.**

Три группы настроек:

| Что                  | Кто меняет                                | Примеры                                                                                               |
| -------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Безопасность и права | только control plane                      | политика, инструменты, модели, лимиты, DLP, подтверждения, аудит, доступ к файлам, минимальная версия |
| Личные предпочтения  | пользователь                              | тема, язык, размер шрифта, уведомления                                                                |
| Подключение          | пользователь или администратор устройства | адрес сервера, прокси, папка кэша; прав не даёт                                                       |

Что нельзя переопределить флагом CLI:

```text
--model
--allow-tool / --deny-tool
--no-dlp
--policy
--quota
```

Если такой флаг передан, клиент либо игнорирует его, либо завершается с понятной
ошибкой. Настройки безопасности не лежат в файле конфигурации пользователя.
Переменные окружения тоже не должны отключать управляемую политику.

Как это работает:

```text
1. mma login --server https://mma.corp
2. CLI → GET /v1/me            — кто я, какие workspace доступны
3. CLI → GET /v1/policy        — политика для workspace
4. Сервер → версия, TTL, подпись, правила
5. CLI проверяет подпись
6. CLI применяет: инструменты, модели, лимиты, DLP, подтверждения
7. Каждый вызов инструмента проходит через локальную проверку
8. Критичные действия всё равно проверяются на сервере
```

Пример ответа сервера (условно):

```yaml
managed: true
version: 7
ttl: 3600
workspace: engineering
tools:
  allow: [read_file, glob, grep]
  deny: [bash, web_fetch]
models:
  allow: [local-qwen]
  external: false
limits:
  tokens_per_day: 200000
  cost_per_month: 50
dlp:
  mode: enforce
audit:
  endpoint: https://mma.corp/v1/events
signature: ed25519:...
```

Что если пользователь попробует обойти:

- **Поменял локальный кэш** → подпись не сходится → клиент переходит в режим
  только чтения или отказывает; событие о попытке уходит в аудит.
- **Истёк TTL политики** → изменения запрещены; продлить TTL локально нельзя.
- **Подменил ответ сервера** → подпись не сходится; клиент не доверяет.
- **Соврал серверу** → в тонком режиме инструменты вообще не на клиенте; в
  гибридном сервер выдаёт короткий пропуск на конкретное действие и проверяет его.
- **Запустил старую версию** → сервер требует минимальную версию и отзывает доступ.

Важная оговорка: если у пользователя есть права администратора на его машине, он
может пропатчить клиент. Абсолютно запретить это нельзя. Поэтому для чувствительных
данных:

- включают **тонкий режим** без локальных инструментов;
- политику и DLP применяют **на сервере**, а не только в клиенте;
- используют управление устройствами, подпись кода и шифрование диска;
- выдают короткоживущие токены и отзывают их;
- замечают попытки вмешательства и реагируют.

Администратор видит по каждому клиенту:

- версию клиента;
- версию применённой политики;
- время последней связи;
- события о вмешательстве или оффлайне;
- право отозвать доступ или потребовать обновление.

Компания также может запретить гибридный режим для конкретного workspace. Тогда
`mma chat --workspace engineering` работает только как тонкий клиент.

### Что если интернета нет

- внутренняя сеть есть → работает как обычно;
- control plane недоступен → работает последний валидный пакет до истечения TTL;
- политика устарела → изменения запрещены, чат может работать только на чтение;
- совсем нет сети → локальная модель, если разрешена, и явный статус «оффлайн».

Никакого «тихого» переключения на внешнюю модель.

### Обновление клиента

- внутренний registry;
- подпись и `sha256`;
- кольца: canary → early → all;
- откат на предыдущую версию;
- минимальная версия на стороне сервера.

## 11. Роли, группы и лимиты

### Два способа дать права

- **Управление доступом на основе ролей** (Role-Based Access Control, далее —
  **RBAC**): человек получает роль, роль получает набор возможностей.
- **Управление доступом на основе атрибутов** (Attribute-Based Access Control,
  далее — **ABAC**): учитываются отдел, класс данных, время, устройство, TTL.

В MMA работают оба: роль задаёт базу, атрибуты сужают.

### Роли

| Роль              | Что может                                                 |
| ----------------- | --------------------------------------------------------- |
| `org_admin`       | Всё управление компанией, кроме чтения чужого содержимого |
| `security_admin`  | Политика, DLP, инциденты, аудит                           |
| `workspace_admin` | Люди и лимиты своего workspace                            |
| `builder`         | Агенты, инструкции, навыки                                |
| `user`            | Чат и работа с разрешёнными агентами                      |
| `auditor`         | Чтение аудита и экспорт                                   |
| `service`         | API по выданным правам                                    |
| `agent`           | Только на время задачи                                    |
| `guest`           | Временный доступ с TTL                                    |

Роли не складываются автоматически. Если человеку нужны две роли, их выдают явно.

### Группы

Обычно роли не назначают по одному. Их берут из групп компании:

```text
Группа компании     → роль MMA
MMA-Admins          → org_admin
MMA-Security        → security_admin
MMA-Audit           → auditor
MMA-Finance-Users   → user (workspace finance)
MMA-Contractors     → user (ограниченный профиль)
```

Правило: не маппить группу «все пользователи». Иначе доступ получат все.

### Лимиты

Лимиты можно ставить на человека, группу, отдел и компанию.

```text
Пользователь:
  токенов в день: 200 000
  денег в месяц: 50 $
  одновременных задач: 2

Workspace "Finance":
  токенов в месяц: 5 000 000
  денег в месяц: 1 000 $
  инструменты: чтение, поиск, запись с подтверждением
  внешние модели: запрещены

Группа "Contractors":
  токенов в день: 20 000
  инструменты: нет
  файлы: нет
  внешние модели: нет
```

Что происходит при исчерпании:

- предупредить;
- перевести на меньшую или локальную модель;
- заблокировать до следующего периода.

Каждое решение пишется в аудит.

### Кто что может

| Действие                | Сотрудник        | Подрядчик | Гость | Админ отдела     | Безопасник | Аудитор |
| ----------------------- | ---------------- | --------- | ----- | ---------------- | ---------- | ------- |
| Чат с локальной моделью | да               | да        | да    | да               | да         | нет     |
| Чат с внешней моделью   | с маской         | нет       | нет   | с маской         | с маской   | нет     |
| Читать файлы            | да               | по выдаче | нет   | да               | да         | нет     |
| Писать файлы            | с подтверждением | нет       | нет   | с подтверждением | нет        | нет     |
| Менять политику         | нет              | нет       | нет   | нет              | да         | нет     |
| Смотреть аудит          | нет              | нет       | нет   | свой отдел       | да         | да      |
| Деплой                  | нет              | нет       | нет   | нет              | нет        | нет     |

## 12. Миграция групп из AD

**Active Directory** — каталог пользователей и групп в Windows.
**System for Cross-domain Identity Management** (далее — **SCIM**) — способ
автоматически передавать пользователей и группы из IdP в MMA.

Миграция — отдельная задача. Делать её лучше по шагам.

### Шаг 1. Инвентаризация

Выгрузить:

- группы безопасности;
- членов групп;
- вложенные группы;
- владельцев групп;
- какие группы реально используются.

Не брать всё подряд. В AD часто есть группы «для старых прав», «для теста»,
«для отпуска».

### Шаг 2. Сопоставление

| Группа AD       | Роль MMA       | Workspace | Дополнительные права | Комментарий          |
| --------------- | -------------- | --------- | -------------------- | -------------------- |
| MMA-Admins      | org_admin      | —         | все админские        | 3 человека           |
| MMA-Security    | security_admin | —         | политика, аудит      | 5 человек            |
| MMA-Finance     | user           | finance   | —                    | 40 человек           |
| MMA-Contractors | user           | support   | —                    | ограниченный профиль |
| MMA-Audit       | auditor        | —         | только чтение        | 2 человека           |

Правила:

- одна группа — одна понятная роль;
- большие группы — отдельное обсуждение;
- вложенные группы сначала развернуть;
- группу «все пользователи» не трогать.

### Шаг 3. Пилот

Взять одну группу, например `MMA-Finance`.

- включить синхронизацию;
- проверить, что люди появились;
- проверить, что роли совпали;
- проверить, что чужие отделы не видны;
- проверить увольнение.

### Шаг 4. Параллельный режим

Некоторое время AD остаётся источником прав, а MMA только читает.

```text
Группа AD → синхронизация → роль MMA
```

Если что-то не так — правится маппинг, а не люди вручную.

### Шаг 5. Переключение

Когда пилот стабилен:

- включить все группы;
- отключить ручные исключения;
- включить SCIM для увольнений;
- проверить ушедших сотрудников.

### Шаг 6. Откат

Если что-то сломалось:

- вернуть предыдущий маппинг;
- отключить синхронизацию;
- не удалять пользователей сразу;
- зафиксировать инцидент в аудите.

### Грабли

- **Вложенные группы.** Лучше развернуть до миграции.
- **Большие группы.** Список групп в токене раздувается и режется.
- **Одинаковые имена.** `MMA-Admins` в разных доменах — разные группы.
- **Переименование.** Если группа переименована, маппинг ломается. Нужен алерт.
- **Удаление.** Если группу удалили в AD, люди не должны остаться с правами.
- **Гости.** Отдельная группа и отдельный TTL.

## 13. Интеграции

Все интеграции идут по стандартным протоколам. Это важно: не нужно писать
отдельный коннектор под каждый продукт. В таблице используются HTTP (Hypertext
Transfer Protocol), HTTPS (HTTP over TLS) и JSON (JavaScript Object Notation).

| Класс                | Что подключается                                                                                               | Протокол                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |

### 13.1. Вход и пользователи

Что настроить:

1. OIDC- или SAML-приложение в IdP.
2. Redirect URL на `https://mma.corp/auth/callback`.
3. Группы в токене.
4. SCIM или синхронизацию.
5. MFA и условный доступ на стороне IdP.

Что проверять:

- вход работает;
- отзыв пользователя закрывает сессию;
- смена группы меняет роль;
- уволенный не может войти и вызвать инструмент.

### 13.2. Kerberos и файловые шары

Главное правило: **права даёт файловый сервер, а не MMA**. Список доступа (access
control list, далее — **ACL**) настраивается в AD и на шаре.

Два режима:

**От имени пользователя** (On-Behalf-Of, далее — **OBO**):

- пользователь входит через IdP;
- сервер получает Kerberos-пропуск на пользователя;
- монтирует только его шары;
- в журнале файлового сервера виден пользователь;
- отзыв в AD действует сразу.

**Сервисная учётка:**

- у workspace своя учётка;
- монтируются только разрешённые шары;
- у каждой сессии свой namespace;
- в аудите виден человек, но в журнале шары — учётка.

Для OBO нужны:

- **Kerberos Constrained Delegation** (далее — **KCD**) или
  **Resource-Based Constrained Delegation** (далее — **RBCD**);
- **Service Principal Name** (далее — **SPN**) для сервиса;
- **Key Distribution Center** (далее — **KDC**) и синхронизация времени;
- **Advanced Encryption Standard** (далее — **AES**), не устаревший RC4;
- отключённый **New Technology LAN Manager** (далее — **NTLM**), если возможно;
- keytab на Linux или group Managed Service Account (далее — gMSA) на Windows.

Пример монтирования:

```bash
mount -t cifs //fs01/finance /run/mma/sessions/<id>/finance \
  -o vers=3.1.1,sec=krb5i,multiuser,cruid=<uid>,ro
```

Проверка:

- группа А видит шару AA;
- группа Б не видит AA;
- после удаления из группы доступ пропадает;
- ссылка на чужую шару не работает.

### 13.3. Модели

Два варианта:

- **внешний провайдер** через model gateway; ключи в Vault; allowlist моделей;
- **локальная модель** (vLLM, Ollama, llama.cpp) в контуре; видеокарта и драйверы.

Model gateway нужен, чтобы:

- был один список разрешённых моделей;
- считались токены и деньги;
- был резерв при отказе провайдера;
- можно было откатить модель.

### 13.4. Мониторинг

Runtime и control plane отдают `/metrics`. Имена метрик ниже — предложение, а не
текущий контракт.

```yaml
scrape_configs:
  - job_name: mma
    scrape_interval: 15s
    metrics_path: /metrics
    static_configs:
      - targets: ["mma-runtime:8080", "mma-control:8080"]
```

Что смотреть:

- количество ходов и ошибок;
- задержку;
- очередь;
- токены и деньги;
- блокировки DLP;
- отказы политики;
- ошибки входа;
- ошибки файловых шар.

Алерты:

- ошибок больше 5% за 5 минут;
- очередь больше 80% лимита;
- расход бюджета больше 80%;
- всплеск отказов политики;
- разрыв цепочки аудита;
- сертификат истекает через 30 дней;
- файловая шара не монтируется.

**Grafana** подключается к Prometheus как источник данных. Панели:

```text
Обзор:      запросы, ошибки, задержка, очередь, активные сессии
Стоимость:  токены, деньги, стоимость хода, топ отделов
Безопасность: DLP, отказы, ошибки входа, новые адреса
Файлы:      ошибки монтирования, задержка, доступные шары
Инфраструктура: процессор, память, диск, соединения, сертификаты
```

### 13.8. Данные и секреты

| Что       | Для чего                             | Чего не делать                        |
| --------- | ------------------------------------ | ------------------------------------- |
| Postgres  | пользователи, роли, политика, лимиты | не класть на NFS                      |
| S3/MinIO  | артефакты, аудит, backup             | не хранить секреты в открытом виде    |
| NFS       | пользовательские файлы               | не использовать для базы              |
| Vault/KMS | секреты и ключи                      | не хранить ключи в файле конфигурации |

Сроки хранения:

- горячие логи — 90 дней;
- тёплые — год;
- холодные и legal hold — 7 лет;
- удаление — через tombstone и стирание ключа.

Цели восстановления:

- **Recovery Time Objective** (далее — **RTO**) — за сколько восстановиться;
- **Recovery Point Objective** (далее — **RPO**) — сколько данных можно потерять.

8. Записать, чего не хватает.

### Каждый день

- файловые шары;
- подтверждения;

### Каждую неделю

- аудит исключений;
- стоимость;
- отставшие клиенты;
- новые агенты;

### Каждый месяц

- сверка пользователей с IdP;
- проверка восстановления;
- обновление;
- пересмотр политик;
- удаление осиротевших агентов.

### Типовые задачи

| Задача               | Что делать                                                   |
| -------------------- | ------------------------------------------------------------ |
| Новый сотрудник      | группа в AD → синхронизация → роль → тестовый вход           |
| Увольнение           | отключить в IdP → проверить сессию → аудит                   |
| Новый агент          | пакет → инструменты → политика → тест → публикация           |
| Запретить инструмент | убрать возможность или добавить запрет → проверить           |
| Добавить шару        | ACL в AD → брокер или namespace → тест двумя группами        |
| Ротация секрета      | Vault → перезагрузка → проверить старый                      |
| Инцидент             | остановить агента → отозвать токены → снимок → SIEM → разбор |
| Обновление           | backup → canary → SLO → promote или rollback                 |
| Восстановление       | изолированный namespace → restore → проверка цепочки         |

### Чего администратор не делает

- не читает чужие промпты без аварийного доступа;
- не меняет себе роль;
- не совмещает политику и деплой;
- не правит рабочий конфиг руками;
- не передаёт токены;
- не отключает аудит «на время».

## 15. Обновления

### Docker-набор

```bash
./backup.sh
./upgrade.sh 0.25.0
```

`upgrade.sh`:

1. проверяет подпись и checksum;
2. делает backup;
3. загружает новые образы;
4. прогоняет миграции;
5. пересоздаёт контейнеры;
6. ждёт health;
7. при ошибке откатывает предыдущую версию.

### Kubernetes

- canary на один workspace;
- смотреть SLO;
- расширять;
- откат по digest.

### Клиенты

- кольца: canary → early → all;
- подпись;
- откат;
- минимальная версия.

### Агенты и политика

- версия;
- подпись;
- dry-run;
- canary;
- откат.

### Модели

- проверка качества;
- canary;
- alias;
- откат.

### Изолированный контур

**Air-gap** — контур без маршрута в интернет.

- пакет с образами, манифестами, подписями и SBOM;
- проверка на шлюзе;
- импорт во внутренний registry;
- canary;
- откат.

## 16. Что уже есть и чего нет

Честно, без маркетинга.

| Уже есть                           | Чего нет                |
| ---------------------------------- | ----------------------- |
| DLP на границе провайдера          | Control plane           |
| Единая точка контроля инструментов | SSO, SCIM, RBAC         |
| Защита путей                       | `actor` в аудите        |
| Сетевые ограничения                | Цепочка хешей аудита    |
| API сервиса                        | HA и Helm               |
| Веб-интерфейс                      | Подпись обновлений      |
| Обновление с `sha256`              | Postgres и S3           |
| Аудит в файл                       | Лимиты на пользователя  |
| Шифрование сессий (опция)          | OBO и credential broker |
| Строгий профиль                    | Admin UI                |

### Что можно сделать сегодня

Пилот:

- один отдел;
- OIDC на reverse proxy;
- строгий профиль;
- инструменты только на чтение;
- одна шара;
- локальная модель;
- аудит в файл.

### Что нельзя назвать enterprise

- общий токен на всех;
- роли «на словах»;
- аудит без `actor`;
- политика в файле конфигурации;
- один контейнер со всем;
- обновление копированием файлов.

## 18. Одна страница

- Enterprise — это режим, а не версия.
- MMA уже умеет DLP и контроль инструментов.
- Не хватает управления: людей, ролей, политики, аудита, лимитов.
- Control plane — отдельный сервис, не модуль агента.
- Runtime — исполнитель; ingress — дверь; аудит — журнал.
- Поставка: Docker-набор, Kubernetes или Windows/AD.
- «Вместе» = один релиз и один установочный набор, а не один контейнер.
- Пользователь входит через IdP; файлы открываются через Kerberos.
- Личный кабинет `/me`: установка клиента, лимиты, устройства, свои действия.
- Первый запуск: выбрать «компания» или «локально»; на корпоративном устройстве локальный режим можно запретить.
- Агент приходит подписанным пакетом из control plane, не с GitHub.
- Локальный клиент получает политику с сервера и не может её переопределить.
- Если у пользователя права администратора на машине — это отдельный риск; для чувствительных данных нужен тонкий режим.
- Обновление — canary, backup, rollback.
- Сначала пилот, потом production.
- Если что-то нельзя объяснить простыми словами — это ещё не готово.
