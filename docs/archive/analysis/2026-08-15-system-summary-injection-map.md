# Карта `<system-summary>` инъекций в контекст модели

Дата: 2026-08-15. Ветка анализа: `master` (после мержа 0.36.0 рефакторинга).
Тип: **аналитический документ** — база для решения об упрощении контура управления моделью. Код не менялся.

## Проблема в двух словах

Агент общается с моделью не только реальными поворотами пользователя, но и десятками
heuristic-сообщений, которые добавляются как `role: "user"` с обёрткой `<system-summary>`.
Эти сообщения:

- накапливаются между LLM-вызовами (до 6-7 за итерацию в худшем случае),
- дублируют друг друга и содержимое tool-результатов,
- вынуждают харнесс **фильтровать их обратно** при извлечении задачи, фактов, компакции
  (`getTaskText`, `lastUserTask`, `FactExtractor.skip`, фильтр stale `<system-summary>` в `compact()`),
- местами противоречат друг другу и правилу №10 (keyword-matching).

## Механика накопления за итерацию

Цикл итерации N:

```
onBeforeThink (start N):
  flush pendingMessages из onBeforeTool/onAfterTool итерации N-1   → до 3-5 сообщений
  + direct: plan-reminder (#11/#12), stuck recovery (#13), hints (#14), force-skip (#15)
                                                                    → ещё до 3-4
LLM call
tools:
  onBeforeTool → warning (#16) в pendingMessages
  onAfterTool  → forbidden (#18), hints (#19), test-run (#20/21/22) в pendingMessages
               + step-gates (#8/9/10) — DIRECT в contextManager
  tool result (role:"tool") + summaries (#3) — direct
```

Худший случай (Windows, bash грепает не тем, план застрял): **6-7 heuristic-сообщений
перед одним LLM-вызовом**, плюс 2-3 после. Нормальный случай — 2-4.

`pendingMessages` не очищаются между итерациями: если onAfterTool итерации N добавил 3
сообщения, все они выливаются в onBeforeThink итерации N+1; счётчик не сбрасывается.

## Конфликты внутри одной итерации

1. **Force-skip (#15) vs auto-advance (#10).** Итерация N: «STOP. Step 3 занял 10 итераций,
   вызови plan update step=3 done/skipped». Тот же ход: onAfterTool автозавершает шаг 3 →
   «Step 3 auto-completed | current: step 4». Модель видит оба приказа про один шаг.
2. **Stuck recovery (#13) + hints (#14) + hints-on-failure (#19)** — **два** сообщения, не три:
   #13 (recovery+skill+actionable+alt одним блоком) и #14 (getHints). `getActionableHints()`
   (ошибко-специфичный) и `getHints()` (step-keyword) — разные методы с разным содержимым;
   перекрытие только в repetitive-tool / consecutive-failure кейсах.
3. **test-run «не помечай done» (#20) + auto-advance (#10) + final audit (#6)** — три
   независимых системы решают вопрос завершения шага; двойная/тройная избыточность.
   Взаимоисключающие ветки (#20/#21/#22): срабатывает ровно одна за команду — это DRY-выигрыш,
   не runtime-шум.
4. **plan-nagging (#11/#12) vs правило №10 и дизайн.** Модели сказано «модель решает, нужен ли
   план», а харнесс принуждает по счётчику итераций, даже для тривиальной задачи.
5. **Hallucination retry (#4) → empty-response (#5) → audit (#6)** — каскад: три разных
   user-сообщения-погремушки за 3 итерации, каждое в своём формате, все ведут к failure-состоянию.
6. **summaries (#3) дублирует tool-сообщение** — полный вывод уже в `role:"tool"`, #3 повторяет
   head(200) как `role:"user"`. Расход контекста и двойная интерпретация.

## Рекомендуемый рефакторинг (основа решения)

Один **`SystemState`-блок** в начале системного промпта (или одно user-сообщение, **заменяемое**
каждую итерацию, не накапливаемое):

- сводка тулов за итерацию (вместо #3),
- активные предупреждения дедуплицированные (stuck/hints/forbidden/test-run в одно),
- состояние плана и аудита (вместо #16/#17/#21),
- ретраи — через единый счётчик в контуре (вместо 4/5).

Эффект: −80% meta-мусора, исчезают все filter-хакеи (`getTaskText`, `lastUserTask`,
`FactExtractor.skip`, фильтр stale `<system-summary>`), остаются только real user turns и
`role:"tool"` сообщения. Модель перестаёт видеть противоречивые приказы.

## Сопутствующие наблюдения

- **LLMJudge** (`llm-judge.ts`): лишний полный вызов LLM на каждый финальный ответ при наличии
  решений; тот же слабый модель судит сам себя. Предлагается: off по умолчанию, гейт по
  фактическим решениям.
- **Loop** (`agent.ts` 1115 строк): 9 независимых предохранителей в одном методе — отдельный
  рефакторинг (`LoopController`), исключённый из 0.38.1.

## Оценка предложений (2026-08-15, after re-verification)

Вердикты по каждому предложению с аргументами «за» и «против» (двусторонняя проверка по скиллу
code-review: каждое предложение оспорено).

### P1. Убрать #16 plan-alignment (и #17 block)

**За:** regex-матчинг путей хрупок (`\b[\w./\\-]+\.[a-z]+` цепляет `1.2.3`); план уже виден
модели как чеклист в системном промпте; сообщения копятся.

**Против (оспариваю):**
- Это **behavioral enforcement**, не дубликат дисплея. Чеклист — статический текст; `checkPlanAlignment` —
  единственный механизм, который ловит редактирование файла из **другого** шага (реальный failure mode,
  changelog #38 «off-track»).
- **Срабатывает редко**: требует `stepPaths.length > 0 && callPaths.length > 0`; шаг без файловых
  токенов никогда не триггерит. Шум низкий.
- Удалить warning = удалить эскалацию (#17). Модель теряет рубеж против расползания задачи.

**Вердикт: НЕ СТОИТ удалять.** Проблема — хрупкий regex, а не механизм. Починить regex
(переиспользовать `extractFileLikeTokens`), сохранить механизм, перенести в SystemState.

### P2. Убрать #18 forbidden-cmd (модульный)

**За:** «две системы делают одно и то же» — bash.ts уже хард-стопит.

**Против (оспариваю — сильнейший спор):**
- **Разные пороги и каналы**: bash.ts хард-стоп на **3-м** фейле, встраивает STOP **в output тула**;
  модуль — сообщение на **2-м** фейле, user-сообщение **перед следующим вызовом**.
- **Комментарий в `windows-commands.ts:8-11` прямо говорит**: bash.ts «injects "STOP using X" INTO
  the tool output, **which a 9B model tends to ignore**; this one … lands before the next model call».
  Системы спроектированы как **дополняющие**, не дублирующие.
- **Списки команд разные**: `FORBIDDEN_COMMANDS` (grep/sed/ls/find/rm/touch/which/diff/cp/mv) vs
  `UNIX_TO_WIN_HINTS` (шире: head/tail/wc/pwd/chmod/pipes/Get-ChildItem…). Удаление модульного =
  потеря раннего предупреждения для команд вне bash.ts.

**Вердикт: НЕ СТОИТ.** Пометка «полностью избыточно» — **ошибка карты**, исправлена в верификации.

### P3. Слить hints 3→1 (#168+#178+#311)

**За:** три сообщения про одно застревание = шум; перекрытие в repetitive/consecutive-кейсах.

**Против (оспариваю):**
- **Разные моменты**: #13/#14 — onBeforeThink (cooldown-гейт), #19 — onAfterTool (немедленно при
  фейле тула). Разное время = разная цель.
- **Разные генераторы**: `getRecoveryMessage` (что делать со step), `getActionableHints`
  (ошибко-специфичный), `getHints` (ключевые слова шага install/test/build) — **дополняют** в типичном
  step-stuck кейсе.
- Слияние в одно = **гигантское сообщение** (actionable бывает 6+ пунктов); для 9B длинное хуже
  двух коротких по делу.

**Вердикт: ЧАСТИЧНО.** Слить только реальное перекрытие (repetitive/consecutive в двух местах)
в один генератор. Не сваливать все три в одно сообщение.

### P4. summaries (#3) → просто tool-результат

**За:** полный вывод уже в `role:"tool"`; #3 повторяет head(200) — чистый расход контекста.

**Против (оспариваю):**
- **Не все бэкенды отдают tool-сообщения целиком** (llama.cpp с кастомными шаблонами может
  дропать `role:"tool"`); #3 — fallback-диджест для слабо обученных 9B.
- Удаление меняет pairing assistant tool_calls → tool result; риск для бэкендов без поддержки
  `role:"tool"`.
- Выигрыш мал: head(200) × N — тривиальные токены.

**Вердикт: ЧАСТИЧНО.** Сократить до диджеста (имя тула + успех + tail ошибки вместо head output)
или opt-in. Полное удаление — риск без выгоды.

### P5. Единый SystemState-блок (заменяемый, не накапливаемый)

**За:** убирает накопление, filter-хакеи, противоречивые приказы; −80% мусора.

**Против (оспариваю — главный архитектурный спор):**
- **Самая рискованная правка**: 35 сайтов, компакция, экстракция задачи, все модули. Одна ошибка =
  сломанная сессия, а loop-level харнесса нет.
- **Jinja rule #1** (AGENTS.md): system-сообщение обязано быть первым. «Состояние системы» в system =
  пересборка каждую итерацию (`refreshSystemPrompt` уже это делает) — дорого для 9B, ломает KV-cache.
- **Теряется эскалация**: модель должна видеть «warning 1, warning 2, BLOCK»; заменяемый блок хранит
  только последнее состояние.
- **Filter-хакеи не все лишние**: часть про корректность (не путать user-повороты), часть про Jinja.

**Вердикт: ЧАСТИЧНО (направление верное, формулировка нет).** Не «заменяемый блок», а
**дедупликация в рамках итерации** (одно сообщение-сводка за ход вместо 3-6) + вывод эскалационной
последовательности в системный промпт. Полный SystemState — после loop-харнесса.

### P6. LLMJudge off по умолчанию

**За:** лишний полный вызов LLM на каждый финальный ответ; слабый судит слабого; 15s timeout.

**Против (оспариваю):**
- **Fast-path**: `decisions.length === 0` → pass без вызова. Дорого только когда модель реально
  приняла решения — ровно тот случай, когда проверка нужна.
- **Единственный ловитель отката решения** (прежний word-matching убран как хрупкий). Off = потеря
  механизма против «сначала выбрал React, потом Vue».
- **Деградация безопасна**: timeout/ошибка → pass, никогда не блокирует цикл. Уже есть лимиты:
  `MAX_DECISIONS_SHOWN = 6`, `MAX_RESPONSE_CHARS = 2000`.

**Вердикт: НЕ СТОИТ выключать.** Карта преувеличила частоту (вызов только при решениях, что редко).
Правильнее: оставить, сократить timeout (15s → 8s), капнуть decisions.

### P7. Loop → LoopController (agent.ts 1115 строк)

**За:** правило #1 нарушено в худшем месте, god object, 9 предохранителей спутаны.

**Против (оспариваю порядок, не цель):**
- **Каждый предохранитель = реальный зафиксированный failure mode** (changelog 31-38). Убрать/
  перемешать без харнесса = повторить класс багов пост-мортемов.
- **Интеракция тонкая**: `suppressRepetitionRetry` + `emptyResponseRetries` + `auditRetries` +
  `lastModelText` связаны флагами. Рефакторинг без тестов — слепая замена.
- Карта сама фиксировала: «исключён, нет loop-level харнесса».

**Вердикт: СТОИТ, но ТОЛЬКО после loop-level тест-харнесса** (уже зафиксирован как долг).

### P3-частично: единый источник причины застревания в `StuckDetector`

**Что было:** три генератора сообщений про одно застревание с независимой логикой приоритета:
`getRecoveryMessage()` (приоритет stuck → tool-errors → consecutive → repetitive → read-only)
и `getHints()`, который добавлял state-буллеты (repetitive/consecutive/read-only) **поверх**
recovery-сообщения. В cooldown-блоке plugin (`execution-plugin.ts:166-180`) recovery и hints
эмитятся **вместе**, так что при `primary === "repetitive"` модель получала одно и то же
дважды (#13 + дубль в #14) — лишнее user-сообщение.

**Что стало** (`src/modules/execution/stuck-detector.ts`):
- добавлен приватный `getPrimaryReason(): "stuck" | "tool-errors" | "consecutive" | "repetitive" | "read-only" | null` —
  **единственный источник истины** по приоритету причины (тот же порядок, что раньше жил в `getRecoveryMessage`);
- `getRecoveryMessage()` отрефакторирован на его использование (приоритет в одном месте);
- `getHints()` теперь гвардит каждый state-буллет: буллет НЕ выводится, если recovery уже
  покрывает эту причину (`primary !== "repetitive"` / `"consecutive"` / `"read-only"`). Step-keyword
  hints (install/test/build) и подсказка при `primary === "stuck"` (когда read-only — сопутствующее,
  не причина) сохраняются.

**Почему так, а не «слить все 3 в одно»:** вердикт P3 «ЧАСТИЧНО». Три генератора в типичном
step-stuck кейсе дополняют друг друга (`getRecoveryMessage` — что делать с шагом, `getActionableHints`
— ошибко-специфичный, `getHints` — ключевые слова шага); сваливание в одно = гигантское сообщение.
Убран только реальный дубль. `getRecoveryMessage()` не менял сигнатуру — второй вызывающий
`moe-executor.ts:203` (лог ретраев субтаска) не затронут.

**Тесты** (`tests/execution-stuck-detector.test.ts`, блок `StuckDetector hint/recovery dedup (P3)`):
1. recovery покрывает repetitive → `getHints()` не повторяет «calling the same tool repeatedly»;

### P1-починить: `checkPlanAlignment` на общем извлекателе файловых токенов

**Что было** (`src/modules/execution/module.ts`): `checkPlanAlignment` извлекал файлы шага и
аргументов вызова сырым regex `/\b[\w./\\-]+\.[a-z]+/gi`. Он цеплял **не-файлы**:
- домены/URL (`weather.com`, `example.com`) → шаг «fetch weather.com data» получал phantom-путь,
  и любой write к реальному файлу снаружи этого «пути» считался off-path → ложный warning (#16);
- extension-only сегменты (`tsx/.ts` в «остались только .tsx/.ts файлы») → phantom-шаг «tsx/.ts»
  блокировал легитимные правки (это ломал changelog #38 «plan-coverage» из 0.36.0);
- `process.env`, JS member access и т.п.

При этом **тот же** извлекатель уже был в модуле и использовался в трёх местах
(`advancePlanIfStepComplete` ~285, `missingStepDeliverables` ~400, `stillExistingDeliverables` ~411) —
в `checkPlanAlignment` его просто забыли переиспользовать.

**Что стало** (`src/modules/execution/module.ts`): все три извлечения (stepPaths, callPaths,
finishedPaths) переведены на `extractFileLikeTokens(stripUrls(text))` с постфиксом
`.map((p) => p.toLowerCase())` для совместимости сравнений. Поведение:
- домены и URL отсекаются (`isFilePathLike` требует ext в allow-list `FILE_EXTENSIONS`,
  `stripUrls` снимает `https?://…` до извлечения);
- extension-only токены (`tsx/.ts`) отклоняются (`lastDot <= 0` у последнего сегмента);
- шаг без файловых токенов → `stepPaths.length === 0` → `checkPlanAlignment` возвращает `null`
  (механизм не активен, warning не генерируется) — это и есть «починить regex, сохранить механизм».

**Тесты** (`tests/execution-scenario-tests.test.ts`):
1. шаг «fetch weather.com data for report» (только домен) → write `src/report.md` ×5 не блокируется
   (до фикса phantom-путь «weather.com» давал off-path warning на 3-м вызове);
2. шаг «keep only .tsx/.ts files in src» → write `src/App.tsx` ×5 не блокируется;
3. существующие кейсы on-track/off-step/block-after-3 и rewrite completed-step файлов зелёные —
   семантика механизма не изменилась для реальных путей.
