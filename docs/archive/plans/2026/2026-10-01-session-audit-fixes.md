сегментная полоса контекста в web-сайдбаре — 175 LLM-вызовов, 251 тул-вызов,
~20.1M prompt-токенов на коммит +230/−5 (`28f4748`).

## Шаг 1. `edit_file` vs CRLF (п.2 разбора, ~22 провала за сессию)

Файл: `src/tools/edit-file.ts:110` (`content.includes(oldStr)`).

- При несовпадении пробовать нормализованный матч: сравнить
  `content.replace(/\r\n/g, "\n")` с нормализованным `oldStr`; при успехе
  вырезать по смещениям в нормализованной строке и склеить оригинал
  (замена обязана сохранить исходные окончания строк файла).
- Тесты: `tests/tools-edit-file.test.ts` (новый или дописать): CRLF-файл +
  LF-`old` (многострочный), CRLF сохраняется после правки; LF-файл как был.
- Проверка: целевые тесты + `tsc --noEmit`.

## Шаг 2. Plan auto-advance для modify-шагов (п.1, самый опасный)

Файл: `src/modules/execution/module.ts:724` (`advancePlanIfStepComplete`).
Корень: токены файлов из описания шага проверяются на существование —
для «изменить существующий файл» истина вакуульно с рождения шага.

- Разделить по смыслу: auto-advance по existence — только для шагов
  создания (файла не было → появился); для остальных требовать
  свидетельство изменения: mtime/digest затронутых файлов новее момента,
  когда шаг стал текущим (снимок при `advance()` к шагу).
- `kind === "delete"` — без изменений (уже `allGone`).
- Шаги без файловых токенов — без изменений (ранний `return`).
- Тесты: юнит на `advancePlanIfStepComplete`/трекер — modify-шаг с
  существующим нетронутым файлом НЕ продвигается; после правки файла —
  продвигается; create-шаг — как раньше.
- Проверка: `bun test tests/execution* tests/plan*` + typecheck.

## Шаг 3. Слепые зоны трекинга правок (п.3, ложный concern критика)

- В `buildEvidencePack` при заданном `baseDir` добирать фактически

- Побочный выигрыш: аудит и perfectionism-детектор видят реальный объём
  работы, а не прокси.
- Тесты: `tests/modules/critic/*` — файл, изменённый мимо файловых тулов,
  присутствует в `changedFiles`.
- Проверка: целевые тесты + typecheck.

## Шаг 4. Автозапись повторов в память (п.5, мусор в `errors.md`)

Файл: `src/core/agent/tool-batch.ts:317` (`memStore.appendRule("errors", …)`).

- Писать наблюдаемое, а не boilerplate: в запись — первые строки реальных
  ошибок и гипотеза причины по сигнатуре (напр. `string_not_found` после
  `read_file` → «возможно CRLF/неточный якорь», а не «проверьте зависимости»).
- Не писать в глобальную память ошибки, похожие на промах модели, а не
  системную проблему: фейл без предшествующего успеха тула за сессию +
  текст вида «no test files matched / not found» — пропускать (или класть
  в сессионный лог, не в `errors.md`).
- Существующие две записи сессии стереть/исправить вручную при проверке.
- Тесты: юнит на условие записи (системная vs модельная ошибка).
- Проверка: целевые тесты + typecheck.
