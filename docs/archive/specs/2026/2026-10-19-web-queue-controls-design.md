# Управление очередью сообщений `mma web`: отмена и принудительный старт

_Дата: 2026-10-19 · Ветка: `feat/web-queue-controls`_

## Задача

В чате `mma web` сообщение, отправленное во время хода, встаёт в per-session
FIFO-очередь и ждёт `turn_end`. Сейчас очередь видна (полоса `#queueStrip`), но
не управляема: пользователь не может убрать ошибочно отправленное сообщение
или запустить важное раньше остальных, не дожидаясь конца текущего хода.

Нужны два действия над конкретным сообщением в очереди:

1. **Отмена** — удалить сообщение из очереди, не запуская его.
2. **Принудительный старт** — прервать текущий ход сессии и запустить выбранное
   сообщение следующим.

## Целевое поведение

- Каждая строка полосы очереди получает кнопки `▶` («Запустить сейчас») и `×`
  («Отменить»).
- Отмена убирает сообщение из очереди и из полосы. В ленту оно не попадает.
- Принудительный старт:
  1. переносит выбранное сообщение в голову очереди;
  2. если слот сессии занят — абортит текущий ход (`agent.shutdown(sessionId)`);
  3. на штатном `turn_end` дренаж поднимает голову, то есть выбранное сообщение;
  4. остальные сообщения сохраняют относительный порядок.
- Если слот уже свободен (гонка с естественным завершением хода), выбранное
  сообщение стартует сразу.
- Действия доступны и для строк-заглушек, текст которых у клиента отсутствует
  (сообщение из другой вкладки или перезагрузка посреди хода).

## Контракт

### Идентификатор сообщения

`QueuedMessage` получает `id: string` — монотонный в рамках `RunPool`
(`q1`, `q2`, …). Идентификатор выдаётся при постановке в очередь и живёт до
дренажа/удаления.

`RunPool`:

- `enqueue(...)` возвращает `QueuedMessage | null` (вместо позиции);
- `queuedIds(sessionId): string[]` — упорядоченные id очереди сессии;
- `queuedIdsBySession(): Record<string, string[]>` — проекция для состояния;
- `removeQueued(sessionId, id): QueuedMessage | undefined`;
- `promoteQueued(sessionId, id): QueuedMessage | undefined` — переносит в голову
  без изменения остальных элементов; повторный вызов для головы — no-op.

### Состояние

`sessionStatus()` (SSE `state` и `GET /api/state`) добавляет
`queuedIds: Record<string, string[]>`. Счётчик `queued` остаётся прежним.

### REST

Оба маршрута требуют `sessionId` и `id` в JSON-теле.

| Маршрут | Успех | Ошибки |
|---|---|---|
| `POST /api/queue/cancel` | `200 { ok: true }` | `400 bad_request`, `404 not_queued`, `409 setup_required` |
| `POST /api/queue/start` | `202 { ok: true, starting: true }` (занято), `200 { ok: true, started: true }` (свободно) | `400 bad_request`, `404 not_queued`, `409 setup_required` |

`POST /api/message` при постановке в очередь добавляет `id` в ответ
(`202 { ok, queued, id, sessionId, queuedForSession }`). Клиент хранит id вместе
с локальной копией сообщения.

## Клиент

- `session.queuedIds` — новая проекция в `state-sync`.
- `PendingMessage` получает `id`.
- Полоса очереди строится как объединение локальных записей и `queuedIds`:
  локальные дают текст, серверные id — управляемость строк-заглушек.
- После отмены локальная запись и id удаляются сразу; после старта запись
  поднимается в голову. Серверный `state` подтверждает результат.
- Ошибка действия показывается через `setIndicator` (i18n).

## Тесты

- `RunPool`: выдача id, `removeQueued`, `promoteQueued` (включая no-op головы).
- Сервер: отмена удаляет сообщение и возвращает `404` на повтор; принудительный
  старт абортит текущий ход и следующим запускает выбранное; `queuedIds`
  присутствует в `/api/state`; неизвестный id — `404`.
- DOM: полоса рисует кнопки для строк с id; `removePending`/`promotePending`
  меняют локальную очередь; строки без id остаются без действий.
