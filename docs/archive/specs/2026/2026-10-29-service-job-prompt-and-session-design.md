# Service job: короткий промпт и сессия не на старте

_Дата: 2026-10-29. Ветка: `fix/stress-register` / `service-overhead`. Источник:
стресс-тест `mma serve`, волна 14 (S-04, S-06)._

**Статус:** реализовано в ветке `service-overhead`; гварды
`tests/service/job-prompt-profile.test.ts`, `tests/service/serve-no-session.test.ts`.
Замер: промпт service-job — **98 токенов** (оценка `estimateTokens`) / 81
(cl100k), **0** определений тулов без `toolAllowlist`; было ~19 959 prompt-токенов
на односложный job.

## Что показала проблема (наблюдение)

1. **S-04.** Задача `mode: job` шла через тот же путь, что REPL и `mma web`:
   полный системный промпт харнесса (директивы, карта проекта, скиллы, скрытые
   тулы) плюс определения всех зарегистрированных тулов. Односложный запрос
   «Ответь одним словом: ок» стоил `promptTokens: 19959` при окне 131072 —
   ~15 % окна на оверхед, который задаче без тулов не нужен.
2. **S-06.** `mma serve` создавал сессию на старте (`bootstrap` →
   `sessionManager.create()`), хотя до первого запроса она пуста
   (`messageCount: 0`). Это тот же класс, что A-01: служебный процесс плодит
   сессии, а `session.maxSessions` участвует в фоновом удалении старых.

## Контракт

### 1. Профиль промпта — свойство хода, а не процесса

`Agent.promptProfile?: PromptProfile` — публичное поле хода
(`PromptProfile = "full" | "service-job"`, дефолт `full`). Его ставит точка
исполнения задачи на время job-хода и возвращает прежнее значение в `finally`.
Профиль — не глобальный флаг и не параметр bootstrap: REPL/web/one-shot поле не
трогают и остаются `full`.

- `full` — текущее поведение: статические блоки, динамические блоки (карта,
  скиллы, сессия, скрытые тулы), плагины. REPL, `mma web`, one-shot не меняются.
- `service-job` — **один короткий системный промпт** без карты проекта, скиллов,
  AGENTS.md, скрытых тулов и плагинных блоков. Промпт собирает
  `buildServiceJobPrompt(model, tools)`; он честно говорит, какие тулы доступны
  (список) или что тулов нет.

Выбор профиля делает точка исполнения задачи (`runTask`), а не вызывающий
хендлер:

| `task.mode` | профиль | тулы, видимые модели |
|---|---|---|
| `job` без `toolAllowlist` | `service-job` | **0** |
| `job` с `toolAllowlist` | `service-job` | ровно allowlist |
| `interactive` | `full` | обычный tag-отбор |

Для `job` пустой `toolAllowlist` — это осознанный `[]`, а не «без
ограничения»: `ToolExecutor.allowedNames()` трактует `[]` как «запрещено всё»,
поэтому `getToolDefinitions()` возвращает 0 определений. Это же значение
работает как enforcement: вызвать невидимый тул нельзя.

### 2. Что теряется в job-режиме (честно)

- Нет доступа к файлам, shell, web, браузеру, MCP, субагентам, плану и памяти —
  если клиент не передал их в `toolAllowlist`.
- Нет карты проекта, скиллов, AGENTS.md и инструкций харнесса: модель отвечает
  как обычный ассистент и не должна утверждать, что что-то прочитала или
  выполнила. Промпт это прямо запрещает.
- `question`/`approve` по-прежнему запрещены (S-04 не меняет §5.2).

Клиент, которому нужны тулы, передаёт `toolAllowlist` — тогда промпт перечисляет
разрешённые имена, а модель видит только их.

### 3. Сессия создаётся явно

`mma serve` — сервис, а не диалог: на старте сессия **не** создаётся
(`SESSION_COMMANDS` больше не содержит `serve`). Сессии появляются только:

- через `POST /v1/sessions` (контракт уже описан в OpenAPI и на `/v1/docs`);
- при `POST /v1/sessions/:id/tasks` для существующей сессии.

Задача на неизвестный `sessionId` остаётся `404 noSession` — молчаливое
создание по произвольному id запрещено (нельзя подтверждать чужие id и плодить
сессии из опечаток). `interactive`-задача тоже требует явной сессии.

One-shot/REPL (`нет подкоманды`), `web`, `meet`, `agents` создают сессию как
раньше.

## Инварианты

- **INV-SJ1.** `job` без `toolAllowlist` не отправляет модели ни одного
  определения тула. Проверка: `tests/service/job-prompt-profile.test.ts` —
  реестр из 120 тулов + `applyTaskScope` → `getToolDefinitions().length === 0`.
- **INV-SJ2.** Системный промпт `service-job` короче 300 токенов (оценка
  `estimateTokens`) и не содержит карты/инструкций харнесса. Порог — часть
  теста: если полный промпт «протечёт» обратно, тест падает.
- **INV-SJ3.** `runTask` возвращает прежние `toolAllowlist` и профиль после
  хода (в `finally`), поэтому interactive-задача на том же раннере снова видит
  полный набор.
- **INV-SJ4.** Старт `serve` не создаёт каталогов в `sessions/`: bootstrap с
  `sessionAutocreate = false` оставляет 0 сессий; после `manager.create()` —
  ровно 1.
- **INV-SJ5.** Профиль — не глобальный флаг: REPL/web путь его не меняет и
  остаётся `full`.

## План

1. `PromptProfile` + `buildServiceJobPrompt` + ветка в `buildSystemPrompt`. Гейт:
   тест токенов и профиля.
2. `runTask` применяет job-скоуп (0 тулов без allowlist, профиль) и
   восстанавливает его. Гейт: тест 0/1/restore.
3. `SESSION_COMMANDS` без `serve`. Гейт: тест bootstrap с 0 сессий.
4. Документация OpenAPI (`toolAllowlist`, `job`) и реестр стресс-теста.
