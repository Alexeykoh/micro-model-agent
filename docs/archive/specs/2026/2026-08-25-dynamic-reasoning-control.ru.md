# Динамическое управление reasoning (think level)

> **Дата:** 2026-08-25
> **Статус:** черновик
> **Происхождение:** обсуждение — агент должен уметь адаптировать глубину размышлений по ходу выполнения, а не работать с фиксированным уровнем на весь запуск.

## 1. Проблема

Reasoning-модели (Qwen3.5-9B и подобные) тратят сильно разное количество токенов на thinking в зависимости от этапа задачи:

- **Планирование / отладка / восстановление после audit-rejection** — глубокий thinking оправдан.
- **Рутинные записи по готовому плану, повторяющиеся правки, чанковая суммаризация** — длинные thinking-цепочки съедают `maxCompletionTokens` (наблюдалось: 12K+ токенов на голый reasoning посреди `tool_call` → обрезание аргументов → recoverable-error retries, см. запись сертификации 69 и `docs/small-model-observations.md`).

Сегодня уровень усилий фиксирован на весь запуск (`ChatOptions.reasoningEffort`, используется только `chunk_query` с дефолтом `"none"`). Основной цикл агента его никогда не задаёт.

**Цель:** три уровня управления reasoning effort — пользовательский выбор, автоматическая policy и override моделью — на provider-mapped механизме, который реально работает на каждом бэкенде.

## 2. Не входит в объём (non-goals)

- Никаких keyword/текстовых эвристик «сложная ли это задача» (правило #10). Только структурные сигналы: история tool-вызовов, состояние плана, счётчики ретраев.
- Никакого динамического управления для субагентов (системный промпт субагента остаётся байт-стабильным, KV-cache friendly).
- Никакого UI/TUI сверх существующих статусных строк.

## 3. Уровни reasoning (множество значений)

Множество уровней выровнено с opencode:

| Уровень   | Семантика                                                       | Маппинг на provider body                         |
| --------- | --------------------------------------------------------------- | ------------------------------------------------- |
| `default` | Бэкенд решает сам (ничего не шлём)                              | поле `reasoning_effort` не отправляется            |
| `none`    | Thinking полностью выключен                                     | `reasoning_effort: "none"` / `enable_thinking:false` / `/no_think` |
| `low`     | Минимальный thinking                                            | `reasoning_effort: "low"` / `enable_thinking:true` |
| `high`    | Глубокий thinking                                               | `reasoning_effort: "high"` / `enable_thinking:true` |
| `max`     | Максимальный thinking (OpenAI gpt-5.2+, OpRouter)              | `reasoning_effort: "max"` / `enable_thinking:true` |

На бэкендах без гранулярности (llama.cpp/template-kwarg, prompt-tag) уровни `low|high|max` сворачиваются в один «thinking on» — гранулярность схлопывается, но работает корректно.

## 4. Пользовательский контроль

Пользователь может явно задать уровень reasoning на сессию. Это **baseline**, поверх которого работают auto-policy и agent override.

### 4.1 REPL-команда `/reasoning`

Сейчас `/reasoning` — тумблит показ/скрытие рассуждений. Расширяется:

```
/reasoning              — показать текущий уровень (как /status)
/reasoning default      — бэкенд решает сам
/reasoning none         — выключить thinking
/reasoning low          — минимальный thinking
/reasoning high         — глубокий thinking
/reasoning max          — максимальный thinking
/reasoning auto         — policy-driven (динамический)
```

Без аргумента — вывод текущего уровня и режима (`Reasoning: high (auto)` или `Reasoning: none (manual)`). С аргументом — переключение.

### 4.2 CLI-флаг

```bash
mma "сделай лендинг" --reasoning high       # фиксированный уровень
mma "сделай лендинг" --reasoning auto       # автоматический
```

### 4.3 Конфигурация

```jsonc
// ~/.mma/config.json
{
  "reasoning": {
    "mode": "auto",         // "auto" | "default" | "none" | "low" | "high" | "max"
                            // по умолчанию: "auto"
    "min": "low",           // нижняя граница clamp в auto-режиме
    "max": "high",          // верхняя граница clamp в auto-режиме
    "overrideCooldown": 5   // итераций между принимаемыми override агента
  }
}
```

Семантика `mode`:

- **`auto`** — ReasoningPolicy активна, цикл динамически меняет уровень по структурным сигналам (§6). Это рекомендуемый режим.
- **`default|none|low|high|max`** — фиксированный уровень на всю сессию. Policy неактивна. Override-тул не регистрируется.
- Режим `auto` доступен только когда probe (§5.2) подтвердил поддержку. Если probe неудачен → откат на `default` + `[WARN]`.

Priority: CLI-флаг > REPL-команда > конфиг > дефолт (`auto`).

## 5. Слой 1: EffortMechanism (provider-mapped)

`reasoning_effort` в OpenAI-теле запроса поддерживается НЕ повсеместно. В частности, llama.cpp управляет thinking у Qwen через chat-template kwargs или prompt-теги; OpenAI-поле может молча игнорироваться — тул будет «работать», а эффекта ноль.

### 5.1 Стратегии механизма

| Стратегия        | Как выражает уровень                                                       | Бэкенды                          |
| ---------------- | -------------------------------------------------------------------------- | -------------------------------- |
| `openai-effort`  | поле `reasoning_effort` в теле запроса (уже есть в `openai-compat.ts`)     | OpenAI, OpenRouter, vLLM, Zen/Go |
| `template-kwarg` | специфичное для бэкенда поле тела (напр. `chat_template_kwargs: { enable_thinking }`) | llama.cpp              |
| `prompt-tag`     | тег, дописываемый к последнему user-сообщению (напр. `/no_think`)          | Qwen-шаблоны без поддержки kwarg |
| `none`           | не поддерживается — фича выключена                                         | всё остальное                    |

Маппинг объявляется на пресете провайдера (`ProviderCapabilities.reasoningEffort` становится enum-стратегией вместо boolean). Кастомные провайдеры по умолчанию получают `none`, если пользователь не задал `provider.reasoningStrategy`.

Маппинг уровней по стратегиям:

- `openai-effort`: пробрасывается как есть (`none|low|high|max`; `default` = поле не шлём).
- `template-kwarg`: `none → enable_thinking:false`; остальные → `enable_thinking:true`.
- `prompt-tag`: `none → дописать "/no_think"`; остальные → ничего не дописываем.

### 5.2 Startup-probe (обязателен перед включением)

Одноразовый probe при бутстрапе (в фоне, как banner-проба LSP):

1. Отправить тривиальный non-streaming запрос с принудительным уровнем `none` через замапленный механизм.
2. Проверить ответ: наличие `reasoning_content` (или контента `<think>`) означает, что механизм НЕ сработал.
3. Результат кешируется в памяти на сессию по ключу `(baseUrl, model)`; неудача → `auto`-режим отключается + одна строка `[WARN]` (i18n `reasoning.probe_failed`, en+ru).

Стоимость probe: ~1 крошечный LLM-вызов при старте, fire-and-forget; запуск продолжается с текущим фиксированным уровнем, пока probe не подтвердит поддержку. Слой Policy неактивен до подтверждения.

## 6. Слой 2: ReasoningPolicy (структурные сигналы, режим auto)

Небольшой модуль `src/modules/reasoning/policy.ts`, который основной цикл опрашивает каждую итерацию перед LLM-вызовом. Входы — счётчики/состояние, которые harness уже отслеживает; никакого анализа текста.

### Сигналы → уровни

| Сигнал (источник)                                                        | Эффект                        |
| ------------------------------------------------------------------------ | ----------------------------- |
| Ответ помечен hallucination-retry (confidence pipeline в `agent.ts`)      | поднять до `high`             |
| Injected feedback: rejection финального аудита / recoverable-LLM-ошибка   | поднять до `high`             |
| Исполнение шага плана: ≥2 подряд успешных file-mutating вызова на шаге    | понизить до `low`             |
| Повтор идентичного tool-вызова детектнут (`StuckDetector`)                | `low` (thinking это не починит) |
| Создан новый план (`plan create`) или re-plan                             | `high` на следующие N=3 итерации |
| Дефолт                                                                    | из конфига (`reasoning.mode` baseline) |

Правила:

- Raise побеждает lower внутри одной итерации; повышения откатываются к дефолту после 5 спокойных итераций (нет новых ретраев/ошибок).
- Каждая автоматическая смена логируется session-event'ом семейства `context` (`{type:"reasoning", from, to, reason}`) и записывается FactExtractor'ом как `[Thinking: high]`, чтобы пережить compaction (см. §8).
- Policy работает ТОЛЬКО когда probe (§5.2) подтвердил механизм И `reasoning.mode === "auto"`.

Это не keyword matching: каждый сигнал — дискретное событие harness, независимое от языка и формулировок.

## 7. Слой 3: тул `set_thinking`

- Файл: `src/tools/set-thinking.ts`. `alwaysOn: true` — переживает сужение набора тулов; регистрируется ТОЛЬКО в `auto`-режиме И после успешного probe.
- Аргументы: `{ level: "none"|"low"|"high"|"max", reason?: string }`.
- Поведение:
  - Пишет в shared mutable state, который цикл читает со следующей итерации (тот же паттерн, что `enable_tools` / `activeToolTags`).
  - Применяется со СЛЕДУЮЩЕГО LLM-вызова; рассчитан на отправку **в одном батче** с другими tool-вызовами — никогда не требует отдельного хода.
  - Auto-режим с clamp: клампится в `[reasoning.min, reasoning.max]`; выход за границы → применяется clamped значение + пояснение в ответе.
  - Cooldown (`overrideCooldown`, по умолчанию 5 итераций): вызовы внутри cooldown принимаются-но-откладываются с объясняющим результатом (без спама ошибками и зацикливания).
  - Результат возвращает эффективный уровень и текущий режим — модель всегда знает актуальное состояние.
- Описание тула прямо говорит: уровень управляется автоматически; использовать только чтобы форсировать более глубокий thinking для действительно сложных подзадач или более мелкий для механических пачек.
- Субагенты/MoE-волны этот тул не видят и всегда работают на родительском дефолтном уровне (инвариант стабильного субагентного промпта).

## 8. Видимость состояния и персистентность

- FactExtractor записывает смены уровня как факт `[Thinking: <level>]` (role-gated к tool/system-summary сообщениям) → переживает compaction.
- Лог сессии (`session.jsonl`): новый тип записи `reasoning` `{from, to, reason: "policy:<signal>"|"agent", iteration}`.
- `llm_usage` события уже несут счётчики токенов — сравнение расхода reasoning-токенов до/после измеряемо из логов для валидации.
- REPL-статус: текущий уровень и режим отображается в `/status` и в REPL banner (строка `Reasoning: <level> (<mode>)`).

## 10. Риски и митигации

| Риск                                             | Митигация                                                      |
| ------------------------------------------------ | --------------------------------------------------------------- |
| Бэкенд молча игнорирует effort (фейковая фича)   | Обязательный probe; `auto` откатывается на `default` до подтверждения |
| Модель спамит `set_thinking`                     | Cooldown + clamp + описание «управляется автоматически»         |
| Понижение уровня увеличивает hallucination-ретраи | Ретраи автоматически поднимают уровень (замкнутый контур, §6)   |
| Дополнительная задержка старта                   | Probe фоновый/fire-and-forget; policy неактивна до завершения   |
| Prompt-tag стратегия загрязняет историю сообщений | Тег дописывается только в исходящую копию запроса, никогда не сохраняется в сессию/контекст |
| Пользователь фиксирует уровень, policy не может его менять | Это осознанный выбор: `/reasoning high` = принудительный high; для динамики — `/reasoning auto` |

## 11. Критерии успеха

- На qwen3.5-9b/LM Studio с `reasoning.mode: "auto"`: рутинные multi-write сценарии показывают ≥30% экономии суммарных completion-токенов против фиксированного `high` при равном или лучшем pass rate (сертификационный набор, `--reps 2`).
- Сценарии с планированием не регрессируют по качеству планов (pass rate audit gate не изменился).
- `/reasoning auto` в REPL и `--reasoning high` в CLI работают и переключаются без перезапуска сессии.
- Все смены уровня видны в `session.jsonl` и восстанавливаемы post-mortem.
