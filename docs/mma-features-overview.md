# MMA v2 — полный список возможностей с подробностями

> Обзор возможностей агента простыми словами. Технические детали — в [AGENTS.md](../AGENTS.md) и [docs/specs/](./specs/).
> Актуально для **MMA 2.17.0**. История версий — в [CHANGELOG.md](../CHANGELOG.md).

## 1. Архитектура: 6-слойная машина состояний

Агент устроен как конвейер из слоёв, где каждый занимается своим делом:

```
CLI/REPL или WebHost → Core (Agent) → LLM-слой → Инструменты → Модули
```

**Как проходит один ход агента (цикл состояний внутри Core):**

1. **INIT** — при старте собирается системный промпт из блоков (инструкции, карта проекта, память, план), строится история диалога.
2. **THINK** — запрос к модели. Ответ проходит проверку на «галлюцинации» до того, как будет показан.
3. **ACT** — если модель решила вызвать инструмент (прочитать файл, запустить команду) — вызов парсится и выполняется через исполнитель.
4. **OBSERVE** — результат инструмента возвращается в контекст; система решает: продолжать цикл или завершаться.
5. **OUTPUT** — модель выдала финальный текст без вызовов инструментов → текст показывается пользователю.
6. **ERROR** — при ошибке: повтор или эскалация, а не падение всей программы.

Перед показом финального ответа работают независимые шлюзы (галлюцинации, финальный аудит, in-loop критик, honest-stop), а сам цикл — это не «большой запутанный объект», а простая машина состояний: легко понять, на каком этапе что пошло не так. Каждый слой тестируется отдельно.

### Два фронтенда, одно ядро (`Host`)

Над одним и тем же `Agent` живут две взаимозаменяемые реализации хост-контракта `Host` (`src/core/host.ts`):

- **`Repl`** — терминальный интерактивный режим;
- **`WebHost`** — `mma web`, браузерный чат без TTY (`src/core/web-host.ts`).

Оба идут через **один** `runAgent`-путь (рендеринг, лог сессии, single-flight guard общие), поэтому поведение агента в терминале и браузере совпадает. Плагины видят узкий `HostBridge`; полный `Host` добавляет `executeCommand` (slash-команды) и `getState` (снапшот для сайдбара/топбара).

### Параллельные сессии (web)

Один `Agent` — не реентерабельный: abort, итерации, `ContextManager` и активная сессия живут в полях инстанса. Поэтому каждая одновременно бегущая сессия в `mma web` получает **свой раннер** (`SessionRunner`, `src/core/bootstrap/session-runner.ts`): собственный `Agent` + `ContextManager` + запиненный (только своя сессия) `SessionManager` + свой `ExecutionModule`/трекер плана + свой `ToolExecutor`/`ToolContext`/реестр.

Разделяются только stateless или долгоживущее: конфиг, провайдер, шаблон реестра тулов, инстансы плагинов, память, индекс. Раннеры спавнятся лениво — по первому сообщению сессии — и держат её историю с диска. Оркестрация слотов, очередей и параллелизма живёт в `RunPool` (`src/modules/webui/session-pool.ts`). В пределах одной сессии — single-flight + FIFO-очередь; между сессиями — настоящее параллельное исполнение.

## 2. Инструменты

| Группа | Инструменты | Что делают |
|---|---|---|
| Файлы | `read_file`, `write_file`, `edit_file`, `list_dir`, `glob`, `grep`, `file_info`, `move_file`, `delete_file`, `create_dir` | Чтение (по 300 строк за раз, чтобы не жечь контекст), запись с автосозданием папок, поиск по имени (`glob`) и по содержимому (`grep`) |
| Команды | `bash` | Запуск команд терминала. Долгие процессы (сервер разработки и т.п.) через ~5 секунд автоматически уходят в фон и получают ID |
| Фоновые процессы | `process_list`, `process_log`, `process_wait`, `process_kill` | Список фоновых процессов, чтение вывода, блокирующее ожидание завершения процесса с буфером вывода (`process_wait` заменяет циклы поллинга `process_log` + `sleep`), остановка дерева процессов |
| Интернет | `web_search`, `web_fetch`, `web_browse` | Поиск, чтение страниц (без JS), полноценный браузер |
| Загрузки | `download_file` | Скачать бинарный файл (картинку, архив) сразу на диск — байты не попадают в контекст |
| Браузер | `browser` | Playwright: открыть сайт, кликнуть по элементу, ввести текст, скролл, скриншот. Элементы нумеруются, агент работает по номерам (`click(3)`) |
| Мультимодальность | `attach_image` | Прикрепить картинку (файл/URL/буфер обмена); большие PNG пережимаются в маленький JPEG, чтобы влезть в контекст |
| Делегирование | `subagent` | Порождение субагента для подзадачи (с зоной доступа к файлам) |
| Обработка текста | `chunk_query` | Разрезать большой текст на куски и обработать параллельно |
| Расширения | `mcp_call`, `pipeline_run`, `load_skill` | Вызов внешнего инструмента MCP-сервера, запуск многошагового сценария (pipeline), загрузка скилла по имени |
| Память | `remember`, `recall` | «Запомни…» / «что помнишь о…» — явная запись и чтение постоянной памяти (регистрируются модулем памяти) |
| История | `search_history` | Полнотекстовый поиск по всем прошлым сессиям |
| Самосправка | `session_info` | Сведения о текущей сессии (id, имя, модель, провайдер, окно контекста, счётчик сообщений) и живое использование контекста (`токены / бюджет истории`) — модель может отвечать на вопросы «где я и сколько уже израсходовано» |
| Служебный | `enable_tools` | Включение скрытых инструментов на лету (см. раздел 3) |
| Вопросы | `question`, `approve` | Интерактивный выбор (одно-/множественный) и «свой ответ», либо явное Yes/No. `question` сначала сам проверяет память агента: что память уже знает — не спрашивается. До 3 незнакомых вопросов за вызов. В терминале и web |
| Структурные (от модулей) | `plan`, `plan_step`, `todo`, `verify`, `project_map`, `lsp_check`, `set_thinking` | Управление планом/подзадачами, закрытие шага (`plan_step step=N status=done\|failed\|skipped`), проверка исполнения, запрос карты проекта, проверка ошибок компиляции через LSP, переключение уровня размышлений |

Примечание: `question`/`approve` включены в базовый набор (с 2.11.0). Системный промпт требует задавать вопросы через тул `question`, а не списком в тексте ответа; обычный текст остаётся лишь headless-fallback'ом.

## 3. Сужение набора инструментов (по умолчанию)

Проблема: каждая схема инструмента тратит токены контекста — полный набор (~28 инструментов) стоит около 3500 токенов на каждый запрос модели.

Механизм сужения **включён по умолчанию** (`tools.enableOnDemand: true`, P5 auto-narrowing, 2.11.0): перед первым вызовом LLM тип задачи определяется детерминированно по тексту запроса (эвристики en+ru без вызова модели) и недостающие теги дописываются в активный набор — только добавление, ничего не убирается. Тривиальный чат идёт на узком наборе (`file`/`code` + alwaysOn), веб-задача сразу видит `research` без лишнего хода на `enable_tools`.

- Видны инструменты с тегами из `tools.defaultTags` (по умолчанию `file`, `code`).
- Остальные не исчезают бесследно: они перечисляются в отдельном компактном блоке промпта, сгруппированные по тегам — модель знает, что они есть.
- Модель вызывает `enable_tools ["research"]` — инструменты появляются со следующего хода. Доступные теги: `file`, `code`, `shell`, `research`, `browser`, `vision`, `image`, `memory`, `core`.
- Структурные и интерактивные инструменты (`alwaysOn`: план, проверка, карта, `enable_tools`, `question`/`approve`, `load_skill`) всегда видны — их нельзя случайно отключить.

## 4. Контекстный бюджет и компакция

У маленькой модели мало «рабочей памяти» — она расходуется бережно:

- **Динамические бюджеты** от размера окна модели (32K → 3K инструкции / 5K запас / 24K история; 64K → 6/10/48 и т.д.).
- **Доли бюджета настраиваются**: `mma context --system 0.15` / `--reserve 0.2` или `/context system 0.15` / `/context reserve 0.2` (допустимо 0.05–0.9, сумма долей < 0.95). Команда без аргумента печатает разбивку «инструкции / запас / история» в токенах и процентах.
- **Компакция** срабатывает при заполнении 75% бюджета истории; 15-итерационный интервал срабатывает лишь когда история реально заполнена (≥ `contextBudget.compactionMinLoad`, по умолчанию 0.5) — иначе сжатие больше не выкидывает середину задачи на ~40% загрузки. Старые сообщения сворачиваются в **структурное резюме**, которое сохраняет самое важное — исходную задачу пользователя, какие файлы созданы/изменены/удалены, состояние плана, ключевые решения, ошибки и то, что уже пробовали безуспешно.
- Последние 6 обменов остаются полностью — свежий контекст не теряется.
- Резюме пишется в лог один раз (без дублирования).
- Подсчёт токенов точный (tiktoken), с грубым запасным вариантом.
- **Наблюдаемость**: в лог сессии пишутся события `context` (структура и заполненность перед каждым запросом) и `compaction` (что, когда и почему сжалось) — можно восстановить всю историю деградации контекста постфактум.
- **Переполнение инструкций больше не молчит**: если AGENTS.md или карта проекта не влезают в системный бюджет, при старте печатается предупреждение с конкретным фиксом (поднять `contextWindow` или увеличить долю `system`), а перед первым запросом блок честно суммаризируется моделью (с сообщением «сжимаю N блоков…») либо обрезается с маркером и подсказкой прочитать полный файл через `read_file`. Кэш суммаризаций — `<проект>/.mma/cache/prompt-summaries`, инвалидируется правкой файла/бюджета.
- **Context probe**: на старте агент спрашивает у активного бэкенда, с каким контекстом модель реально загружена, и сравнивает с настроенным `contextWindow` — при меньшем предупреждает, при большем подсказывает увеличить (без автоматического клампа). Цепочка проб (2.8.0): LM Studio native → Ollama native → llama.cpp `/props` → OpenAI-совместимые метаданные `/models` → каталог models.dev (для Zen/Go). Голый `/models` без метаданных → тихий `null` (fail-open).

Подробнее о том, почему после десятков сжатий агент всё ещё помняет задачу — см. раздел [«Как агент не теряет суть проекта»](#8-как-агент-не-теряет-суть-проекта).

## 5. Планирование и гарантии исполнения

- **План-чеклист всегда на виду**: сам план лежит на диске — **у каждой сессии свой слот** `.mma/plans/sessions/<sessionId>/active.json` (с 2.12.0); его актуальное состояние `[x] сделано / [ ] ждёт` впрыскивается в контекст после каждой пачки инструментов, а в системном промпте есть статичный блок-напоминание о плане. Так модель видит прогресс каждый ход, но системный промпт не мутирует — префикс-кэш бэкенда не ломается.
- **План следует за сессией**: переключение сессии (`/resume`, `/new`, web-активация) переносит трекер на её план; удаление сессии убирает слот. Черновики и архив остаются общей библиотекой. Легаси-план `active.json` усыновляется активной сессией при первом старте после апгрейда.
- Решение создавать план принимает сама модель (по сложности задачи), а не хрупкие эвристики по ключевым словам.
- **Хранилище планов**: активный план + черновики + архив. Создание нового не уничтожает старый — незавершённый уходит в черновики. Есть `re-plan` (сохранить сделанное, перепланировать остаток), удаление, очистка.
- **Контракты шага (2.11.0)**: при `plan create`/`re-plan` на каждый шаг требуется парный `checks` — `file-exists:<path>` (жёстко проверяется `StepVerifier` при закрытии), `command:<cmd>` / `manual:<text>` (самосертификация с явной пометкой). Закрытие шага — тулом `plan_step step=N status=done|failed|skipped` (без параметра `action`); старая форма `plan update step=` работает как алиас. Проверка покрытия шагов (`plan.coverage_blocked`) блокирует создание битого плана до любой мутации.
- **Самосертификация шагов запрещена**: пометить шаг «готово» можно только если названные в нём файлы реально существуют (для шагов-удалений — что файлов больше нет). Шаг с ошибкой компиляции «закрыть» тоже нельзя. Авто-закрытие шага требует, чтобы файл был создан/изменён **после** `plan.createdAt`, а не просто существовал раньше (фикс 2.15.0 — иначе старый файл закрывал шаг до написания кода).
- **Детектор застревания**: слишком много итераций на одном шаге, три одинаковых вызова подряд, серия неудачных bash-команд, долгие серии только-чтения без записи — всё это вызывает подсказку «смени подход».
- **Финальный аудит-шлюз**: когда модель пытается выдать финальный ответ при активном плане, система проверяет — все ли шаги закрыты, все ли файлы на месте, проходит ли проверка типов и тесты. Если нет — в контекст летит предупреждение, и работа продолжается (ограничено лимитом итераций).
- После каждой записи файла автоматически гоняется быстрая проверка синтаксиса/типов, ошибки показываются модели немедленно.

## 6. Надёжность связи с LLM

Малые модели через локальные бэкенды (llama.cpp, LM Studio) капризны — связь укреплена со всех сторон:

- **Повторы с экспоненциальной паузой** при 429 (перегрузка) и ошибках сервера; уважается заголовок `Retry-After`.
- **Стриминг с fallback**: если стрим не вернул ни текста, ни вызова инструмента — автоматический повтор тем же запросом в обычном (не потоковом) режиме, который надёжнее для tool-calls.
- **Обрыв потока до первого байта** — тихо повторяется; после начала выдачи контента — нет (иначе задублируются куски).
- **Тайм-аут тишины**: молчаливый сервер не съедает весь тайм-аут запроса.
- **Обрезанные ответы** распознаются (`finish_reason: length`) и не маскируются под «пустой ответ» — модель получает понятную ошибку и адаптируется (например, режет большую запись на части).
- **Переключение провайдеров (failover)**: основной провайдер лёг (429/сеть) → автоматический переход на следующий из настроенных; удавшийся становится основным. Есть проверка доступности всех провайдеров (`mma provider check`).
- **Hot-swap**: сменить модель/провайдера посреди диалога командой, без перезапуска.
- **Реальный расход токенов**: стриминговые запросы просят бэкенд присылать `usage` в финальном чанке (`stream_options.include_usage`), поэтому LM Studio / vLLM / OpenAI / OpenRouter отдают настоящие счётчики, а не оценку «символы / 4».

### Кэширование промпта (prompt cache)

У каждого провайдера теперь описано его поведение кэша (`ProviderCapabilities.cache`, можно переопределить на запись в `provider.entries[].cache`). OpenAI-совместимый провайдер шлёт нужные бэкенду подсказки: `cache_prompt` (llama.cpp), `prompt_cache_key` (OpenAI), `session_id` (sticky-роутинг OpenRouter); заголовок `x-opencode-session` включается только при заданной capability (легаси-поведение сохранено).

- **Нормализация ответов**: `parseCacheUsage` приводит форматы OpenAI/LM Studio/llama.cpp/vLLM/OpenRouter/Zen/Go, DeepSeek, Anthropic и Ollama к одному виду (`Chunk.usage.cache`). Нет полей → честный `unknown`, а не «промах».
- **Экономия**: цены `cachedInput`/`cacheWrite` учитываются в стоимости, `CostTracker.saved` считает сэкономленное; для MiniMax/GLM есть встроенные цены кэш-чтения.
- **Монитор префикса**: даже если бэкенд ничего не сообщает, клиентский `prefix-monitor` определяет, что сломало кэшируемый префикс — `system`, `tools`, `history` или `volatile`.
- **Показ**: одна строка в футере REPL/прогона/`--json`: `Cache: 87% hit · saved $0.42` либо `Prefix stable: 93% · broke: tool set`. `mma session show <id>` агрегирует `llm_usage` в токены и hit-rate.
- **Баланс провайдера**: `mma usage` показывает расход/лимит ключа и баланс — поддерживается OpenRouter (`/key`, `/credits`); Zen/Go отвечают, что баланс смотрится в веб-панели.

## 7. MoE — разложение задачи по субагентам

«Mixture of Experts» на уровне агента: одна большая задача → несколько специалистов. Вместо того чтобы одна маленькая модель тащила всё сразу (и путалась), задача делится, и каждую часть делает отдельный субагент со своим набором полномочий.

### Как это работает, шаг за шагом

1. **Router строит план.** Отдельная модель-оркестратор (обычно покрупнее рабочей) превращает запрос пользователя в структурированный план из подзадач: что сделать, какие файлы затронуть, от чего что зависит.
2. **План проверяется на здравость** до исполнения:
   - *циклы* («А зависит от Б, а Б от А») — детектируются;
   - *конфликт записей* — две подзадачи одновременно пишут в один файл;
   - *нарушенные зависимости* — подзадача читает файл, который появится только позже (read-after-write);
   - отсутствующие зависимости достраиваются автоматически; неисправимое → план на переделку.
3. **Каждому эксперту — свои полномочия.** Эксперты описываются в конфиге: своя модель, свой набор инструментов (по тегам — например, «файловому» эксперту не дают веба) и лимит попыток. Субагенту выдаётся **зона доступа к файлам**: назначенные файлы можно менять, остальные — в лучшем случае читать.
4. **Параллельные волны.** Подзадачи сортируются топологически по зависимостям и исполняются волнами: сначала независимые (параллельно), потом те, кто их дождался, и так до конца.
5. **Устойчивость к сбоям.** Временные ошибки (тайм-аут, перегрузка сервера, сеть) ретраятся с паузой до лимита попыток эксперта. Структурный провал (субагент сделал не то) не убивает процесс — он уходит оркестратору как сигнал для перепланирования.
6. **Верификация и слияние.** Оркестратор оценивает результаты (`verifyAndMerge`): годится → финальный ответ; нет → перепланирование (до 3 циклов). Финальная проверка общая: файлы существуют, проверка типов проходит, тесты зелёные — по артефактам всех подзадач.
7. **Результаты — по ссылке.** Если включен режим артефактов, полные ответы субагентов сохраняются в файлы, а плану остаются короткие резюме (см. раздел 11).

### Отказоустойчивость всего механизма

Если MoE выключен в конфиге или споткнулся (модель выдала нечитаемый план, оркестратор недоступен) — агент **прозрачно падает обратно** в обычный одиночный режим работы. Задача всё равно будет решена, просто одной моделью без распараллеливания.

### Детали, которые важны для качества

- **Эксперты — из конфига**: `config.experts` (модель, теги инструментов, число попыток, описание) рендерится прямо в промпт планировщика; фолбэк — теги инструментов. Оркестратор ходит через `ProviderManager`, поэтому уважает per-entry `contextWindow`/`retry`/`rateLimits` и failover.
- **Машиночитаемые критерии успеха**: `success_criteria` вида `file-exists:`, `substring-in-file:`, `command-exit-0:` проверяются `StepVerifier` до слияния; критерии, которые нельзя проверить автоматически, остаются предупреждениями в контексте оркестратора.
- **Избирательный re-plan**: при повторном планировании уже успешные сабтаски переносятся как есть (`skipIds`/`carriedResults`), переисполняются только упавшие и новые — а не всё заново.
- **Работа идёт только на верхнем уровне**: сабагент внутри MoE всегда исполняет обычный одиночный цикл и не порождает собственный MoE (иначе рекурсия вешала прогон).
- **Наблюдаемость**: события `moe_plan`/`moe_subtask`/`moe_replan`/`moe_verify` пишутся в `session.jsonl` и видны в `mma session show`; расход токенов агрегируется по тегу эксперта, а сабагент получает реальный id сессии (не «moe»).

## 8. Как агент не теряет суть проекта

Главная проблема длинных сессий на маленькой модели: контекст заполняется, история сжимается, и агент «забывает», что делал. MMA решает это комбинацией механизмов — **ничего важного не живёт только в контексте**.

### Якоря, которые переживают каждое сжатие

При компакции старые сообщения сворачиваются в структурное резюме, но самое критичное дублируется отдельными якорями:

- **`[Task: …]`** — исходная задача пользователя. Менеджер контекста запоминает *первую настоящую* инструкцию хода (игнорируя служебные обёртки вроде `<system-summary>`) и всегда заново вставляет её в сжатое резюме. Вставленная ошибка или лог ошибку задачей не подменяют. Каждый новый запрос пользователя становится новой сохраняемой задачей (`resetUserTurn()`), чтобы задача прошлого хода не протухала.
- **`[Plan: …]`** — состояние плана. План вообще не живёт в истории диалога — он лежит на диске (`.mma/plans/sessions/<sessionId>/active.json`) и после каждого сжатия заново впрыскивается в промпт из первоисточника. Поэтому сколько бы раз ни сжимался контекст, чеклист `[x]/[ ]` остаётся актуальным.
- **`[Files: …]` / `[Deleted: …]` / `[Read: …]`** — экстрактор фактов из результатов инструментов выписывает созданные/изменённые файлы, удалённые и прочитанные (до 12 последних чтений), так что после сжатия агент знает, что уже видел и что сделал, и не перечитывает одно и то же по кругу.
- **`[Errors: …]`** — повторявшиеся ошибки тоже попадают в резюме.

Резюме не вкладывается само в себя (сжатые сводки исключаются из экстракции фактов), поэтому якоря не размножаются и не искажаются от сжатия к сжатию.

### Почему 10–30 сжатий подряд ничего не ломают

1. **Единственный источник истины — диск, а не контекст.** План, карта проекта, память проекта, артефакты субагентов — всё это файлы на диске. Контекст можно сжать хоть сто раз — при следующем ходе эти данные восстанавливаются из первоисточника.
2. **Защита от «спирали смерти» сжатий.** Каждая компакция снижает оценку качества контекста; раньше после ~50 принудительных сжатий качество падало ниже порога триггера, и сжатия шли бесконечно. Теперь штраф за сжатие ограничен снизу — качество никогда не заклинивает, плюс есть кулдаун между принудительными сжатиями.
3. **Сжатие — не потеря, а переупаковка.** В резюме осознанно сохраняются: задача, список файлов, ошибки, «что пробовали и не сработало», ключевые решения. Теряется только болтовня. Свежие 6 обменов всегда остаются целиком — текущий момент не размывается.
4. **Долговременная память вне сессии.** Повторяющиеся системные сбои (один инструмент упал 3+ раза) автоматически записываются в `errors.md`; решения и соглашения — в `decisions.md`/`conventions.md`. Это markdown-файлы в домашней папке, они живут годами и подмешиваются в промпт новых сессий независимо от того, что было сжато.

Итог: сжатие меняет *форму* памяти (полная история → компактное резюме), но не *факт* знания — потому что всё существенное продублировано якорями, диском или постоянной памятью.

## 9. Память: три горизонта

Память агента многослойная: чем важнее информация и дольше она нужна, тем надёжнее хранится.

### Горизонт 1 — рабочий контекст (текущий ход)

Само окно контекста модели. Живёт недолго и периодически сжимается, но критичные факты продублированы якорями `[Task:]`, `[Plan:]`, `[Files:]`, `[Errors:]` (подробно — раздел 8).

### Горизонт 2 — сессия на диске (часы и дни)

Каждый диалог сохраняется в `~/.mma/sessions/<id>/`:

- **`meta.json`** — паспорт сессии: имя, модель, счётчики сообщений, временные метки.
- **`history.jsonl`** — переписка (вопросы, ответы, сводки инструментов).
- **`session.jsonl`** — полный журнал для разбора полётов: каждый вызов инструмента с аргументами, сырым результатом и длительностью; события `context`/`compaction` (как заполнялся и сжимался контекст), `llm_usage` (токены, время и кэш каждого запроса к модели), `context_probe` (фактический контекст загруженной модели), MoE-события и аудит.

Сессии можно переключать (`/resume` — продолжить позже с тем же контекстом), искать по истории всех сессий инструментом `search_history`. Опционально файлы шифруются (см. раздел «Безопасность»).

### Горизонт 3 — постоянная память проекта (месяцы)

Markdown-файлы в домашней папке `~/.mma`, которые переживают любые сессии и подмешиваются в системный промпт каждой новой сессии:

- **`conventions.md`** — соглашения проекта (стиль кода, принятые практики).
- **`decisions.md`** — ключевые архитектурные решения («используем vitest, не jest»).
- **`errors.md`** — выученные ошибки. Пополняется автоматически: если один и тот же инструмент падает 3+ раза за сессию (например, сервер диагностики не стартует из-за битой установки), система записывает правило, чтобы в будущих сессиях агент сразу знал обходной путь.

Плюс явная память по запросу: инструменты `remember` / `recall` — «запомни, что…» / «что ты помнишь о…».

### Артефакты и кэши

Ряд рабочих данных тоже живёт на диске внутри проекта: ответы субагентов (`.mma/artifacts/<сессия>/`), планы (`.mma/plans/`), карта проекта (`.mma/index-cache.json`), куки браузера (`.mma/browser/cookies.json`). Всё это — часть той же философии: долговечные знания не держат в контексте.

## 10. Карта проекта (indexer)

Чтобы маленькая модель не гадала («наверное, это Next.js?»), при старте агент строит карту рабочего пространства:

- **Обход проекта**: рекурсивный обходчик определяет языки, считает файлы, вытаскивает ключевые экспорты из кода. Языки описаны данными: TypeScript/JavaScript, Python, Rust, Go, Java, Kotlin, C#, Ruby, PHP, Swift, Scala, C/C++, Shell, Lua (+ JSON/Markdown/YAML/TOML/XML/HTML/CSS). Обход игнорирует не только `node_modules`, но и `venv`/`.venv`/`__pycache__`, `target`, `vendor`, `.gradle`, `obj`, `.idea` и прочие вендорные деревья — иначе чужие зависимости забивают карту.
- **Профиль стека**: из манифестов (`package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`…) читается однострочное резюме `[Stack: …]` — название проекта, главные зависимости, скрипты. Модель сразу видит: Vite+React+TS, а не выдумывает фреймворк.
- **Кэш на диске**: результат индексации пишется в `<проект>/.mma/index-cache.json`, повторные запуски мгновенны.
- **Живая карта**: наблюдатель за файлами замечает изменения и пересобирает карту прямо посреди сессии (карта — динамический блок промпта, а не замороженный снимок со старта).
- **Файлы в промпте ранжируются**: в текстовую карту попадают не первые попавшиеся 100 файлов, а отсортированные по важности (исходники → тесты → документация/конфиги, самый плотный код-каталог первым, cap 80). Полный индекс при этом содержит все файлы.
- **Инструмент `project_map`** для агента и команды `mma map` / `/map` для пользователя: `summary` (языки, топ-каталоги, экспорты), `find` (поиск по путям и именам символов), `refresh` (принудительная переиндексация).

В сумме: агент всегда знает, *что за проект перед ним* и *где что лежит*, даже когда контекст давно сжат — карта восстановима с диска и обновляется сама.

## 11. RLM-приёмы: результаты по ссылке и чанкирование

Идея из статьи про Recursive Language Models — не тащить большие данные через контекст:

- **Артефакты**: полный ответ субагента сохраняется в файл (`.mma/artifacts/<сессия>/`), а родителю уходит короткий путь + резюме. Родитель читает файл целиком только если он действительно нужен. Защита от выхода за пределы каталога включена.
- **chunk_query**: длинный документ (лог, большой файл) режется на куски по границам строк; по каждому куску параллельно запускается простой вопрос-ответ к модели (без полного агентного цикла); результаты опционально синтезируются в итоговый ответ. Ограничение параллелизма настраивается.

## 12. Безопасность (подробно)

### Как устроена проверка: конвейер валидации

Каждый вызов инструмента проходит через конвейер:

```
вызов инструмента → плагины → валидаторы → само действие → плагины → результат
```

Порядок валидаторов зависит от типа инструмента: файловые операции проверяются валидатором путей и сканером содержимого, веб-операции — сетевым, команды — валидатором bash. Заблокированный вызов не доходит до файловой системы/сети, а факт блокировки пишется в аудит-журнал.

**Важно:** безопасность **включена по умолчанию** (пресет `balanced`): валидатор команд и сетевой активны, проверка путей и сканер содержимого по умолчанию выключены, но включаются одним переключателем у каждого валидатора. Полностью отключить можно флагом `security.enabled: false` — явный выбор пользователя уважается. Мастер первого запуска применяет ответы пользователя о безопасности к конфигу.

### Валидатор команд (bash)

- **Чёрный список команд**: `rm`, `dd`, `chmod`, `wget`, `curl`, `ssh` и т.п. — выполнение отклоняется.
- **Блокировка опасных флагов**: `-rf`, `--force`, `--no-preserve-root`.
- **Лазейки через интерпретаторы закрыты**: нельзя обойти blacklist, спрятав команду внутри `bun -e "..."` или аналогичных флагов интерпретаторов.
- **Белый список (опционально)**: строгий режим, где разрешены только явно перечисленные команды.
- Каждая команда логируется в аудит; на Windows серия повторяющихся запрещённых команд жёстко останавливается, чтобы агент не долбился в закрытую дверь.

### Валидатор путей

- **Глобальные запреты**: `.git/`, `node_modules/`, `.env`, `*.key` — чтение и запись запрещены независимо от контекста.
- **Контейнмент**: итоговый (разрешённый) путь обязан лежать внутри рабочей папки агента. Проверка устойчива к хитростям Windows: регистру букв, обоим типам разделителей и подмене через соседний префикс (`docs` vs `docs-other` — второй не пройдёт как «часть» первого).
- **Зоны субагентов**: каждый субагент получает собственный список разрешённых файлов (`allowed_files`) и файлов только-для-чтения (`read_only_files`) — выйти за зону он не может даже случайно.
- Применяется ко всем файловым инструментам. Отдельный нюанс: у MMA есть эвристика «исправления опечаток» в путях — поэтому правило такое, что её результат всегда перепроверяется валидатором, доверять ей самому нельзя.

### Валидатор сети

- Чёрный список доменов + опциональный белый список для `web_fetch`, `web_search`, `web_browse`, `download_file` и автоматического поиска по ошибкам.
- **Санитизация URL**: чувствительные query-параметры (токены, ключи в адресной строке) вычищаются до запроса.

### Сканер содержимого

Перед записью/правкой файла текст сканируется на опасные паттерны: `eval(`, `child_process.exec(`, `rm -rf` и подобные. Находка помечается, решение — показать предупреждение или заблокировать.

### Шифрование сессий

- Файлы `history.jsonl` и `session.jsonl` шифруются алгоритмом **AES-256-GCM** (современный стандарт с проверкой целостности).
- Путь к ключу настраивается в конфиге.
- Обратная совместимость: старые незашифрованные сессии читаются без конвертации.

### Аудит-журнал и уведомления

- Все значимые события пишутся в `~/.mma/logs/audit.jsonl`: вызовы инструментов, файловые операции, команды bash, сетевые запросы, блокировки безопасности.
- **Нотификатор**: поверх журнала работает система уведомлений — в файл `audit-notifications.jsonl` или webhook (с автоматическими ретраями при сбоях доставки).
- Фильтрация: по уровню серьёзности (`low` / `medium` / `high` / `critical`) и по типу событий — можно слушать только блокировки, игнорируя рутину.
- Есть статистика: сколько событий, каких типов, за период.

### Чистка секретов

Все сообщения логов и аудит-записи автоматически прогоняются через санитайзер: маскируются значения вида `sk-…`, заголовки `Bearer …` и поля с именами `api_key` / `token` / `password` / `secret`. Даже в собственных логах MMA секреты не должны светиться.

### Готовые политики

Три пресета одним переключением:

| Политика | Для чего | Характер |
|---|---|---|
| **strict** | продакшен, чужие машины | максимум запретов, минимум гибкости |
| **balanced** | повседневная работа (по умолчанию) | разумный баланс |
| **permissive** | тесты, песочницы | минимум ограничений |

Поддерживаются кастомные политики с переопределением отдельных правил.

### Прочие ограничители

- Глубина рекурсии субагентов ограничена (по умолчанию 3) — защита от бесконечного порождения субагентами субагентов.
- Лимиты числа файловых операций и частоты запросов (rate limits) — защита от шторма вызовов.

## 13. Диагностика кода (LSP + проверки)

- **LSP** (Language Server Protocol — тот же движок, что подсвечивает ошибки в редакторе): после каждой записи/правки файла агент получает настоящие ошибки компиляции мгновенно, а не после сборки. Поддержка TypeScript/JavaScript, Python, Rust, Go, JSON, HTML, CSS; в Angular-проектах `.html` обслуживает Angular-сервер. Есть отдельная команда «проверь ошибки в проекте». Мёртвый сервер диагностики виден в баннере при старте.
- **`/lsp doctor` (2.17.0)**: per-server диагностика «почему LSP не работает» — применим ли сервер, есть ли бинарник в PATH, пойдёт ли через `npx`, реальная проба `spawn + initialize` и **классифицированная причина** (`ok` / `disabled` / `not-applicable` / `binary-missing` / `offline` / `network` / `timeout` / `spawn-failed` / `server-error` / `deadline`) с actionable-подсказкой.
- **Офлайн-сеть (2.17.0)**: при `MMA_LSP_OFFLINE=1` `npx` не вызывается вообще — используются только бинарники из PATH; сервер, которому нужен `npx`, падает быстро и понятно. Сбой LSP сопровождается одним `hint:`-класса (нет бинарника / сеть / офлайн / spawn / таймаут), чтобы модель ушла на собственные build/test, а не ретраила вслепую.
- **lint-on-write**: после каждой записи — быстрая проверка синтаксиса; ошибка приписывается к результату записи, чтобы модель починила сразу же. Проверка типов гоняется **локальным** `tsc` через текущий рантайм (не `npx`) — быстро и без сетевых попыток; если локального `tsc` нет, проверка пропускается мгновенно, а не висит.
- Отсутствующий линтер не спамит ошибками — определяется один раз и пропускается.

## 14. Конвейер анти-галлюцинаций и честности

Перед показом ответа пользователя текст проверяется несколькими независимыми механизмами (детерминированными, без лишних вызовов LLM):

- **Проверка фактов** — упомянутые пути/файлы сверяются с известными (диск, индекс, сжатая память). Понимает dotfiles (`.prettierrc.json`); короткий путь (`webui/state.ts`) сопоставляется с полным (`src/modules/webui/state.ts`) по индексу базовых имён (2.15.0).
- **Проверка консистентности** — не противоречит ли модель решениям, принятым ранее в диалоге.
- **Проверка уверенности** — повторяющиеся ответы и маркеры неуверенности (короткий, но законченный ответ больше не считается «пустым»).
- **Success-claim check** — сильное заявление «готово/опубликовано» при наличии сигналов ошибок в последних 10 tool-выводах и без хеджинга запускает одну ограниченную перепроверку (`hall.claim_contradiction`), затем fail-open. Провалы `plan`/`plan_step`/`todo` игнорируются — они про служебный блокнот, а не про результат задачи (2.15.0).
- **Проверка артефактов** — если файл заявлен как созданный/валидный, но отсутствует или не парсится (проверка well-formed XML для `.xml/.drawio/.svg/.xaml/...`), либо вывод подан как результат запуска без успешных exec-тулов — ограниченный retry с отдельным бюджетом на класс (`claim`/`artifact`/`output`), чтобы одна съеденная попытка не экранировала другую ложь.
- **Honest-stop стрик** — серия полностью провальных пакетов инструментов: на 4-м подряд — директива «остановись, ответь честно, вывод не выдумывай»; на 6-м — жёсткий стоп (`retryLoopStopped`), чтобы модель не перебирала `python`/`python3`/`bun`/`pip` бесконечно.

Исходы: пропустить → показать с ⚠️ → перезапросить у модели → заблокировать после 3 попыток и спросить пользователя.

### In-loop критик (Counter-Agent, 2.6.0)

Дополнительный LLM-верификатор с опорой на **evidence**, работающий в обычном одиночном цикле (MoE-путь не затронут). Вызывается перед принятием финального ответа:

- **Evidence скоупится текущим заходом** — тулы прошлых вопросов не свидетельствуют против текущей задачи (фикс 2.13.1); чистый чат без тул-событий проходит `pass` без вызова LLM.
- **Поведение**: свежий `critical` в пределах `critic.maxRepairCycles` → ремонт + один retry; `concern`, `critical` сверх бюджета и near-identical повтор → инжект `<system-summary>` с советом и `pass` (без зацикливания на одинаковом ответе). Жёсткий лимит `critic.maxCalls` за прогон.
- **Что видит**: задачу, план, дайджест тулов, изменённые файлы, команды, выдержки файлов и (для ходов без мутаций) выдержку финального ответа ≤ 2000 символов. Изменения, сделанные вне файловых тулов (скрипты через bash, heredoc), учитываются через `git status --porcelain` (2.15.0).
- **Read-only tool-loop (Phase 2)**: критик может запросить до 3 проверок (`read_file`/`grep`/`glob`/`file_info`/`list_dir`) и вынести финальный вердикт по их выводам; лимит — общий таймаут, fail-open к вердикту первого прохода.
- **Fail-open**: null / timeout / битый JSON / throw ⇒ `pass`.
- **Конфиг**: `critic.{enabled,model,provider,tools,maxCalls,maxRepairCycles,timeoutMs}`; доступно в `/config` и web Settings.
- **Наблюдаемость**: события `critic_check`/`critic_verdict`/`critic_escalation` в `session.jsonl` + diagnostics-строка при verbose. **В чат вердикт не рисуется** — только model-facing repair через `<system-summary>`.

## 15. Модули (подсистемы)

- **Skills** — наборы инструкций по задачам, трёхуровневая progressive disclosure (сначала только названия, детали догружаются по мере нужды).
- **Плагины** — хуки на каждое событие жизненного цикла (до/после размышления, до/после инструмента, стриминг, конец хода `onTurnEnd`…). Изоляция ошибок: упавший плагин не валит остальных. Версионирование и дедупликация по имени, проверка совместимости с версией MMA. Поддерживаются папки-плагины. Пример-плагин trace-server транслирует работу агента в браузер в реальном времени; web-ui — браузерный чат с SSE-стримингом и `HostBridge` для отправки/прерывания запросов.
- **MCP** — подключение внешних инструментов по стандарту Model Context Protocol. Ленивое подключение: старт не блокируется недоступным сервером, обнаружение идёт в фоне с таймаутом, а модель может дёрнуть placeholder-`connect` при необходимости.
- **Pipelines** — многошаговые сценарии из YAML.
- **Indexer** — см. раздел [«Карта проекта»](#10-карта-проекта-indexer).
- **Память** — markdown-заметки между запусками: соглашения проекта, принятые решения, выученные ошибки.
- **Сессии** — несколько независимых диалогов с полным логом на диске; переключение, переименование, поиск по истории всех сессий.
- **Cost tracking** — стоимость сессии в долларах рядом с токенами, разбивка по провайдерам, свои цены для любых моделей. Учитываются кэш-чтение/запись, показывается экономия; `mma usage` выводит баланс/расход провайдера (OpenRouter).
- **Web UI (`mma web`)** — вторая реализация хоста над тем же ядром: SSE + REST, параллельные сессии (per-session раннеры + очередь ходов), сайдбар с вкладками **Session / Map / Trace**, streaming Markdown с подсветкой и копированием, activity rail, локализация, темы, вложения. Общий код с терминалом — через `Host`-контракт.
- **Критик (Counter-Agent)** — in-loop LLM-верификатор с evidence, см. раздел [«Конвейер анти-галлюцинаций и честности»](#14-конвейер-анти-галлюцинаций-и-честности).
- **Self-update** — проверка новой версии на npm и автоустановка; работающий процесс не прерывается. По умолчанию фоновая проверка и автоустановка выключены (`updater.checkOnStart: false`), включаются в конфиге.

## 16. Certification

Оффлайн-тест: «работает ли вот эта модель через вот этот бэкенд с MMA?»

- Набор сценариев (создать файл, исправить баг, проверить типы, MoE-сценарии…) прогоняется N раз через реального агента в песочнице.
- Проверка по фактам: файл существует, содержимое корректное, exit code, подстрока в выводе — словам агента не верим.
- Точечный перепрогон (`--scenarios <ids>`) с дозаписью результатов в манифест; пер-реп таймаут (`--timeout <ms>` + `timeoutMs` у сценария).
- Результат в манифесте: галочка ✔ у модели = сертифицирована на этом провайдере этой версией MMA. Глобальный манифест `~/.mma/certifications.json` синхронизируется с пакетом при обновлении.
- Можно добавлять свои сценарии в YAML.

## 17. REPL (интерактивный режим)

- **Собственный редактор строки** (не стандартный readline, который глючит под Bun): Shift+Enter для многострочного ввода, нормальная вставка из буфера (без дублей экрана), история, навигация по перенесённым строкам.
- Живой чеклист плана печатается при каждом изменении; заголовки инструментов привязаны к шагам плана.
- Горячие клавиши: двойной Esc — прервать текущую операцию, Ctrl+C — выход, Ctrl+V — вставить картинку из буфера.
- Автодеградация в plain-text без TTY/в CI.
- Slash-команды — полный список в разделе 18.

## 19. Прочее

- **i18n en/ru** — вообще все пользовательские строки через словарь, оба языка обязаны совпадать по ключам.
- **Кросс-платформенность** — процессы, пути, shell и файловые операции обязаны работать на Windows, macOS и Linux (без `mklink`/`npx` для локальных тулов, с квотированием путей; тест, которому не хватает примитива ОС, пропускается, а не падает).
- **Автообновление через npm** — см. модули выше; в dev-режиме (запуск из TypeScript-исходников) самообновление отключено, чтобы не перезаписать глобальную установку.
- **Мультипровайдер** — несколько провайдеров с приоритетами, ценами, лимитами запросов; переключение «на горячую»; автоматический failover.
- **Миграция с v1** — автоопределение старого конфига, бэкап всего `~/.mma`, аккуратный старт с новыми настройками.
- **Диагностика крашей** — глобальный перехват падений с окружением в `crash.jsonl`; отчёт об окружении (ОС, рантайм, инструменты, браузеры) в каждом логе сессии.
