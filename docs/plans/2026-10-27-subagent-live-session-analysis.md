## 2. Дефекты

### D1 (blocker). Субагент с `allowed_files` не может пользоваться `bash` и `grep`

`validateWorkdir` (`src/modules/security/path-validator.ts`) берёт корни
только из `scope.allowed_files` и требует, чтобы cwd лежал **внутри** одного из них.
Если скоуп перечисляет файлы (`src/App.tsx`, `src/`) или каталог уже проекта, то
cwd `bash` (`baseDir` = корень проекта) в него не попадает → любой `bash` блокируется.
`grep` этим путём не ломается: он запускает `rg` с cwd `baseDir` и workdir не
валидирует (его `path`-аргумент проверяется отдельно, как путь файлового тула).

**Доказательство:** 10 из 13 записей `security_block` в `audit.jsonl` — с причиной
`Workdir is outside the allowed scope for this sub-agent`
(21:01:04, 21:01:38, 21:06:22, 21:07:45, 21:07:48, 21:07:49, 21:08:39, 21:09:12,
21:09:31, 21:10:44) — все внутри трёх упавших прогонов.

**Воспроизведение:**

```
subagent(task: "прочитай src/components/*.tsx и верни отчёт",
         allowed_files: ["src/"], tool_tags: ["file", "code"])
```

любой `bash` внутри прогона → `[SECURITY BLOCKED] Workdir is outside the
allowed scope for this sub-agent`, хотя файлы в скоупе. С `allowed_files` из
отдельных файлов — то же самое.

**Наблюдаемое следствие:** прогон 21:07:43 не мог прочитать `tailwind.config.js`
(он вне `["src/"]`, хотя был назван в задаче) и не мог запустить сборку; вместо
чтения модель пошла искать обход — `find C:\ -maxdepth 2 -name package.json`,
`cmd.exe /c "dir /s /b …"` — и получила ещё три блока, сожгя бюджет.

**Почему это следствие структуры:** скоуп описан как список **файлов**, а `bash`/
`grep` оперируют **каталогом**. Пока контракт скоупа файловый, любой тул с cwd
невыразим, и каждый новый такой тул будет ломаться так же. Поэтому фикс — спека
скоупа (правило 2), а не правка одной ветки `if`: либо cwd разрешается внутри
`baseDir` при непустом скоупе (per-path проверки на чтение/запись остаются), либо
корни `bash` выводятся из общих каталогов scope-записей. Гейт-тест: `bash` в
пределах проекта проходит, `cat` файла вне скоупа — по решению спеки.

### D2 (blocker). «Лимит токенов» съедает reasoning, а не ответ

В `src/llm/openai-compat.ts:625-638` ошибка `llm_truncated` бросается только при
`finish_reason=length` **и** `!st.sawText` **и** без накопленного tool_call. То есть
за весь вызов модель не выдала ни одного символа `content` и ни одного tool_call —
бюджет съели reasoning-токены (deepseek-v4.1-flash отдаёт `reasoning_content`).

**Подтверждение из сессии:** прогон 21:14:03 просил «максимум 8 строк» и упал на
900 токенах, а тот же файл с `max_tokens: 4000` (21:14:31) дал ответ в два
предложения. Короткий ответ в обоих случаях; разница — бюджет на «размышление».

Почему это не лечится по тексту ошибки:

- `withTokenCap` (`src/llm/token-cap.ts`) — потолок на **каждый** вызов
  субагента; `provider.maxCompletionTokens` не задан в конфиге → дефолт **8192**
  (`src/config/registry-extra.ts:163-165`);
- ретрай (`MAX_LLM_ERROR_RETRIES = 2`, `src/core/agent/constants.ts:36`) повторяет
  детерминированный переполнение: отсюда 284 с и 219 с у двух прогонов, а
  reasoning-политика на `recoverableLlmError` поднимает effort до `high` — повтор
  гарантированно обрывается снова.

Связанный долг: `hosted-reasoning-discovery` (thinking-модель съедает маленькие
бюджеты) — это тот же класс на другом конце шкалы.

**Воспроизведение:** `subagent(task: "прочитай X и ответь 8 строками",
allowed_files: ["X"], max_tokens: 900, tool_tags: ["file"])` → `llm_truncated`,
`Частичный вывод:` пуст.

**Направление фикса:** при `finish_reason=length` без текста не повторять тот же
запрос, а один раз выключить reasoning и поднять бюджет; текст ошибки должен
называть настоящую причину.

### D3. `max_tokens` описан как «кап», но это общий бюджет генерации

`max_tokens` (схема `src/tools/subagent.ts`) подаётся как потолок ответа, но
провайдер считает в нём **и рассуждения**: «900» не значит «ответ на 900 токенов»,
это «рассуждения + ответ». Именно поэтому задача «ответь 8 строками» упала на 900,
а на 4000 — прошла. Вверх лимит при этом работает (петля не передаёт свой
`maxTokens`, поэтому `withTokenCap` подставляет `max_tokens` как есть), то есть
5000…32000 были рабочим рычагом — но подсказка в ошибке предлагала обратное
(«дробить вывод»), и модель пошла вниз по лимиту.

### D4. Прогон субагента не оставляет следа в `session.jsonl`

Между `subagent` call (21:01:03) и result (21:05:47) — **ноль** событий: ни
`llm_usage`, ни `tool_call`, ни причины падения. В лог попадают только блокировки
(через `audit.jsonl`). Стоимость прогона, число чтений, длина reasoning и момент
обрыва восстановить нельзя; «думал 4 минуты» и «прочитал 12 файлов» неотличимы.
Поверхности получают события через `ctx.subagentRuns` (в памяти), durable-следа нет.
`DEBT(subagent-run-invisible-in-session-log)`.

### D5. `expert_tag` не перечислен в схеме тула, а блок не пишется в audit

Модель дважды отправила `expert_tag: "code-review"` — это имя скилла, не эксперта
(конфиг: `code`, `research`, `browser`, `vision`). Список валидных тегов есть только
в тексте ошибки; второй вызов — побайтовый повтор первого после `load_skill`, то
есть обратной связи не хватило. Ветка «unknown expert_tag»
(`src/tools/subagent-run.ts:88-94`) возвращает ошибку **без** `logSecurityBlock`,
поэтому блок виден только в `tool_result` родителя и не попадает в `audit.jsonl`.

### D6. Ошибка провайдера 403 не видна пользователю и не приводит к failover

20:54:31 и 20:54:55 — `llm.call` 403 `RegionError` в `session.jsonl`; в
`history.jsonl` **ни одного** сообщения об ошибке. Пользователь трижды вручную
отправил одну и ту же фразу (20:54:30, 20:54:54, 20:55:00) и только после смены
провайдера получил ответ. `provider.json` не содержит `fallback`, поэтому
детерминированная ошибка не переключает модель.
`DEBT(llm-provider-error-invisible-to-user)`.

## 5. Как повторить разбор

```powershell
$s = "$env:USERPROFILE\.mma\sessions\ses_mvoac9q9_ukjrorvcgjrkhyrv"
# события хода: типы, тулы, причины
Get-Content "$s\session.jsonl" -Encoding UTF8 |
  ForEach-Object { $_ | ConvertFrom-Json } |
  Where-Object type -in 'tool_call','tool_result','error','user','llm_usage'
# блокировки
Get-Content "$s\audit.jsonl" -Encoding UTF8 |
  ForEach-Object { $_ | ConvertFrom-Json } |
  Where-Object action -eq 'security_block'
```

Консоль Windows в OEM-кодировке портит кириллицу — вывод лучше писать в файл
(`Out-File -Encoding utf8`) и читать оттуда.
