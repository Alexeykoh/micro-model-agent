# F2: OpenCode's tool system

## Findings

### [1] OpenCode uses Effect-TS for tool definition with a `Tool.define()` function that takes an ID and an Effect yielding a tool definition object
- quote: "export function define<Parameters extends Schema.Decoder<unknown>, Result extends Metadata, R, ID extends string = string>(id: ID, init: Effect.Effect<Init<Parameters, Result>, never, R>): Effect.Effect<Info<Parameters, Result>, never, R | Truncate.Service | Agent.Service> & { id: ID }"
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/tool.ts
- source_type: primary
- published: unknown
- confidence: high

### [2] Each tool is defined as a `Def` interface with id, description, parameters (an Effect Schema decoder), optional JSON schema, and an execute function
- quote: "export interface Def<Parameters extends Schema.Decoder<unknown> = Schema.Decoder<unknown>, M extends Metadata = Metadata> { id: string; description: string; parameters: Parameters; jsonSchema?: JSONSchema7; execute(args: Schema.Schema.Type<Parameters>, ctx: Context): Effect.Effect<ExecuteResult<M>>; formatValidationError?(error: unknown): string }"
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/tool.ts
- source_type: primary
- published: unknown
- confidence: high

### [3] Tool schemas use Effect's Schema library (not Zod internally for built-in tools), though Zod is used at the registry boundary for plugin/custom tools
- quote: "Plugin tools still expose Zod args publicly; keep that compatibility boxed at the registry boundary and give the LLM the original JSON Schema."
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/registry.ts
- source_type: primary
- published: unknown
- confidence: high

### [4] Individual tool parameters are defined using Schema.Struct with typed fields and .annotate() for descriptions (e.g., the ReadTool)
- quote: "export const Parameters = Schema.Struct({ filePath: Schema.String.annotate({ description: 'The absolute path to the file or directory to read' }), offset: Schema.optional(NonNegativeInt).annotate({ description: 'The line number to start reading from (1-indexed)' }), limit: Schema.optional(NonNegativeInt).annotate({ description: 'The maximum number of lines to read (defaults to 2000)' }) })"
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/read.ts
- source_type: primary
- published: unknown
- confidence: high

### [5] The ToolRegistry collects all tools, lazily initializes them, and exposes a `tools()` method that filters by provider, model, and agent permissions before returning the final tool list
- quote: "const tools: Interface['tools'] = Effect.fn('ToolRegistry.tools')(function* (input) { const filtered = (yield* all()).filter((tool) => { ... }) })"
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/registry.ts
- source_type: primary
- published: unknown
- confidence: high

### [6] Tool execution wraps arguments through the Effect Schema decoder, catching schema errors and converting them to `InvalidArgumentsError` for the LLM to retry
- quote: "const decoded = yield* decode(args).pipe(Effect.mapError((error) => new InvalidArgumentsError({ tool: id, detail: toolInfo.formatValidationError ? toolInfo.formatValidationError(error) : String(error), })))"
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/tool.ts
- source_type: primary
- published: unknown
- confidence: high

### [7] Each tool receives a rich `Context` object with sessionID, messageID, agent name, abort signal, messages array, and both a `metadata()` callback and an `ask()` callback for permission requests
- quote: "export type Context<M extends Metadata = Metadata> = { sessionID: SessionID; messageID: MessageID; agent: string; abort: AbortSignal; callID?: string; extra?: { [key: string]: unknown }; messages: SessionV1.WithParts[]; metadata(input: { title?: string; metadata?: M }): Effect.Effect<void>; ask(input: Omit<PermissionV1.Request, 'id' | 'sessionID' | 'tool'>): Effect.Effect<void> }"
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/tool.ts
- source_type: primary
- published: unknown
- confidence: high

### [8] Custom tools are created by placing .ts/.js files in `.opencode/tools/` or `~/.config/opencode/tools/`, using a Zod-based `tool()` helper from `@opencode-ai/plugin`
- quote: "Tools are defined as TypeScript or JavaScript files. They can be defined: Locally by placing them in the .opencode/tools/ directory of your project. Or globally, by placing them in ~/.config/opencode/tools/."
- url: https://opencode.ai/docs/custom-tools/
- source_type: primary
- published: Jul 14, 2026
- confidence: high

### [9] Tool output is automatically truncated using a Truncate service; the tool system wraps execution to ensure output stays within token limits
- quote: "const truncated = yield* truncate.output(result.output, {}, agent) return { ...result, output: truncated.content, metadata: { ...result.metadata, truncated: truncated.truncated, ...(truncated.truncated && { outputPath: truncated.outputPath }), } }"
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/tool.ts
- source_type: primary
- published: unknown
- confidence: high

### [10] Tool descriptions are loaded from companion .txt files (e.g., read.txt, edit.txt) and injected as the tool's description string, keeping prompts separate from code
- quote: "import DESCRIPTION from './read.txt'" (in read.ts)
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/read.ts
- source_type: primary
- published: unknown
- confidence: high

### [11] Permissions gate tool access at three levels (allow/ask/deny) using wildcard glob patterns against tool names, with per-agent overrides and an evaluation order where last matching rule wins
- quote: "Each permission key can be set to: 'ask' — Prompt for approval before running the tool, 'allow' — Allow all operations without approval, 'deny' — Disable the tool"
- url: https://opencode.ai/docs/agents/
- source_type: primary
- published: Jul 14, 2026
- confidence: high

### [12] MCP (Model Context Protocol) tools and custom plugin tools are integrated at the registry level by converting their Zod schemas to JSON Schema and wrapping their promise-based execute functions into Effect-based ones via EffectBridge
- quote: "const bridge = yield* EffectBridge.make() const pluginCtx: PluginToolContext = { ...toolCtx, ask: (req) => bridge.promise(toolCtx.ask(req)), directory: ctx.directory, worktree: ctx.worktree, }"
- url: https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/registry.ts
- source_type: primary
- published: unknown
- confidence: high

## Dead ends
- The `sst/opencode` GitHub URL no longer resolves; the repo moved to `anomalyco/opencode`. No harm done since the `dev` branch had all needed files.
- The `schema.ts` file in the tool directory is just a tiny ID schema (ToolID branded type), not the main schema system. The real schema work happens via Effect's `Schema` library.

## Suggested follow-ups
- Investigate how the Vercel AI SDK's tool schema format integrates with OpenCode's Effect Schema system (the `@ai-sdk/provider` JSONSchema7 type suggests tight coupling)
- Study the `truncate.ts` service to understand token-budget-aware output truncation for small models
- Examine the `apply_patch` tool for a more complex tool definition pattern with multi-file mutation
- Look at the permission system (`permission.ts`) for fine-grained glob-based permission evaluation
