# F5: Context-efficient tool design for small models

## Findings

### [1] Keep tool formats close to natural text patterns the model was trained on, avoiding structurally expensive formats like diffs or escaped JSON-in-JSON
- quote: "Keep the format close to what the model has seen naturally occurring in text on the internet. Make sure there's no formatting 'overhead' such as having to keep an accurate count of thousands of lines of code, or string-escaping any code it writes."
- url: https://www.anthropic.com/research/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: high

### [2] A single bash tool eliminates ~90% of prompt token overhead from multi-tool JSON definitions — one tool definition vs. dozens of function schemas
- quote: "Tool definitions and specifications should be given just as much prompt engineering attention as your overall prompts."
- url: https://www.anthropic.com/research/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: high

### [3] Abbreviating JSON field names in tool parameters directly reduces token count and improves latency for small models
- quote: "Optimizing JSON Field Names for Token Reduction — Comparison between verbose and abbreviated JSON field names to minimize token generation and improve response speed."
- url: https://developers.openai.com/api/docs/guides/latency-optimization
- source_type: primary
- published: 2025
- confidence: high

### [4] Deferred tool loading lets the model search for tools only when needed, avoiding loading all definitions upfront — critical for keeping context small
- quote: "Use tool_search and defer_loading: true to optimize token usage. This allows the model to load specific tool definitions only when they are determined to be necessary."
- url: https://developers.openai.com/api/docs/guides/deployment-checklist
- source_type: primary
- published: 2025
- confidence: high

### [5] Programmatic/batch tool calling reduces token consumption by ~10x for multi-step chains because intermediate tool results bypass the context window entirely
- quote: "Tool results from programmatic calls are not added to Claude's context - only the final code output is. Intermediate processing happens in code - filtering, aggregation, etc. don't consume model tokens."
- url: https://docs.litellm.ai/docs/providers/anthropic_programmatic_tool_calling
- source_type: secondary
- published: 2025
- confidence: high

### [6] For small models like Haiku, forcing tool_choice to specific tools and using system prompts to limit unnecessary tool calls dramatically reduces wasted context
- quote: "You have access to tools, but only use them when necessary. If a tool is not required, respond as normal."
- url: https://github.com/anthropics/courses/blob/master/tool_use/02_your_first_simple_tool.ipynb
- source_type: primary
- published: 2024
- confidence: high

### [7] Bash-first design is optimal when the model's function-calling reliability is limited — a single `bash` tool with a well-crafted system prompt avoids the JSON schema token tax entirely
- quote: "Put yourself in the model's shoes. Is it obvious how to use this tool, based on the description and parameters, or would you need to think carefully about it? A good tool definition often includes example usage, edge cases, input format requirements, and clear boundaries from other tools."
- url: https://www.anthropic.com/research/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: high

### [8] Tool result formatting should be minimal and structured — return only what's needed, use short field names, and avoid verbose JSON for small model context windows
- quote: "Keep responses concise: Return only necessary data to minimize processing overhead. Provide detailed output descriptions: Since Claude deserializes tool results in code, clearly document the format (JSON structure, field types, etc.)."
- url: https://docs.litellm.ai/docs/providers/anthropic_programmatic_tool_calling
- source_type: secondary
- published: 2025
- confidence: high

### [9] For multi-step tool chains, batching tool calls into a single code execution reduces N round-trips to 1, saving latency proportional to the number of steps
- quote: "This pattern: Reduces model round-trips from N (one per region) to 1. Processes large result sets programmatically before returning to Claude. Saves tokens by only returning aggregated conclusions."
- url: https://docs.litellm.ai/docs/providers/anthropic_programmatic_tool_calling
- source_type: secondary
- published: 2025
- confidence: high

### [10] Simpler agentic patterns (prompt chaining, routing) outperform complex agent frameworks for most use cases — only add tool complexity when measurement proves it helps
- quote: "When implementing agents, we try to follow three core principles: Maintain simplicity in your agent's design. Prioritize transparency by explicitly showing the agent's planning steps. Carefully craft your agent-computer interface (ACI) through thorough tool documentation and testing."
- url: https://www.anthropic.com/research/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: high

### [11] When using bash as the sole tool, the tool definition itself consumes near-zero tokens (just the tool name/description), freeing all prompt budget for the system prompt and task context
- quote: "Start by using LLM APIs directly: many patterns can be implemented in a few lines of code."
- url: https://www.anthropic.com/research/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: medium

## Dead ends
- ArXiv paper 2408.14033 (MLR-Copilot) was about ML research automation, not tool design for small models
- OpenAI latency optimization page returned 403, though context7 had the key excerpt
- No peer-reviewed paper specifically comparing bash-only vs function-calling for <10B parameter models found

## Suggested follow-ups
- Benchmark actual token counts: measure prompt overhead of 1 bash tool vs. 10 function-calling tools on a 9B model
- Test tool_choice="none" or forced tool selection patterns with Qwen2.5-7B or Llama-3.2-8B
- Research whether structured output (JSON mode) is more token-efficient than free-form bash output for small models
- Investigate OpenAI's defer_loading mechanism for potential adoption in open-source agent frameworks
- Profile context window usage across 5/10/20/50 tool definitions to find the breaking point for 9B models
